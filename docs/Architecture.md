# Architecture

## 1. Обзор системы

```
 ┌─────────────────────┐          HTTPS POST (webhook)          ┌──────────────────────┐
 │   SMS Gateway App    │  ?upload_token=... / X-Upload-Token   │                        │
 │ (сторонний, на теле- │ ─────────────────────────────────────▶│                        │
 │  фоне с SIM-картой)  │  X-Signature: HMAC-SHA256 (опц.)       │                        │
 └─────────────────────┘                                        │      Go Backend       │
                                                                  │                        │
 ┌─────────────────────┐        REST API (JWT + download_token) │  handlers → services  │
 │  Android Viewer App  │ ◀─────────────────────────────────────│    → storage           │
 │  (наше приложение)   │                                        │                        │
 │                       │ ◀─────────────────────────────────────│                        │
 └─────────────────────┘        WebSocket/SSE (push новых SMS)   └───────────┬────────────┘
                                                                              │
                                                                     ┌────────▼────────┐
                                                                     │     SQLite       │
                                                                     └──────────────────┘
```

Поток данных: телефон-шлюз получает SMS → приложение-шлюз отправляет webhook на бэкенд с `upload_token` → бэкенд проверяет токен (и опционально HMAC-подпись), сохраняет сообщение → бэкенд рассылает новое сообщение по WebSocket/SSE всем подписанным viewer-клиентам и отдаёт историю через REST.

## 2. Компоненты

### 2.1 Gateway App (внешний, неизменяемый)

Стороннее приложение [android_income_sms_gateway_webhook](https://github.com/bogkonstantin/android_income_sms_gateway_webhook). Формат запроса:

- **Метод:** `POST`, `Content-Type: application/json; charset=utf-8`
- **Тело:**
  ```json
  {
    "from": "номер отправителя",
    "text": "текст сообщения",
    "sentStamp": "временная метка отправки",
    "receivedStamp": "временная метка получения",
    "sim": "слот SIM"
  }
  ```
- **Опциональная подпись:** заголовок `X-Signature` — HMAC-SHA-256 от тела запроса.
- **Retry:** приложение само повторяет отправку (до 10 попыток с экспоненциальной задержкой), бэкенду важно быть идемпотентным/устойчивым к дублям.
- `upload_token` передаётся в URL (query-параметр) или в кастомном заголовке — настраивается в самом приложении-шлюзе как часть URL webhook.

### 2.2 Backend (Go)

Слоистая структура: `handlers → services → storage` (repository pattern).

- **HTTP-сервер** — роутинг (например, `chi` или `gin`; конкретный выбор — деталь реализации, не фиксируется здесь).
- **Модуль авторизации пользователей** — логин/пароль → хэш пароля (bcrypt/argon2) → выдача JWT access + refresh.
- **Модуль устройств и токенов** — генерация, ревокация и перевыпуск `upload_token` (привязан к Device) и `download_token` (привязан к паре Device–подписчик).
- **Модуль приёма webhook** — проверка `upload_token`, опциональная проверка `X-Signature`, дедупликация повторов, сохранение SMS.
- **Модуль раздачи сообщений** — REST для списка/фильтрации/пагинации истории, WebSocket или SSE для push новых сообщений подписанным клиентам.

### 2.3 Хранилище

SQLite на старте (один файл, без внешней СУБД). Верхнеуровневые таблицы:

- `users` — учётные записи (логин, хэш пароля).
- `devices` — устройства-шлюзы, каждое с собственным `upload_token`, привязанное к владельцу.
- `viewer_bindings` — связь "кто может просматривать какое устройство", хранит `download_token`, реализует модель многие-ко-многим.
- `messages` — принятые SMS, привязаны к `device_id`.
- `refresh_tokens` — активные refresh-токены пользователей (для ротации/отзыва).

При росте нагрузки — миграция на PostgreSQL без изменения слоя `services`/`handlers` (storage реализует интерфейс репозитория).

### 2.4 Android Viewer App

- Экран логина (логин/пароль → получение JWT).
- Список привязанных устройств-шлюзов.
- Добавление устройства по `download_token` (ручной ввод или QR-код).
- Лента сообщений выбранного устройства с realtime-обновлением через WebSocket/SSE, историей через REST.

## 3. Модель данных

- `User` 1 — N `Device`: пользователь регистрирует устройство-шлюз и получает для него `upload_token`.
- `User`/`Device` N — M через `viewer_bindings`: любой пользователь может получить `download_token` на любое устройство (если ему его выдали), и одно устройство может просматриваться несколькими пользователями.
- `Device` 1 — N `Message`: все SMS, пришедшие с этого устройства.

## 4. Аутентификация и токены

- **Пользователи:** логин + пароль → JWT access-токен (короткий TTL, например 15 мин) + refresh-токен (длинный TTL, с ротацией при каждом использовании и возможностью отзыва).
- **`upload_token`:** привязан к записи `Device`, передаётся приложением-шлюзом при каждом webhook-запросе, определяет, в какое устройство записать сообщение. Может быть отозван и перевыпущен владельцем устройства.
- **`download_token`:** привязан к `Device`, а не к паре (`Device`, подписчик) — это многоразовая "инвайт-ссылка": устройство может иметь несколько одновременно активных `download_token` (например, отдельный для семьи и для коллег), и любой аутентифицированный пользователь, знающий конкретный токен, может сам добавить себе доступ. Используется вместе с JWT для получения доступа к потоку конкретного устройства. Обеспечивает модель "многие ко многим" — несколько шлюзов, несколько просматривающих аккаунтов, гибкая раздача доступа без совместного использования пароля владельца устройства. Точечная ревокация одного `download_token` рвёт доступ только тем, кто подключился через него — см. [спецификацию 0002-devices-tokens](specs/0002-devices-tokens.md).
- **`X-Signature` (HMAC-SHA-256):** опциональная дополнительная проверка целостности webhook-запроса, если она включена в настройках приложения-шлюза; секрет для подписи хранится вместе с записью `Device`.

## 5. Realtime-доставка

- **WebSocket** (или SSE как более простая альтернатива) — push новых сообщений подписанным viewer-клиентам сразу после сохранения в БД.
- **REST** — используется для начальной загрузки истории, пагинации и как fallback, если realtime-соединение недоступно.

## 6. Развёртывание (для старта)

- Один Go-бинарник + файл SQLite, упакованные в Docker-контейнер.
- Без внешних зависимых сервисов на старте (не требуется отдельный сервер БД, брокер сообщений и т.п.).
- При росте пользователей/нагрузки — миграция хранилища на управляемый PostgreSQL, слой `storage` спроектирован так, чтобы это не затронуло остальной код.

## 7. Безопасность

- Обязательный HTTPS для всех соединений (webhook, REST, WebSocket).
- Хэширование паролей пользователей (bcrypt/argon2), пароли никогда не хранятся в открытом виде.
- Ротация refresh-токенов, возможность отзыва отдельной сессии.
- Возможность отзыва/перевыпуска `upload_token` и `download_token` независимо друг от друга.
- Rate-limiting на webhook-эндпоинт для защиты от злоупотреблений/флуда.
- Проверка HMAC-подписи (`X-Signature`), если она включена в настройках устройства-шлюза.
