# Roadmap

Дорожная карта разработки по этапам, от базовой инфраструктуры до MVP и дальнейших улучшений. Порядок последовательный — этапы без явных зависимостей от следующих можно частично распараллелить, но рекомендуется двигаться сверху вниз.

## Milestone 0 — Подготовка

- [x] Инициализация Go-модуля, структура проекта (`cmd/`, `internal/handlers`, `internal/services`, `internal/storage`)
- [x] Инициализация Android Viewer App проекта (Kotlin, минимальный шаблон)
- [x] Настройка SQLite и системы миграций (собственный минимальный мигратор на `embed.FS`, без cgo-зависимостей)

## Milestone 1 — Авторизация пользователей

- [x] Регистрация и логин по логину + паролю, хэширование паролей (bcrypt/argon2)
- [x] Выдача JWT access + refresh, эндпоинт обновления токена
- [x] Логаут и отзыв refresh-токена
- [x] Таблицы `users`, `refresh_tokens`

См. [спецификацию 0001-auth](specs/0001-auth.md).

## Milestone 2 — Устройства и токены

- [x] CRUD для `devices`: регистрация устройства-шлюза
- [x] Генерация, ревокация и перевыпуск `upload_token`
- [x] `viewer_bindings`: выдача и отзыв `download_token` для привязки просматривающих аккаунтов к устройству

См. [спецификацию 0002-devices-tokens](specs/0002-devices-tokens.md).

## Milestone 3 — Приём SMS (webhook)

- [x] Эндпоинт приёма webhook от Gateway App: валидация `upload_token`

- [x] Дедупликация повторных доставок (Gateway App повторяет отправку до 10 раз)
- [x] Сохранение сообщений в `messages`
- [x] Ручное end-to-end тестирование с реальным приложением-шлюзом на устройстве (2026-08-26, реальный SMS дошёл до Viewer App через Gateway App → webhook → бэкенд)

## Milestone 12 — Android Gateway App (собственное SMS-приложение по умолчанию)

**Этап 1 (готово):**
- [x] Новый отдельный Android-проект (`android_gateway/`), с манифестом из всех 4 обязательных компонентов дефолтного SMS-приложения (`SMS_DELIVER_ACTION`, `WAP_PUSH_DELIVER_ACTION` — заглушка, `RESPOND_VIA_MESSAGE` — минимальная реализация без UI, `SENDTO` — экран-заглушка); подтверждено на физическом устройстве (TECNO LI9/HiOS), что приложение появляется в списке кандидатов и реально становится дефолтным
- [x] Приём входящих SMS через `SMS_DELIVER_ACTION`, определение SIM-слота через официальный API, сохранение в локальную Room-БД
- [x] Пересылка на существующий backend-webhook (`0003-sms-webhook.md`, формат/эндпоинт без изменений) через Hilt+WorkManager с экспоненциальным ретраем; сообщение, пришедшее до настройки сервера/токена, не теряется — повторно отправляется при сохранении настроек
- [x] Ручное сквозное подтверждение на физическом устройстве: реальная SMS дошла, сохранилась, доставлена на бэкенд (`docker logs`, `201`); в процессе найден и исправлен реальный баг рассинхронизации `RoleManager`/legacy `Settings.Secure.sms_default_application` на этом OEM

**Этап 2 (готово):**
- [x] Список диалогов (группировка по номеру, последнее сообщение сверху) и экран переписки (полная история по номеру)
- [x] Отправка SMS из UI (`SmsManager`, экран переписки) — сохраняется локально как исходящее; на backend не пересылается (формат `0003-sms-webhook.md` покрывает только входящие, не менялся)
- [x] Импорт истории из `content://sms` при первом запуске после назначения дефолтным (разовый, с флагом в настройках)
- [x] Unit-тест на логику определения SIM-слота (вынесена в чистую функцию `SimSlotResolver`, закрывает пробел этапа 1)
- [x] Ручной триггер повторной отправки для отдельного `FAILED`-сообщения (кнопка «Повторить»), закрывает пробел этапа 1
- [x] Ручное сквозное подтверждение на физическом устройстве: импорт истории, приём во время этой сессии, отправка нового сообщения (сохранено, без краша) — в процессе `peer-review-template` найдены и исправлены 3 реальных бага (некоррелированный SQL-запрос списка диалогов, отсутствие `onNewIntent` в `MainActivity` — из-за чего переход по `sms:`-ссылке терялся при уже открытом приложении, отсутствие обработки ошибок при отправке SMS)

**Этап 4 (готово 2026-08-28):**
- [x] Выбор SIM-слота при отправке: `SimOptionsProvider` (`SubscriptionManager`), селектор в UI виден только при 2+ активных SIM, `MessageRepository.sendMessage`/`OutgoingSmsSender` принимают `subscriptionId`/`simSlot`. Сквозная проверка UI→ViewModel→Repository покрыта тестом (`ThreadViewModelTest`, добавлен после того, как `peer-review-template` нашёл пробел — предыдущие тесты проверяли только UI-состояние селектора, не то, что выбранный slot реально доходит до `sendMessage`). Не проверено на реальном dual-SIM устройстве (на TECNO LI9 не подтверждено наличие двух активных SIM) — логика верна, но живого прогона с двумя настоящими SIM нет.
- [x] `RESPOND_VIA_MESSAGE` — **проверено и подтверждено расхождение с OEM, не баг приложения**: вызвать сервис через `adb` напрямую нельзя (нужно signature-разрешение `SEND_RESPOND_VIA_MESSAGE`, есть только у системного дайлера). Сделан реальный тест: звонок с другого телефона, отклонение через встроенную функцию OEM-дайлера (Transsion/HiOS «smart.caller») «отклонить с сообщением» — SMS реально дошла до звонившего. Но `adb logcat` и БД приложения сразу после теста не показали ни одного вызова `RespondViaMessageService`; позже, после переустановки и повторного разового импорта `content://sms`, это же сообщение появилось в истории — подтверждено, что оно было отправлено напрямую через системный провайдер самим OEM-дайлером, **в обход** стандартного механизма `RESPOND_VIA_MESSAGE`. Manifest/permission сервиса сверены с эталонной декларацией AOSP/Google Messages — совпадают, ошибки конфигурации нет. Вывод: этот OEM не использует штатный контракт дефолтного SMS-приложения для быстрого ответа (аналогично уже задокументированным на этом OEM расхождениям — Hiber-заморозка, рассинхронизация `RoleManager`). На стоковом Android/дайлере Google Phone сервис будет вызван как положено.
- [x] `WapPushReceiver` — вместо полного no-op сохраняет видимую заглушку («[MMS] содержимое не поддерживается») в Room по той же схеме `goAsync`+`try/catch/finally`, что и `SmsDeliverReceiver`, не пересылается на webhook.
- [x] Live-подхват записей, которые сторонние компоненты пишут напрямую в `content://sms` в обход `SMS_DELIVER`/`RESPOND_VIA_MESSAGE` (реальный случай — quick-reply OEM-дайлера, см. пункт выше): `ContentObserver` в `GatewayApp` + инкрементальная синхронизация по watermark `_ID` (`SmsHistoryImporter.syncNewMessages()`), плюс fallback-проверка при каждом `ON_RESUME` экрана (на случай, если процесс был не запущен в момент записи). `peer-review-template` нашёл и исправил реальную гонку — `ContentObserver` и `ON_RESUME`-fallback могли одновременно прочитать один и тот же watermark и задвоить вставку — закрыто общим `Mutex` на обоих методах. Живая проверка дважды на устройстве: до фикса запись OEM-дайлера появлялась только после переустановки; после — появилась в списке диалогов без переустановки/перезапуска приложения. Известное ограничение: наблюдатель подписан только на дерево `content://sms` (текстовые SMS), не на `content://mms` — на подхват MMS-контента эта доработка не распространяется.
- [ ] Живая проверка приёма реального MMS/WAP push — не проводилась (заглушка реализована и не должна падать, но реальный MMS не приходил в течение тестирования)
- [ ] Подтверждение фактической доставки SMS, отправленного из UI треда (не через OEM quick-reply), реальному получателю — проверено только сохранение исходящего сообщения в БД без краша
- [ ] HMAC-подпись webhook-запроса, поиск/архивация/удаление диалогов, живой приём на подтверждённом dual-SIM устройстве

**UI/UX-доработки (найдено по M3-чеклисту `android-skills:android-ux`, 2026-08-28; готово 2026-08-28; полностью дефолтная тема — не проблема, оставлена как есть, тёмная тема будет проверена вручную отдельно пользователем):**
- [x] Список диалогов: карточки между строками (`Card`, `heightIn(min=48dp)`), время последнего сообщения (`dd.MM HH:mm`), имя контакта через `ContactNameResolver`/`READ_CONTACTS` с откатом на номер при отсутствии совпадения, пустое состояние и индикатор загрузки (`LinearProgressIndicator`) на время первого импорта истории, `TopAppBar`, FAB «новое сообщение» → `NewMessageDialog` → переход в тред
- [x] Экран переписки: чат-пузыри (`primaryContainer`/`surfaceVariant` по направлению сообщения), `TopAppBar` с именем/номером собеседника и кнопкой «назад», автоскролл к последнему сообщению, время на сообщении, статус «отправляется» (спиннер вместо кнопки, поле недоступно), кнопка «Повторить» в `MaterialTheme.colorScheme.error`
- [x] Настройки: поля в карточке, подсказки под полями, кнопка «Скопировать» токена (`LocalClipboardManager`)
- [x] Экран «сделать приложением по умолчанию»: иконка, развёрнутое объяснение
- [~] Accessibility — частично: строки списка ≥48dp и `semantics(mergeDescendants=true)` добавлены; реальный прогон с включённым TalkBack не проводился — только структурные семантические аннотации, без живой проверки

Найдено `peer-review-template` и исправлено: `SmsHistoryImporter.isImporting` мог зависнуть в `true` навсегда и уронить приложение при любом исключении в процессе импорта истории (флаг сбрасывался не в `finally`) — обёрнуто в `try/catch/finally`. Известное ограничение (не блокирует, в backlog): при обрыве процесса посреди импорта (не пойманное исключение, не сбой самого чтения) уже вставленные строки могут задвоиться при повторной попытке — импорт не транзакционный. Также как раскрытое ограничение производительности: `ConversationsViewModel` заново резолвит имя контакта для всех диалогов при каждом новом входящем SMS (без кеша) — приемлемо на ожидаемом масштабе личного использования, для будущей оптимизации при большом числе контактов.

Спецификация 0013 остаётся `Draft` — MVP ещё не закрыт целиком. См. [спецификацию 0013-android-gateway-app](specs/0013-android-gateway-app.md).
