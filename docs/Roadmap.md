# Roadmap

Дорожная карта разработки по этапам, от базовой инфраструктуры до MVP и дальнейших улучшений. Порядок последовательный — этапы без явных зависимостей от следующих можно частично распараллелить, но рекомендуется двигаться сверху вниз.

## Milestone 0 — Подготовка

- [x] Инициализация Go-модуля, структура проекта (`cmd/`, `internal/handlers`, `internal/services`, `internal/storage`)
- [x] Инициализация Android Viewer App проекта (Kotlin, минимальный шаблон)
- [x] Настройка SQLite и системы миграций (собственный минимальный мигратор на `embed.FS`, без cgo-зависимостей)

## Milestone 1 — Авторизация пользователей

- [x] Логаут и отзыв refresh-токена
- [x] Таблицы `users`, `refresh_tokens`

**Этап 4 (готово 2026-08-28):**
- [x] Выбор SIM-слота при отправке: `SimOptionsProvider` (`SubscriptionManager`), селектор в UI виден только при 2+ активных SIM, `MessageRepository.sendMessage`/`OutgoingSmsSender` принимают `subscriptionId`/`simSlot`. - [x] `RESPOND_VIA_MESSAGE` — **проверено и подтверждено расхождение с OEM, не баг приложения**: вызвать сервис через `adb` напрямую нельзя (нужно signature-разрешение `SEND_RESPOND_VIA_MESSAGE`, есть только у системного дайлера). Вывод: этот OEM не использует штатный контракт дефолтного SMS-приложения для быстрого ответа (аналогично уже задокументированным на этом OEM расхождениям — Hiber-заморозка, рассинхронизация `RoleManager`). На стоковом Android/дайлере Google Phone сервис будет вызван как положено.
- [x] `WapPushReceiver` — вместо полного no-op сохраняет видимую заглушку («[MMS] содержимое не поддерживается») в Room по той же схеме `goAsync`+`try/catch/finally`, что и `SmsDeliverReceiver`, не пересылается на webhook.
- [x] Live-подхват записей, которые сторонние компоненты пишут напрямую в `content://sms` в обход `SMS_DELIVER`/`RESPOND_VIA_MESSAGE` (реальный случай — quick-reply OEM-дайлера, см. пункт выше): `ContentObserver` в `GatewayApp` + инкрементальная синхронизация по watermark `_ID` (`SmsHistoryImporter.syncNewMessages()`), плюс fallback-проверка при каждом `ON_RESUME` экрана (на случай, если процесс был не запущен в момент записи). `peer-review-template` нашёл и исправил реальную гонку — `ContentObserver` и `ON_RESUME`-fallback могли одновременно прочитать один и тот же watermark и задвоить вставку — закрыто общим `Mutex` на обоих методах. Живая проверка дважды на устройстве: до фикса запись OEM-дайлера появлялась только после переустановки; после — появилась в списке диалогов без переустановки/перезапуска приложения. Известное ограничение: наблюдатель подписан только на дерево `content://sms` (текстовые SMS), не на `content://mms` — на подхват MMS-контента эта доработка не распространяется.

## Milestone 14 — Android Gateway App: фильтрация входящих SMS

Выявлено при анализе issues референсного проекта bogkonstantin/android_income_sms_gateway_webhook (#52, #96, #88, #70) — у нас не было никакой фильтрации, `SmsDeliverReceiver` форвардил 100% входящих SMS. Спека: [0015-gateway-sms-filtering](specs/0015-gateway-sms-filtering.md) (Implemented).

- [x] Система 1 — фильтр приёма (блокирует запись в Room/UI целиком, сообщение как будто не приходило)
- [x] Система 2 — фильтр форвардинга (сообщение остаётся в приложении со статусом `NOT_FORWARDED`, но не уходит на backend)
- [x] Общая модель `FilterRule` (sender/`subscriptionId`/content, AND всех непустых критериев) с независимым режимом blacklist/whitelist на каждую систему; sender — точное совпадение или regex, content — вхождение подстроки или regex
- [x] Экраны управления правилами (список, добавление/редактирование/удаление с подтверждением, toggle enabled, переупорядочивание кнопками вверх/вниз)
- [x] SIM-критерий хранит `subscriptionId` (не физический слот), правило с недоступной SIM не удаляется автоматически — помечается «SIM недоступна»

Две коррекции по ходу реализации, обе явно согласованы с владельцем продукта (не внесены самовольно, см. правило в `CLAUDE.md`):
- **Семантика content-паттерна.** Живая проверка на устройстве (2026-08-29) показала, что точное совпадение для текста сообщения (как изначально требовала спека, симметрично отправителю) никогда не срабатывает на реальных SMS — ключевое слово почти никогда не равно всему телу сообщения целиком. **Доработка (2026-08-29, по прямому репорту владельца продукта — подлагивания при скролле и списка диалогов, и переписки в треде):** найдена и исправлена реальная причина, не связанная с самим Milestone 18 — в `ConversationsScreen.kt`/`ThreadScreen.kt` колбэки строк/пузырьков (`onOpenThread`/`onArchiveToggle`/`onDeleteRequested`, `onRetry`/`onDelete`) оборачивались в новую лямбду **на каждый элемент при каждой рекомпозиции** прямо внутри `items{}`-блока `LazyColumn` — Compose сравнивает такие параметры по идентичности, поэтому свежесозданная лямбда каждый раз заставляла `ConversationRow`/`MessageBubble` рекомпозироваться полностью, даже когда собственные данные строки/пузырька не менялись (это происходило при любом изменении состояния экрана — новое SMS, тик `failedCount`, ввод текста в поле треда посимвольно и т.д.), и на не самом мощном устройстве (TECNO LI9) это давало заметные подлагивания при скролле в обоих местах. Исправлено: колбэки теперь передаются без обёртки через `items{}` (стабильная ссылка на один и тот же объект), а специфичное для элемента замыкание (по `sender`/`id`) создаётся только внутри самого `ConversationRow`/`MessageBubble` (в `ThreadContent` — через `remember(actions) { ... }`, по одному разу на весь экран, а не на каждое сообщение) — теперь Compose корректно пропускает рекомпозицию непострадавших строк/пузырьков при скролле. Заодно устранена мелкая, но реальная нагрузка на GC: `formatConversationTime`/`formatTime` создавали новый `SimpleDateFormat` на каждый вызов (на каждую строку/пузырёк, на каждую рекомпозицию) — заменено на один общий `SimpleDateFormat` на файл (безопасно — вызовы происходят только на UI-потоке Compose). `peer-review-template` не нашёл дефектов в исправлении (проверены все точки вызова изменённых composable-функций, стабильность `actions`/`hiltViewModel()`, отсутствие конкурентного использования `SimpleDateFormat` из фоновых потоков) — новых тестов не добавлено: поведенческие тесты (`ConversationsScreenTest`/`ThreadScreenTest`) уже проверяют, что колбэки вызываются с правильным `sender`/`id`, а тест на количество рекомпозиций потребовал бы новой инфраструктуры непропорционально размеру фикса; полный набор инструментированных тестов — 97/97 зелёных на TECNO LI9.
