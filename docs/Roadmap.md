# Roadmap

Дорожная карта разработки по этапам, от базовой инфраструктуры до MVP и дальнейших улучшений. Порядок последовательный — этапы без явных зависимостей от следующих можно частично распараллелить, но рекомендуется двигаться сверху вниз.

## Milestone 0 — Подготовка

- [x] Инициализация Go-модуля, структура проекта (`cmd/`, `internal/handlers`, `internal/services`, `internal/storage`)
- [x] Инициализация Android Viewer App проекта (Kotlin, минимальный шаблон)
- [x] Настройка SQLite и системы миграций (собственный минимальный мигратор на `embed.FS`, без cgo-зависимостей)

## Milestone 1 — Авторизация пользователей

- [x] Логаут и отзыв refresh-токена
- [x] Таблицы `users`, `refresh_tokens`

**Этап 4 (готово 2026-08-28):**
- [x] Выбор SIM-слота при отправке: `SimOptionsProvider` (`SubscriptionManager`), селектор в UI виден только при 2+ активных SIM, `MessageRepository.sendMessage`/`OutgoingSmsSender` принимают `subscriptionId`/`simSlot`. - [x] `RESPOND_VIA_MESSAGE` — **проверено и подтверждено расхождение с OEM, не баг приложения**: вызвать сервис через `adb` напрямую нельзя (нужно signature-разрешение `SEND_RESPOND_VIA_MESSAGE`, есть только у системного дайлера). Вывод: этот OEM не использует штатный контракт дефолтного SMS-приложения для быстрого ответа (аналогично уже задокументированным на этом OEM расхождениям — Hiber-заморозка, рассинхронизация `RoleManager`). На стоковом Android/дайлере Google Phone сервис будет вызван как положено.
- [x] `WapPushReceiver` — вместо полного no-op сохраняет видимую заглушку («[MMS] содержимое не поддерживается») в Room по той же схеме `goAsync`+`try/catch/finally`, что и `SmsDeliverReceiver`, не пересылается на webhook.
- [x] Live-подхват записей, которые сторонние компоненты пишут напрямую в `content://sms` в обход `SMS_DELIVER`/`RESPOND_VIA_MESSAGE` (реальный случай — quick-reply OEM-дайлера, см. пункт выше): `ContentObserver` в `GatewayApp` + инкрементальная синхронизация по watermark `_ID` (`SmsHistoryImporter.syncNewMessages()`), плюс fallback-проверка при каждом `ON_RESUME` экрана (на случай, если процесс был не запущен в момент записи). `peer-review-template` нашёл и исправил реальную гонку — `ContentObserver` и `ON_RESUME`-fallback могли одновременно прочитать один и тот же watermark и задвоить вставку — закрыто общим `Mutex` на обоих методах. Живая проверка дважды на устройстве: до фикса запись OEM-дайлера появлялась только после переустановки; после — появилась в списке диалогов без переустановки/перезапуска приложения. Известное ограничение: наблюдатель подписан только на дерево `content://sms` (текстовые SMS), не на `content://mms` — на подхват MMS-контента эта доработка не распространяется.

## Milestone 14 — Android Gateway App: фильтрация входящих SMS

Выявлено при анализе issues референсного проекта bogkonstantin/android_income_sms_gateway_webhook (#52, #96, #88, #70) — у нас не было никакой фильтрации, `SmsDeliverReceiver` форвардил 100% входящих SMS. Спека: [0015-gateway-sms-filtering](specs/0015-gateway-sms-filtering.md) (Implemented).

- [x] Система 1 — фильтр приёма (блокирует запись в Room/UI целиком, сообщение как будто не приходило)
- [x] Система 2 — фильтр форвардинга (сообщение остаётся в приложении со статусом `NOT_FORWARDED`, но не уходит на backend)
- [x] Общая модель `FilterRule` (sender/`subscriptionId`/content, AND всех непустых критериев) с независимым режимом blacklist/whitelist на каждую систему; sender — точное совпадение или regex, content — вхождение подстроки или regex
- [x] Экраны управления правилами (список, добавление/редактирование/удаление с подтверждением, toggle enabled, переупорядочивание кнопками вверх/вниз)
- [x] SIM-критерий хранит `subscriptionId` (не физический слот), правило с недоступной SIM не удаляется автоматически — помечается «SIM недоступна»

Две коррекции по ходу реализации, обе явно согласованы с владельцем продукта (не внесены самовольно, см. правило в `CLAUDE.md`):
- **Семантика content-паттерна.** Живая проверка на устройстве (2026-08-29) показала, что точное совпадение для текста сообщения (как изначально требовала спека, симметрично отправителю) никогда не срабатывает на реальных SMS — ключевое слово почти никогда не равно всему телу сообщения целиком. С владельцем продукта согласована асимметрия: sender — точное совпадение, content — вхождение подстроки (regex доступен для обоих). Отражено в спеке (допущение 5) и покрыто регресс-тестами.
- **Переупорядочивание правил.** Peer review нашёл, что критерий приёмки «порядок можно менять в UI» не был реализован (все правила сохранялись с `sortOrder=0`). Вынесено на решение владельца продукта — выбрано реализовать сейчас, не откладывать в backlog. Сделано через кнопки вверх/вниз (drag-библиотеки в проекте нет), с тестами.

Тестовое покрытие: юнит-тесты чистой логики матчинга, инструментированные тесты DAO/репозитория/UI (67/67 зелёных на физическом TECNO LI9), дважды живая проверка на устройстве (reception- и forwarding-блокировка реальными SMS, включая повторную проверку после фикса content-семантики). Честный пробел: ветка `SmsDeliverReceiver`, вызывающая reception-проверку, покрыта только живой проверкой и юнит-тестами самой логики матчинга — отдельного инструментированного теста на `BroadcastReceiver.onReceive` нет; аналогично не автотестированы FAB «добавить правило» и клик по строке «редактировать» как навигационные колбэки (сами экраны/действия покрыты по отдельности).

## Milestone 15 — Android Gateway App: настраиваемый retry и bulk resend

Выявлено при анализе issues референсного проекта bogkonstantin/android_income_sms_gateway_webhook (#69, #38, #3) — количество попыток форвардинга и интервал backoff были захардкожены (`MAX_RETRIES=10`, `EXPONENTIAL`/30 сек), не было массового повтора всех `FAILED`-сообщений. Спека: [0016-gateway-retry-config-and-bulk-resend](specs/0016-gateway-retry-config-and-bulk-resend.md) (Implemented).

- [x] Настраиваемые `maxAttempts` (1–50), `baseIntervalSeconds` (10–3600), `backoffPolicy` (`EXPONENTIAL`/`LINEAR`) вместо констант в `WebhookRequestWorker`/`MessageRepository.enqueueDelivery`
- [x] Новый экран «Доставка» — принимает `webhookUrl`/`uploadToken` (переехали из `SettingsScreen`) + новые retry-настройки с валидацией диапазонов; `SettingsScreen` теперь только точка входа на «Доставка» и «Фильтрация SMS» (своей `ViewModel`/`UiState` больше не имеет)
- [x] Bulk resend — кнопка «Повторить неудавшиеся» в `TopAppBar` списка диалогов (видна при `FAILED`-сообщениях > 0), с подтверждением через `ConfirmDialog` (получил необязательный параметр `confirmLabel`, существующие места вызова не затронуты); затрагивает только `FAILED`, не `NOT_FORWARDED` (осознанно оставлено фильтру, см. [0015](specs/0015-gateway-sms-filtering.md))

Найдено `peer-review-template` и исправлено: `MessageRepository.retryAllFailed()` изначально не сбрасывал статус сообщения на `PENDING` перед повторной постановкой в очередь (в отличие от уже существующего `retryMessage()`) — из-за этого `observeFailedCount()` продолжал бы считать сообщение как `FAILED`, пока идёт повторная попытка, кнопка bulk resend оставалась бы видимой и повторное нажатие могло поставить дублирующую задачу `WorkManager` для того же сообщения. Исправлено добавлением того же сброса статуса, что и в `retryMessage()`, с регресс-тестом.

Найдено при `analysis-qa-checklist` (не самовольное отклонение от спеки, см. правило в `CLAUDE.md`): дословная формулировка теста в спеке 0016 ("переданные в `WorkRequest` `BackoffCriteria` соответствуют значениям `GatewayConfigStore`, проверяется через `WorkManager.getWorkInfosByTag`") технически невыполнима — `WorkInfo` не раскрывает `BackoffCriteria` для инспекции в тестах. Смысл критерия сохранён эквивалентной проверкой (`verify(configStore).retryBackoffPolicy()`/`retryBaseIntervalSeconds()`), дополненной живой проверкой на устройстве и границей `maxAttempts` в `WebhookRequestWorkerTest`; изменение отражено в тексте спеки.

Тестовое покрытие: юнит-тесты `GatewayConfigStore`, инструментированные тесты `MessageRepository`/`WebhookRequestWorker`/`DeliveryScreen`/`SettingsScreen`/`ConversationsScreen`/`ConversationsViewModel` (80/80 зелёных на физическом TECNO LI9). Живая проверка на устройстве: `maxAttempts=2` с недоступным сервером — реальное SMS дошло до `FAILED` ровно после 2 попыток (подтверждено логами `WorkManager`), не после захардкоженных 10; bulk resend по кнопке в `TopAppBar` реально поставил новую задачу форвардинга для того же сообщения (подтверждено логами).
