## Milestone 12 — Android Gateway App (собственное SMS-приложение по умолчанию)

Спецификация [0013-android-gateway-app](../specs/0013-android-gateway-app.md), статус закрыт в рамках Milestone 18 ниже.

- [x] **Этап 1:** новый проект `android_gateway/`, все 4 обязательных компонента дефолтного SMS-приложения, приём SMS через `SMS_DELIVER_ACTION` с определением SIM-слота, пересылка на backend через Hilt+WorkManager с ретраем; подтверждено на физическом устройстве (TECNO LI9); попутно найден и исправлен реальный баг рассинхронизации `RoleManager`/legacy `Settings.Secure.sms_default_application` на этом OEM
- [x] **Этап 2:** список диалогов, экран переписки, отправка SMS из UI, импорт истории из `content://sms` при первом запуске, кнопка «Повторить» для `FAILED`; `peer-review-template` нашёл и исправил 3 бага (некоррелированный SQL списка диалогов, отсутствие `onNewIntent`, отсутствие обработки ошибок отправки)
- [x] **Этап 4:** выбор SIM-слота при отправке (`SimOptionsProvider`), `RESPOND_VIA_MESSAGE` (проверено — на этом OEM дайлер обходит штатный контракт, используя системный провайдер напрямую, не баг приложения), `WapPushReceiver`-заглушка, `ContentObserver`+watermark-синхронизация для live-подхвата записей, минующих `SMS_DELIVER`; `peer-review-template` нашёл и исправил гонку двойной вставки между `ContentObserver` и `ON_RESUME`-fallback (закрыто общим `Mutex`)
- [x] **Этап 5 (поиск/архивация/удаление):** полнотекстовый поиск по всей переписке, архивация через `conversation_meta`, удаление диалога/сообщения с подтверждением — всё чисто локально в Room; найдена и исправлена гонка отмены корутины при удалении (`withContext(NonCancellable)`, атомарный `@Transaction`)
- [x] **UI/UX-доработки** (по M3-чеклисту `android-skills:android-ux`): карточки диалогов, чат-пузыри, экран настроек, экран «сделать приложением по умолчанию»; найден и исправлен зависающий флаг `isImporting` (не сбрасывался в `finally`)

Известное ограничение, снятое позже в Milestone 18: `ConversationsViewModel` резолвил имя контакта на каждый диалог при каждом входящем SMS без кеша.

Оставшиеся с этапа 4 живые проверки (реальный MMS/WAP push, доставка исходящего SMS реальному получателю, dual-SIM устройство, HMAC-подпись) не блокировали закрытие спеки и перенесены в открытый пункт Roadmap 2 (Backlog).

## Milestone 14 — Android Gateway App: фильтрация входящих SMS

Выявлено при анализе issues референсного проекта bogkonstantin/android_income_sms_gateway_webhook (#52, #96, #88, #70). Спека: [0015-gateway-sms-filtering](../specs/0015-gateway-sms-filtering.md) (Implemented).

- [x] Фильтр приёма (блокирует запись целиком) и фильтр форвардинга (`NOT_FORWARDED`, но не уходит на backend) — независимы
- [x] Общая модель `FilterRule` (sender/`subscriptionId`/content, AND всех критериев), независимый blacklist/whitelist на каждую систему; sender — точное совпадение или regex, content — подстрока или regex
- [x] Экраны управления правилами (CRUD, toggle, переупорядочивание кнопками вверх/вниз)
- [x] SIM-критерий по `subscriptionId`, недоступная SIM помечается, а не удаляется

Две коррекции, обе явно согласованы с владельцем продукта: асимметрия sender/content (точное совпадение vs. подстрока — живая проверка показала, что точное совпадение для content никогда не срабатывает на реальных SMS); переупорядочивание правил в UI реализовано сразу, не отложено в backlog, после того как peer review нашёл, что оно не было сделано.

Тестовое покрытие: юнит-тесты матчинга + инструментированные тесты DAO/репозитория/UI (67/67 на TECNO LI9), дважды живая проверка на устройстве.

## Milestone 15 — Android Gateway App: настраиваемый retry и bulk resend

Выявлено при анализе issues референсного проекта (#69, #38, #3). Спека: [0016-gateway-retry-config-and-bulk-resend](../specs/0016-gateway-retry-config-and-bulk-resend.md) (Implemented).

- [x] Настраиваемые `maxAttempts` (1–50), `baseIntervalSeconds` (10–3600), `backoffPolicy` вместо констант
- [x] Новый экран «Доставка» (`webhookUrl`/`uploadToken` переехали из Settings + retry-настройки с валидацией)
- [x] Bulk resend — кнопка «Повторить неудавшиеся», только для `FAILED`, не `NOT_FORWARDED`

`peer-review-template` нашёл и исправил: `retryAllFailed()` не сбрасывал статус на `PENDING` перед повторной постановкой (в отличие от `retryMessage()`) — дублирующие задачи `WorkManager`. `analysis-qa-checklist` нашёл невыполнимую дословно формулировку теста в спеке (инспекция `BackoffCriteria` через `WorkInfo` невозможна) — заменена эквивалентной проверкой, спека скорректирована.

Тестовое покрытие: 80/80 на TECNO LI9. Живая проверка: `maxAttempts=2` → `FAILED` ровно после 2 попыток; bulk resend реально поставил новую задачу.

## Milestone 16 — Android Gateway App: пауза форвардинга, проверка соединения, уведомления о результате, лог доставки

Выявлено при анализе issues референсного проекта (#59, #58/#56, #91, #68). Спека: [0017-gateway-delivery-reliability-and-visibility](../specs/0017-gateway-delivery-reliability-and-visibility.md) (Implemented).

- [x] Глобальная пауза форвардинга (входящие сохраняются локально как `PENDING`, не ставятся в очередь; снятие паузы повторно ставит накопившееся)
- [x] Кнопка «Проверить соединение» — реальный `POST` тестового payload на `webhookUrl`
- [x] Уведомление о результате форвардинга (отдельный notification channel `delivery_result`)
- [x] Экран «Лог доставки» (`delivery_log`, запись после каждой попытки)

`peer-review-template` нашёл и исправил 2 дефекта: (1) `retryMessage()`/`retryAllFailed()` при активной паузе сбрасывали статус в `PENDING`, хотя `enqueueDelivery()` молча ничего не ставил в очередь — сообщение выглядело «в процессе», реально зависало; исправлено полным no-op'ом при паузе. (2) `WebhookConnectionTester.test()` строил `Request` вне `try`/`catch` — `IllegalArgumentException` на URL без схемы ронял приложение; исправлено. Заодно закрыт пробел покрытия: тест не проверял, что «Проверить соединение» использует текущие несохранённые поля формы, а не устаревшие из `GatewayConfigStore`.

Тестовое покрытие: 100/100 на TECNO LI9. Живая проверка через локальный backend (Docker, `adb reverse`): реальный успех (HTTP 201) и реальная ошибка соединения; пауза реально держала сообщение без задач `WorkManager`; лог доставки показал реальный `HTTP 500` с последующим успешным повтором.

## Milestone 18 — Android Gateway App: мгновенная навигация в треде, ускорение холодного старта списка диалогов

Собрано напрямую от владельца продукта (2026-08-29). Спека: [0020-gateway-thread-and-startup-performance](../specs/0020-gateway-thread-and-startup-performance.md) (Implemented).

- [x] Открытие треда с большой историей сразу показывает последнее сообщение без анимированной прокрутки (`scrollToItem` вместо `animateScrollToItem` на первом открытии); новое сообщение в уже открытом треде по-прежнему докручивается анимированно
- [x] Переход по клику на результат поиска открывает тред сразу на найденном сообщении — новый query-параметр `messageId` в маршруте `thread/{sender}?messageId={messageId}`
- [x] Кеш резолвинга имени контакта в `ConversationsViewModel` — закрывает known limitation Milestone 12
- [x] Новый Room-индекс `messages(sender, createdAt)` (`MIGRATION_5_6`, v5→v6), подтверждён `query-validation` и фактическим `EXPLAIN QUERY PLAN`: `SEARCH messages` (полный скан) → `SEARCH messages USING COVERING INDEX`

`peer-review-template` нашёл и исправил 2 дефекта: (1) гонка записи в `contactNameCache` между отменённым и новым коллектором при переключении архива — исправлено `synchronized`. (2) тесты `ThreadScreenTest` не отличали `scrollToItem` от `animateScrollToItem` (Compose-тесты сами доводят анимацию до конца) — исправлено заморозкой `composeRule.mainClock`, регрессия подтверждена сабботажным тестом.

Тестовое покрытие: 97/97 на TECNO LI9. Отдельно обойдён флейк устройства (OEM-заморозка «Hiber», не связана с кодом — whitelist через `adb shell dumpsys deviceidle`). Живая проверка: поиск по подстроке более раннего сообщения → тред открылся именно на нём. Оговорка: реальные диалоги на устройстве малы, сценарий «тысячи сообщений» подтверждён только инструментированным тестом (200 синтетических сообщений).

**Доработка (2026-08-29, репорт владельца продукта о подлагиваниях скролла):** найдена и исправлена реальная причина — колбэки строк/пузырьков (`onOpenThread`/`onArchiveToggle`/`onDeleteRequested`, `onRetry`/`onDelete`) оборачивались в новую лямбду на каждый элемент при каждой рекомпозиции внутри `items{}` `LazyColumn`, что заставляло `ConversationRow`/`MessageBubble` рекомпозироваться полностью даже без изменения собственных данных. Исправлено передачей стабильных ссылок через `items{}` и созданием специфичного для элемента замыкания внутри самого `ConversationRow`/`MessageBubble` (в `ThreadContent` — через `remember(actions)`, один раз на экран). Заодно заменены `SimpleDateFormat`-аллокации на каждый вызов на один общий инстанс на файл. `peer-review-template` дефектов не нашёл; новых тестов не добавлено (поведенческие тесты уже покрывают правильность `sender`/`id`, тест на число рекомпозиций непропорционален размеру фикса). 97/97 зелёных.

**Оговорка:** живая проверка владельцем продукта показала, что подлагивания сохраняются даже после этого фикса — причина неполная/не единственная. Замерено `adb shell dumpsys gfxinfo` на списке диалогов: **55.56% janky-кадров** (15/27), 90p 150ms/95p 250ms при бюджете ~16.6ms; GPU-время в норме (6-9ms) — узкое место на UI-потоке. Дальнейшая диагностика вынесена в открытый Milestone «измеримая диагностика производительности» — см. [Roadmap 2.md](Roadmap%202.md).
