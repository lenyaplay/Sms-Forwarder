## Milestone 17 — Android Gateway App: переход из уведомления в тред, разворачиваемый текст уведомления

Собрано напрямую от владельца продукта (2026-08-29). Спека: [0019-gateway-notification-deep-link-and-expanded-text](../specs/0019-gateway-notification-deep-link-and-expanded-text.md) (Implemented). Требования — [docs/requirements/0019-0021-requirements-doc.md](../requirements/0019-0021-requirements-doc.md)/[0019-0021-analysis-brief.md](../requirements/0019-0021-analysis-brief.md).

- [x] Тап по уведомлению о новом SMS открывает сразу экран переписки с этим отправителем — `IncomingSmsNotifier` теперь кладёт `EXTRA_OPEN_SENDER` в `PendingIntent`, переиспользуя существующую инфраструктуру `MainActivity`/`GatewayNavGraph`; `requestCode = sender.hashCode()` + `FLAG_UPDATE_CURRENT` не дают разным отправителям схлопнуться в один закешированный `PendingIntent`
- [x] Разворачиваемый текст уведомления (`NotificationCompat.BigTextStyle`) поверх уже существующего `setContentText` — свёрнутый вид не меняется, развёрнутый показывает полный текст

Найдено `peer-review-template` и исправлено: `GatewayNavGraph`'s `LaunchedEffect(openSender)` был ключён на голую строку `sender` — повторный тап на уведомление от того же отправителя после ухода с его треда был бы молчаливым no-op. Исправлено: `openSender` стал `OpenSenderRequest(sender, requestId)` с монотонным `requestId`, `LaunchedEffect` теперь ключён на весь объект. Отдельная находка peer review (`sender.hashCode()` как `requestCode` теоретически может коллизировать для двух разных отправителей) принята как приемлемо низкий риск на масштабе личного использования, не устраняется.

Найдено живой проверкой (не peer review) и исправлено — реальный баг, ломавший ровно тот сценарий, ради которого затевалась фича: `Intent` не нёс `FLAG_ACTIVITY_CLEAR_TOP`, поэтому тап по уведомлению, когда `MainActivity` уже была видна на экране (на другом треде), просто разворачивал существующий task (`START_TASK_TO_FRONT`) без вызова `onNewIntent` — extra тихо терялся, тред не переключался. Исправлено добавлением `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP`, тем же паттерном, что уже использует `SendToActivity.kt` для `sms:`-диплинков. Спека ошибочно полагала этот путь уже проверенным в Milestone 12 — на деле тот прецедент покрывал только холодный старт.

Тестовое покрытие: автотестов не добавлено — вся новая логика тривиальная композиция Android framework API (requestCode, флаги intent, builder-вызовы), не бизнес-логика; в проекте нет прецедента ни unit-тестов, требующих `Context`, ни инструментированных тестов, запускающих реальный `Activity`/`NavGraph` (все существующие Compose-тесты работают с изолированными `*Content`-композаблами на фейковых данных). Вместо этого — живая проверка. **Проведена не на физическом устройстве, а на Android-эмуляторе** (`Pixel_2` AVD) через `adb emu sms send` с несколькими фейковыми номерами — у владельца продукта был доступен только один реальный номер. Все 4 критерия приёмки спеки 0019 подтверждены: холодный старт → нужный тред; приложение уже открыто на другом треде → корректное переключение (после фикса выше); повторный тап на того же отправителя → корректное переоткрытие (после фикса `OpenSenderRequest`); развёрнутое уведомление → полный текст виден. Физическое устройство отдельно не перепроверялось.

## Milestone 19 — Android Gateway App: кнопка сброса настроек доставки

Собрано напрямую от владельца продукта (2026-08-29). Спека: [0021-gateway-reset-delivery-settings](../specs/0021-gateway-reset-delivery-settings.md) (Implemented).

- [x] Кнопка «Сбросить настройки доставки» на экране «Доставка» — очищает `serverUrl`/`uploadToken`, retry-настройки (до дефолтов) и паузу форвардинга (→ `false`), с обязательным подтверждением через `ConfirmDialog`
- [x] Не трогает правила фильтрации ([0015](../specs/0015-gateway-sms-filtering.md)) и служебные флаги импорта истории — `GatewayConfigStore.resetDeliverySettings()` точечно `.remove()`-ит только 6 delivery-ключей в общем файле `SharedPreferences`, не `.clear()`
- [x] **Первый в проекте Activity-level инструментированный тест** (`DeliveryResetActivityTest.kt`, по прямому запросу владельца продукта) — реальный `MainActivity`, реальный Hilt DI, реальная навигация «Настройки → Доставка → Сброс», закрывает пробел, явно принятый в Milestone 17 (там все Compose-тесты были только на изолированных `*Content`)

Незапланированный, но необходимый фикс, найденный именно этим Activity-тестом на реальном устройстве: экран «Доставка» никогда не был скроллящимся — новая кнопка внизу формы оказалась физически недостижима (реальная инъекция тача не находила кнопку подтверждения диалога). Исправлено `.verticalScroll(rememberScrollState())` — предсуществующий пробел экрана, который обнажила именно новая кнопка.

Урок по инфраструктуре тестов (для будущих Activity-тестов в проекте): `createAndroidComposeRule<Activity>()` запускает `Activity` при применении своего `@Rule`, что происходит раньше `@Before` — сидирование состояния (роль/разрешения/настройки) нужно выносить в отдельный `TestRule` (`ExternalResource`), упорядоченный `@get:Rule(order=N)` **перед** `composeRule`. `ActivityScenario.recreate()` как обходной путь пробовался первым и не сработал надёжно — не использовать.

Найдено `peer-review-template` и исправлено: (1) `HiltAndroidRule.inject()` не вызывался нигде в новом тесте — добавлено; (2) текст диалога подтверждения не упоминал сброс паузы форвардинга — дополнен.

Тестовое покрытие: 101/101 инструментированных зелёных на TECNO LI9 (было 97 после Milestone 17), плюс unit-тесты `GatewayConfigStoreTest`/`DeliveryScreenTest` зелёные. Живая проверка человеком с реально настроенным сервером отдельно не проводилась — вместо неё Activity-тест проходит через реальный `Activity`/навигацию/`SharedPreferences`, а факт, что форвардинг не работает без настроенного сервера, уже живо подтверждён в Milestone 16 (`isConfigured()`-гейт) — не блокирует `Implemented`, по аналогии с Milestone 18.

Выявлено при анализе issues референсного проекта bogkonstantin/android_income_sms_gateway_webhook (#102/#57, #61/#43, #76). Спека: [0018-gateway-delete-contact-privacy-export](../specs/0018-gateway-delete-contact-privacy-export.md) (Implemented).

- [x] Новое поле `MessageEntity.systemSmsId` для сопоставления с `content://sms`-строкой, бэкфилл через `SmsHistoryImporter` (нечёткое сопоставление ±2000мс по `sentStamp`/`receivedStamp` — точное совпадение не работает, carrier vs. local время; исходящие бэкфиллятся бесплатно через уже существующий `ContentObserver` на всё дерево `content://sms`, без новой проводки)
- [x] Новое поле `contactName` в `WebhookPayload` (аддитивное расширение [0003-sms-webhook.md](../specs/0003-sms-webhook.md)), скрыто по умолчанию (`hideContactNameInPayload = true`) — подтверждено инструментированным тестом на реальном теле HTTP-запроса (MockWebServer), поле физически отсутствует в JSON при дефолте, не `null`

**Техническая поправка, не изменение требования:** спека предполагала `GatewayDatabase.version = 6`/`MIGRATION_5_6` для `systemSmsId` — этот слот уже занят индексом из Milestone 18 (спека 0018 написана раньше). Реализовано как `version = 7`/`MIGRATION_6_7`.

**Уточнено с владельцем продукта в этой сессии** (не было явно зафиксировано в спеке): импорт настроек полностью заменяет правила фильтрации на целевом устройстве, не сливает с уже существующими — иначе повторный импорт одного файла давал бы дубли.

Найдено `peer-review-template` и исправлено (два реальных дефекта): (1) замена правил фильтрации при импорте (`deleteAll()` + цикл `upsert()`) не была обёрнута в `@Transaction`, вопреки заявленной в коде атомарности — крах процесса посреди цикла мог оставить правила частично восстановленными; исправлено новым `FilterRuleDao.replaceAll()` (`@Transaction`). (2) сортировка кандидатов бэкфилла `systemSmsId` учитывала близость только `receivedStamp`, хотя запрос может сматчить строку и по `sentStamp` — «ближайший» кандидат мог оказаться не самым близким; исправлено сортировкой по минимуму обоих расстояний.

Тестовое покрытие: 127/127 инструментированных зелёных на TECNO LI9 (было 101 после Milestone 19), включая реальный `ContentResolver`/`SecurityException`-путь в `MessageRepositoryTest` (без моков) и реальное тело HTTP-запроса в `WebhookRequestWorkerTest`. Живая проверка вручную покрыла ручное удаление сообщения целиком (см. выше); «удалить после пересылки» и экспорт/импорт через реальный SAF-файл на переустановленном приложении отдельно не прогонялись — оба переиспользуют уже отдельно живо проверенный/полно протестированный код (тот же `deleteMessage`, тот же раунд-трип сериализации), риск расхождения оценён как низкий — не блокирует `Implemented`, по аналогии с прошлыми milestone'ами.

## Milestone 21 — Android Gateway App: измеримая диагностика производительности, инструментарий по требованию, быстрый холодный старт

Собрано напрямую от владельца продукта (2026-08-29) — после фикса нестабильных лямбд (Milestone 18) подлагивания скролла на живом устройстве сохранились, нужны цифры вместо гипотез, плюс постоянный инструментарий, а не разовый замер. Спека — [docs/specs/0022-gateway-performance-diagnostics.md](../specs/0022-gateway-performance-diagnostics.md) (Implemented частично, см. ниже), собрана через `stakeholder-requirements-gathering`.

- [x] Система измерения производительности «по требованию»: `androidx.metrics:metrics-performance` (`JankStats`, версия `1.0.0-beta01` — новее требует `compileSdk 35`) + таймеры фоновых операций (`PerfMonitor.measure`), под одним общим переключателем «Диагностика» на экране «Настройки» (работает на любой сборке, не debug-only). Пишет в logcat и в файл на устройстве (`filesDir/perf/perf-log.txt`). Живо проверено на TECNO LI9: включение/выключение реально влияет на запись в оба места.
- [ ] **Не решено полностью.** Диагностика конкретной причины лагов скролла с цифрами. Живое сравнение с системным SMS-приложением на том же устройстве и жесте: `com.transsion.smartmessage` — 0.87% janky-кадров (230 кадров всего); Gateway App baseline — 65.52%. Протестированы 3 кандидата: `distinctUntilChanged()` (66.67%, оставлен как независимо корректный, но не устранивший лаг), отключение тени `Card` (71.88%, эффекта не дало, отменено), удаление `SwipeToDismissBox` (неоднозначно — 1 из 4 прогонов дал 11.39%, три контрольных вернулись к 79-91%, не воспроизвелось, отменено). **Важная методологическая находка**: `Total frames rendered` за идентичный жест на идентичном билде колебался 29-202 между запусками — однократный замер `dumpsys gfxinfo` через `adb shell input swipe` на этом устройстве/датасете недостаточно надёжен, что ослабляет доверие ко всем выводам этого пункта. Открытый вопрос для будущей сессии: переделать методологию (усреднение по нескольким прогонам, детерминированный скролл) и/или собрать замер на более крупном датасете.
- [x] Экран списка диалогов больше не показывает пустое состояние («Нет сообщений») до первой реальной эмиссии `Flow` — новое поле `ConversationsUiState.hasLoadedOnce`. Живо проверено на TECNO LI9 с реальной SMS-историей.
- [x] Частный случай push-уведомления — покрывается тем же фиксом без отдельного кода (Room-запись уже гарантированно предшествует показу уведомления).

Peer-review нашёл и исправил 2 реальных дефекта в `PerfMonitor.kt` (не потокобезопасный `SimpleDateFormat`, неатомарная конкурентная запись в файл — обёрнуто в `Mutex`). Инструментированный набор: 136/136 зелёных на TECNO LI9 (было 127 после Milestone 20).

Примечание: пункт про уведомление, не открывающее нужный тред, реализуется как Milestone 17 — не дублируется здесь отдельным пунктом.

## Milestone 22 — Android Gateway App: изолированная диагностика лага скролла (эмерджентность компонентов + надёжная методология замера)

Статус: **Implemented (частично)**, спека [0023-gateway-scroll-jank-isolation.md](../specs/0023-gateway-scroll-jank-isolation.md). Продолжение Milestone 21: причина лага скролла списка диалогов осталась не подтверждена — ни один изолированный кандидат (`distinctUntilChanged()`, тень `Card`, `SwipeToDismissBox`) не дал воспроизводимого эффекта, а сам замер `dumpsys gfxinfo` через `adb shell input swipe` оказался ненадёжен (29-202 отрендеренных кадра на идентичном билде и жесте). Рабочая гипотеза владельца продукта (2026-09-02): лаг может быть эмерджентным свойством *комбинации* компонентов, не сводимым к любому из них по отдельности.

- [x] Построен новый диагностический инструмент (`ScrollJankLayerTest.kt`, androidTest): детерминированный `performTouchInput`-скролл через `ComposeTestRule` (не `adb shell input swipe`) + 5 прогонов на слой + формальный порог значимости (`JankComparison.kt`: разница средних vs разброс baseline, с защитой от аномально шумного baseline; каждый слой сравнивается и против абсолютного baseline, и против непосредственно предыдущего слоя — находка `query-validation`, единичное «vs baseline» не позволяло понять, какой именно слой вносит эффект).
- [x] Слои 0-3 (baseline `Text` → `Card` → усиленная тень → `SwipeToDismissBox`, все на синтетических данных) измерены на TECNO LI9: **все статистически неотличимы друг от друга** (2.79-2.83% janky кадров) — гипотеза эмерджентности **не подтверждена** на этом датасете и этой методологии. Абсолютные цифры кардинально ниже диапазона Milestone 21 (55.56-90.91% janky) — правдоподобная (не доказанная) находка: сама методология `adb shell input swipe`, а не код экрана, была основным источником прежних высоких цифр.
- [x] Найдена и исправлена `peer-review-template`-ревью реальная ошибка в самом эксперименте: Слой 4 (реальные данные устройства) на деле выполнился на synthetic-фолбэке — на устройстве не было активной роли SMS-приложения по умолчанию/истории на момент прогона, `observeConversations()` вернул пустой список, лог ошибочно писал «real data». Исправлено (лог явно различает `REAL`/`SYNTHETIC-FALLBACK`), честно задокументировано в спеке — **проверка на реальных данных устройства фактически не состоялась**.
- [ ] Перенесено в Milestone 23 (см. ниже — Сценарий D): прогнать тот же протокол напрямую на реальном `ConversationsScreen` (через `MainActivity`, с заранее подтверждённой ролью SMS-приложения по умолчанию и реальной историей) — если результат снова ~2-3% janky, находка о методологии подтверждается содержательно; плюс прямой A/B `performTouchInput` vs `adb shell input swipe` на одном экране в одном прогоне, чтобы доказать/опровергнуть находку про методологию, а не оставлять её правдоподобной, но недоказанной.
- Полный регресс: **141/141** зелёных на TECNO LI9 (было 136 после Milestone 21).

## Milestone 23 — Android Gateway App: диагностика лага именно первых (холодных) скроллов (гипотеза «прогрева»)

## Milestone 29 — Android Gateway App: точная реализация Ngo/Teo/Byrne (2003) balance/equilibrium/symmetry вместо пиксельной эвристики

Статус: **Draft, не начата**. Найдено 2026-09-05 при обсуждении Milestone 27/спеки 0033: текущий `symmetry.py` (`tools/ui-metrics/`) — задокументированное упрощение (mirror-flip SSIM + HSV-взвешенный визуальный момент по пикселям), не точное воспроизведение published APB. Прочитана сама статья — Ngo, D.C.L., Teo, L.S., Byrne, J.G. (2003), "Modelling interface aesthetics", *Information Sciences* 152, 25–46, DOI `10.1016/S0020-0255(02)00404-8` — формулы Balance (BM), Equilibrium (EM), Symmetry (SYM) там полностью заданы (формулы 1-17) и **не требуют пиксельной сегментации**: они оперируют списком дискретных экранных объектов (позиция, ширина, высота, площадь каждого), не растровым изображением.

Ключевая идея, ради которой заведён отдельный Milestone: Roborazzi-снапшоты (Milestone 27, Stage A) рендерятся из реального Compose-дерева — у нас уже есть точные bounding box'ы каждого элемента через `SemanticsNode` в момент теста, без необходимости восстанавливать их сегментацией по пикселям (что для UI-скриншотов менее надёжно, чем для естественных изображений). Это открывает путь к буквальной, а не приближённой реализации формул статьи.

- [ ] На этапе A (Kotlin, `*SnapshotTest.kt`) экспортировать geometry semantics-дерева (bounding box каждого интерактивного/визуального элемента) в JSON рядом с PNG-снапшотом.
- [ ] В `tools/ui-metrics/` реализовать точные формулы BM/EM/SYM (1)-(17) из статьи над этим JSON вместо текущей HSV-пиксельной эвристики в `symmetry.py`.
- [ ] Требует отдельной спеки (новая архитектура экспорта данных из Kotlin-теста + пересмотр решения спеки 0033 Допущение 10, которое зафиксировало текущее упрощение) — не тихая доработка существующего кода.
- [ ] Открытый вопрос, требующий решения владельца продукта перед стартом: веса измерений `ai` в формуле статьи (2003 год) заданы равными (`ai=1` для всех), сами авторы явно называют подбор весов открытой проблемой — нужно ли использовать равные веса как в оригинале или подбирать свои под chat UI.
- [ ] **Saliency heatmap-визуализации как часть репозитория** — во время бейк-оффа saliency (Milestone 27, Stage C) для сравнения моделей был сгенерирован скрипт, рисующий тепловую карту поверх каждого скриншота (композит оригинал+heatmap); скрипт и картинки были одноразовыми и удалены после выбора модели (Допущение 9 спеки 0033). Нужно вынести генерацию heatmap в постоянный инструмент — не только числовой `saliency`-score в CLI, но и сохранённые PNG с картой внимания для каждого экрана/темы, коммитятся в репозиторий и перегенерируются вместе с остальными Stage C метриками при обновлении baseline-скриншотов.
