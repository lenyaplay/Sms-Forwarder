## Milestone 21 — Android Gateway App: измеримая диагностика производительности, инструментарий по требованию, быстрый холодный старт

Собрано напрямую от владельца продукта (2026-08-29) — после фикса нестабильных лямбд (Milestone 18) подлагивания скролла на живом устройстве сохранились, нужны цифры вместо гипотез, плюс постоянный инструментарий, а не разовый замер. Спека ещё не написана — перед кодом обычный цикл (`docs/Development.md`: спека → скилы → тесты).

- [ ] Система измерения производительности экранов «по требованию» — не постоянный оверлей, а нечто, что можно включить/снять метрики при необходимости (кандидат: `androidx.metrics.performance`/`JankStats` с логированием в logcat/файл на debug-сборке); должна покрывать не только Compose-рендеринг, но и фоновые процессы (импорт истории, форвардинг) — точный набор метрик и способ включения зафиксировать в спеке
- [ ] Диагностика конкретной оставшейся причины лагов скролла с цифрами. Baseline уже снят вручную: `adb shell dumpsys gfxinfo` на списке диалогов — 55.56% janky-кадров (15/27), 90p 150ms/95p 250ms при бюджете ~16.6ms; GPU-время в норме (6-9ms) — узкое место на UI-потоке. Кандидаты для проверки: `SwipeToDismissBox` на каждой строке, стоимость `Card`-теней, пересборка `ConversationUi`/списка при каждой эмиссии `Flow`
- [ ] Экран списка диалогов долго показывает пустое состояние («Нет сообщений») при холодном старте, прежде чем реально подгрузится история — мгновенно показать последние известные данные (кэш/persisted state) вместо пустого экрана на время первой эмиссии `Flow`, либо ускорить сам путь до первой эмиссии
- [ ] Частный случай предыдущего пункта: если к моменту холодного старта уже показано push-уведомление о новом SMS — сообщение уже сохранено в Room, список/тред не должны показывать пустое состояние для данных, которые уже точно есть локально

Примечание: пункт про уведомление, не открывающее нужный тред, реализуется как Milestone 17 — не дублируется здесь отдельным пунктом.
