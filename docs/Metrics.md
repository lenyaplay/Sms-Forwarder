# Metrics.md

Метрики качества процесса разработки этого проекта. Не путать с `docs/specs/0022-gateway-performance-diagnostics.md` и последующими спеками — те про производительность приложения (runtime), этот файл — про качество самого процесса разработки (сколько багов утекает мимо тестов/ревью).

## Defect Escape Rate (DER)

Доля багов, обнаруженных **после** коммита (Production), от общего числа багов за период. Адаптация под этот проект: здесь нет отдельного QA/Stage-окружения и Jira — ближайший аналог заведён ниже.

**Environment Detected** (обязательное поле каждой записи):
- **Stage** — баг пойман до/во время коммита фичи: автотестом (unit/androidTest), код-ревью (`peer-review-template`), финальной сверкой (`analysis-qa-checklist`) или live-проверкой на TECNO в рамках той же итерации, что и сама фича.
- **Production** — баг обнаружен после того, как коммит с фичей уже смёржен и приложение реально используется (обычным использованием владельцем продукта, либо найден в новой сессии/итерации, не в той, где фича была написана).

**Формула (Вариант А, базовая — с этого и стартуем):**

```
DER = Баги на Production / (Баги на Stage + Баги на Production) × 100%
```

Пересчитывается по итогам примерно раз в месяц (или по факту накопления заметного числа записей — при личном темпе разработки жёсткий календарный период не обязателен), с учётом что баг, внесённый в январском коммите, может "выстрелить" только через несколько недель реального использования — не подводить итог раньше, чем прошло разумное время с последнего коммита за период.

**Что НЕ считается багом для DER** (по золотым правилам, адаптировано под проект):
- Дубликаты одного и того же root cause — считается 1 раз, а не по числу проявлений.
- Change request — пользователь (владелец продукта) просит изменить поведение/UX, которое и так работало как было спроектировано — это доработка, не дефект.
- Внешние сбои вне контроля кода приложения (например, сам Android/OEM-специфичный баг, недоступность стороннего backend'а в конкретный момент) — если приложение корректно обработало ситуацию (не крашнулось, показало осмысленную ошибку).

## Важность теста: не все тесты равны по значению

Проблема: подавляющее большинство тестов проекта всегда зелёные (это нормально — страховочная сетка, а не источник сигнала само по себе). Усреднённые метрики вида "% прошедших тестов" или "сколько тестов упало за спринт" не отличают тест, который 99% времени молчит, но раз в год ловит критический баг, от теста, который проверяет то, что физически не может сломаться. Ниже — как в этом проекте (без Jira, без настроенного mutation-testing тула для Kotlin/Compose, без формального CI cost-accounting) практически отслеживать это, без выдумывания цифр, которых у нас нет.

### 1. Defect Detection Value — лог "выстрелов" существующих тестов

Отдельный от DER-лога случай: не когда новый тест сам содержал баг (это DER), а когда **уже существующий, ранее закоммиченный тест** ловит регрессию в новой работе — то самое "молчал 11 месяцев, на 12-й спас". Каждая такая находка — прямое доказательство ценности конкретного теста, фиксируется здесь на будущее (при удалении/рефакторинге тестов эта история — аргумент "не трогать").

### 2. Cost of Failure — тег на явно критичных тестах

Без формального денежного расчёта (это отдельная инфраструктура, не оправдана для проекта такого масштаба), но с явной маркировкой в коде: тест, чей провал в проде означал бы необратимую потерю данных, полную неработоспособность форвардинга или утечку токена/приватных данных, помечается комментарием `// COST_OF_FAILURE: <последствие>` прямо над тестом. Это делает важность видимой при чтении кода, а не только "в среднем по больше выборке". Кандидаты на такую маркировку (не проставлено, требует отдельного прохода по существующим тестам — не входит в эту сессию):
- Доставка вебхука / retry-логика (`docs/specs/0017-gateway-delivery-reliability-and-visibility.md`) — провал = тихая потеря сообщений.
- Delete-after-forward / privacy-export (`0018`) — провал = утечка или неверное удаление приватных данных.
- Импорт истории / дедупликация (`SmsHistoryImporter`, `MessageDao.findUnmatchedForBackfill`) — провал = дублирование или потеря сообщений.

### 3. Mutation Score — инфраструктурный пробел, не сделано

Для Kotlin есть `pitest-kotlin` (JVM-таргет, требует настройки под Gradle-модуль `app`), но в проекте не подключён — не входит в эту сессию, кандидат в тот же список инфраструктурных инвестиций, что и Milestone 27 (Roborazzi/контраст/saliency, см. [Roadmap 2.md](roadmaps/Roadmap%202.md)). Пока Mutation Score не посчитан ни для одного теста — не утверждать "тест ловит баги", пока это не подтверждено мутационным прогоном хотя бы точечно на критичных модулях выше (доставка, приватность, дедупликация).

Важная оговорка, применимая ко всем "instrumented"-тестам проекта (androidTest, `ThreadScreenTest` и аналоги): низкий Mutation Score там — архитектурная норма, а не диагноз плохих тестов. UI-тест проверяет *что видно на экране*, а не каждую внутреннюю ветвь логики — множество мутаций кода не меняют то, что тест способен увидеть, и физически не могут быть "убиты" таким тестом.

**Решение (2026-09-04, окончательное на данный момент): автоматический mutation testing для androidTest в проект не подключается.** Три известных инструмента, целящихся именно в Android instrumented-тесты, проверены предметно (не по абстрактным описаниям, а по факту состояния репозиториев) и отклонены:

| Инструмент | Проверенный факт | Итог |
|---|---|---|
| **METFORD** (2025, github.com/specs-feup/paper-metford, "mutant schemata" + `adb shell setprop debug.MUID`) | Чистый research-репозиторий воспроизводимости статьи — нет ни Gradle-плагина, ни CLI для сторонних проектов, только замороженные версии приложений-подопытных автора и отчёты их же экспериментов. На 6 приложениях авторов средний Mutation Score всего 15.6%, задокументированная нестабильность (3-105 расходящихся мутантов/приложение между прогонами). | Неприменим — нет пути подключения к произвольному проекту без переписывания инструмента с нуля. |
| **MutAPK** / MutAPK 2.0 (github.com/TheSoftwareDesignLab/MutAPK, мутация DEX-байткода собранного APK) | Единственный реально собираемый (Maven), MIT-лицензия, документация есть. Но: 12 звёзд, 5 форков, **5 открытых issues без признаков ответа**, дата последнего коммита нигде не отображается (обычно значит — давно неактивен). Standalone CLI, не Gradle-плагин — интеграция в CI/локальный процесс потребовала бы ручной обвязки под каждый прогон. | Технически можно было бы попробовать разово вручную, но не как постоянная инфраструктура — риск unmaintained-зависимости не окупается. |
| **muDroid** (github.com/Yuan-W/muDroid) | Python **2.7** (снят с поддержки), лицензии нет вообще, `setup.py` нет, **0 issues и 0 PR** (не отсутствие проблем — отсутствие пользователей), жёстко требует разрешение экрана 1920×1200. | Нежизнеспособен полностью. |

Ни один инструмент не даёт готового, поддерживаемого пути к Mutation Score для androidTest. Вопрос закрыт до появления нового факта (например, реально поддерживаемого инструмента) — не переоткрывается без такого триггера.

**Практика в проекте**: Mutation Score считается вручную (без pitest/без androidTest-специфичных инструментов) — точечно, по запросу, на конкретных чистых функциях (пример: `MessageGrouping.isFirstInGroup`, 6/6 mutation kill, спека 0029).
