## Business Question

Владелец продукта (2026-09-03): «При открытии приложения слишком долго подгружается список — скорость появления первых сообщений должна быть в идеале мгновенной».

Это отдельная, новая задача от уже закрытых Milestone 21-23: те разбирали джанк (задержку между кадрами) *во время скролла* уже открытого списка; здесь речь о задержке *до появления* самого списка на экране при открытии приложения. Смежная спека [0020](../specs/0020-gateway-thread-and-startup-performance.md) (Implemented) уже устранила повторный резолвинг контактов и добавила SQL-индекс, но прямо зафиксировала пробел: «холодный старт субъективно не хронометрирован отдельно в этой сессии» — числового замера самой задержки открытия ни разу не было.

## Success Criteria

1. **Оба сценария открытия измеряются раздельно** — холодный старт (процесс не в памяти, как при первом запуске/после смахивания из недавних) и тёплый старт (процесс уже в памяти, `Activity` пересоздаётся/возобновляется). Оба важны, оба получают отдельные числа — не усредняются в один показатель.
2. **Числовая цель — ориентир системного SMS-приложения** (`com.transsion.smartmessage`, тот же эталон, что уже использовался в Milestone 21/23): замерить его время «открытие → первые видимые диалоги» тем же методом и на том же устройстве, и считать эту цифру целевым порогом для Gateway App, а не произвольное «<100мс».
3. **Локализация источника** — спека сама определяет, где именно уходит время (кандидаты: `SmsHistoryImporter` при холодном старте, сам `Room`-запрос `observeConversations`, `ContactNameResolver`, общий холодный старт процесса/JIT уже частично снятый Baseline Profile из Milestone 23 но не проверенный для этого конкретного пути, что-то ещё) — не предполагается заранее какая причина верна.
4. **Допустим частичный/инкрементальный первый рендер** — не требуется, чтобы весь список отрисовался одномоментно; достаточно, чтобы что-то реальное (хотя бы первые видимые на экране диалоги) появилось быстро, дальнейшая часть списка может дорисоваться чуть позже без видимой задержки для пользователя.
5. **Критерий закрытия** — конкретный фикс с измеренными цифрами до/после (по аналогии с вариантом a Допущения 7 из спек 0024/0025), сравнение с эталоном системного приложения. Если причина окажется platform-level и неустранимой в коде приложения — честный отрицательный результат с объяснением, тем же паттерном, что уже принят в спеке 0025.
6. Реализация не меняет backend-API — работа клиентская.

## Scope

**In scope:**
- Замер текущего времени «открытие приложения → первый реальный кадр со списком диалогов» на физическом устройстве (TECNO LI9), раздельно для холодного и тёплого старта.
- Тот же замер для `com.transsion.smartmessage` как эталон.
- Локализация источника задержки (импорт истории / SQL-запрос / резолвинг контактов / холодный старт процесса-JIT / сам UI-пайплайн `ConversationsViewModel`).
- Фикс найденной причины с измерением до/после тем же протоколом.

**Out of scope:**
- Повторное открытие уже закрытых спек 0020/0021/0022/0023/0024/0025 задним числом (только ссылки на их выводы).
- Джанк во время самого скролла (уже закрыт Milestone 23) — если он случайно всплывёт в замерах, фиксируется отдельно, не решается в рамках этой спеки.
- Изменения backend/Viewer App.

## Assumptions and Constraints

- Холодный и тёплый старт — оба в скоупе, измеряются и фиксируются раздельно.
- Целевой порог — не абстрактное число, а измеренное время открытия системного SMS-приложения на том же устройстве.
- Частичный первый рендер допустим как решение, если он даёт мгновенное ощущение появления данных.
- Причина не предполагается заранее — определяется по факту локализации в реализации.
