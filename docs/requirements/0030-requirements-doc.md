## Business Question

Текущий `data/perf` (11 файлов, 1560 строк) — по факту дневник одного расследования (specs 0024/0025/0026) про заедание при холодном скролле, а не устойчивая система регресс-контроля: часть тестов заменялась "полезными альтернативами" в процессе поиска причины (первые версии оказывались вводящими в заблуждение — см. `ColdScrollJankWarmupHypothesisTest`, опровергнут `ColdScrollJankAttachArtifactTest`). Владелец продукта хочет: (1) не допускать регресса производительности впредь, (2) всегда точно знать, на что уходит время — с атрибуцией по конкретным категориям: создание Activity, фазы Jetpack Compose (recomposition/layout/draw), файловый I/O, работа с `content://sms`, влияние JIT vs AOT (baseline profile) компиляции.

Явно НЕ отбрасываются существующие 8 файлов расследования — по решению владельца продукта они используются как основа новой системы, а не удаляются.

## Decision This Informs

**Decision type:** Operational (постоянная инфраструктура регресс-контроля, влияет на каждый будущий коммит, трогающий UI/старт/импорт).
**Decider:** Владелец продукта.
**Decision deadline:** нет жёсткого срока.
**What happens if this analysis isn't available:** регресс производительности обнаруживается только вручную, постфактум, живым наблюдением на устройстве (как это уже было с исходным багом spec 0024) — дорого, медленно, не воспроизводимо автоматически на каждом коммите.

## Success Criteria

1. Новый perf-набор построен на `AndroidX Macrobenchmark` (`androidx.benchmark.macro`) как harness — заменяет самодельные `Choreographer`/`JankStats`-обвязки из текущих 11 файлов везде, где Macrobenchmark даёт готовую метрику (`StartupTimingMetric`, `FrameTimingMetric`).
2. Доменные категории, не покрываемые встроенными метриками Macrobenchmark, измеряются через собственные `Trace.beginSection(...)`/`endSection()` маркеры, расставленные в продовом коде (`SmsHistoryImporter`, `ThreadContent`/Compose-фазы), читаемые `TraceSectionMetric`.
3. Покрыты все 4 категории:
   - Activity/Compose cold start (холодный старт до первых реальных строк — развитие `ColdStartConversationsListTest`, spec 0026).
   - Compose recomposition/layout/draw (разбивка кадра по фазам — новое, сейчас нигде не измеряется отдельно).
   - `content://sms` + файловый I/O (время самого запроса к провайдеру и записи в Room/файл — новое).
   - JIT vs AOT / baseline profile (сравнение `CompilationMode.None()` vs `CompilationMode.Full()`/сгенерированный baseline profile — новое, требует `BaselineProfileRule`).
4. Регресс определяется по паттерну "5 baseline-прогонов → диапазон min/max → выход за диапазон = регресс/прогресс", тот же метод, что уже применялся в specs 0024/0025 (`ColdScrollWarmupTest` и аналоги).
5. Baseline-диапазоны фиксируются в файле репозитория (формат — JSON рядом с тестами или `docs/PerfBaselines.md`, решается на этапе спеки), версионируются тем же коммитом, что и код, влияющий на перф.
6. Существующие 8 файлов расследования (specs 0024/0025) не удаляются — используются как источник уже проверенных сценариев/находок при проектировании новых тестов; какие именно из них переносятся as-is, какие переписываются на Macrobenchmark, а какие остаются как есть (документируют уже закрытый вопрос про `JankStats.createAndTrack`-артефакт и не нуждаются в повторном прогоне на каждом коммите) — решается в самой спеке после построчного разбора.
7. Автотесты — по стандартному правилу проекта; т.к. Macrobenchmark-модуль обычно отдельный Gradle-модуль (не `app`), потребуется решение по структуре модулей на этапе спеки.

## Scope

**In scope:**
- Новый Macrobenchmark-модуль (или расширение существующего perf-пакета — уточняется на этапе спеки).
- `Trace.beginSection` маркеры в `SmsHistoryImporter.kt` (импорт истории), `ThreadContent`/Compose-коде (recomposition-границы), там, где сейчас нет инструментации.
- Baseline profile генерация/подключение (`androidx.baselineprofile` Gradle plugin, если ещё не подключён — проверяется на этапе спеки).
- Разбор существующих 11 файлов `data/perf`: что оставить, что переписать, что архивировать.
- Файл фиксации baseline-диапазонов.

**Out of scope:**
- Изменения backend-API.
- Новые UI-фичи — эта итерация только про измерительную инфраструктуру.
- Ретроактивный анализ прошлых perf-инцидентов вне уже задокументированных в specs 0024/0025/0026.

## Assumptions and Constraints

- Инструмент — `AndroidX Macrobenchmark` как harness + собственные `Trace.beginSection` для доменных категорий (решение владельца продукта).
- Все 4 категории атрибуции — в первой версии (решение владельца продукта, а не MVP-подмножество).
- Baseline — 5 прогонов, диапазон min/max (решение владельца продукта, продолжение паттерна из specs 0024/0025).
- Baseline-числа хранятся в файле репозитория, версионируются вместе с кодом (решение владельца продукта).
- Существующие 8 файлов расследования не удаляются — используются как основа (решение владельца продукта).
