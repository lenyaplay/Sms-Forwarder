## Business Question

Milestone 22 (спека 0023) построил детерминированный протокол замера джанка списка диалогов, но переиспользовал одну композицию на слой с 5 прогонами, сбрасывая только позицию скролла между ними — а не пересоздавая экран заново. Владелец продукта указал на методологическую дыру: реальный лаг концентрируется именно в **первых** скроллах после холодного старта, и со временем (при прокрутке туда-сюда) заметно уменьшается — у системного SMS-приложения такого «прогрева» нет, оно ровное с самого начала. Значит 5 прогонов Milestone 22 сами по себе уже являются тем «прокручиванием туда-сюда», которое всё улучшает, и усреднённые 2.79-2.83% janky могли уже отражать прогретое состояние, а не то, что видит пользователь на холодном старте.

Владелец продукта уточнил ещё точнее: даже «первый прогон целиком» как единица измерения слишком груба — джанк может быть сконцентрирован в первых ~10% кадров одного прогона, а единое janky%-число на весь прогон эту локальную концентрацию маскирует так же, как усреднение по прогонам маскировало разницу между первым и последующими.

Нужен новый протокол: холодные прогоны со свежим запуском Activity/композиции каждый раз (не сброс позиции на старой) + сегментация внутри каждого прогона, чтобы увидеть форму кривой джанка, а не одно усреднённое число.

**Decider:** Владелец продукта.

## Success Criteria

1. Новый протокол замера использует **10 холодных прогонов** на сценарий, каждый — со свежим запуском `Activity`/композиции (не сброс позиции скролла на старой композиции, как в Milestone 22).
2. Каждый прогон разбивается на **децили по порядковому номеру кадра** (10 равных сегментов); после первого прогона данных строится распределение janky% по децилям, и при необходимости гранулярность корректируется (например до более мелких сегментов в начале прогона), если форма кривой это оправдывает — решение принимается по факту, не жёстко фиксируется деционным разбиением навсегда.
3. `FrameCounter`/эквивалент запоминает порядковый номер (и по возможности timestamp) каждого кадра, а не только суммарные total/jank счётчики — чтобы разбиение на сегменты было возможно постфактум.
4. То же измерение проведено на системном SMS-приложении (`com.transsion.smartmessage`) через `adb shell dumpsys gfxinfo <package> framestats` (единственный доступный инструмент для стороннего не-Compose приложения) — для сравнения, показывает ли оно ту же кривую «прогрева» или нет.
5. Гипотеза прогрева считается подтверждённой, если janky% в первых сегментах/прогонах статистически значимо выше, чем в последних (формула значимости — по аналогии с `JankComparison.kt` из Milestone 22: разница средних превышает разброс сравниваемого набора), не подтверждена — если разница внутри разброса.
6. Критерий закрытия Milestone при неудаче — **та же схема, что в Milestone 22** (Допущение 7 спеки 0023): либо (a) конкретный подтверждённый фикс с цифрами до/после, либо (b) полный проход без значимого результата **и** предложен более полезный диагностический инструмент/уточнённая методология + план следующего Milestone.
7. Реализация не меняет backend-API — вся работа клиентская, ограничена androidTest-инфраструктурой и (при необходимости, по итогам исследования причины) точечным фиксом в `main`.

## Scope

**In scope:**
- Новый протокол: 10 холодных прогонов на сценарий, каждый со свежим запуском `Activity`/композиции — техническое решение проблемы «`ComposeTestRule.setContent` только один раз за тест-метод» (найдено в Milestone 22) фиксируется в спеке.
- Сегментация janky% по децилям номера кадра внутри каждого прогона, с возможной корректировкой гранулярности по факту первых данных.
- Расширение `FrameCounter` (или новый эквивалент) для хранения порядкового номера/timestamp каждого кадра.
- Измерение на системном SMS-приложении через `adb shell dumpsys gfxinfo framestats` для сравнения кривой прогрева.
- Проверка гипотезы прогрева на уже собранных данных Milestone 22 (1-й прогон vs остальные, для контекста, не как основной источник вывода).
- Если гипотеза подтвердится — исследование вероятных причин (холодная композиция строк `LazyColumn`, JIT-прогрев, декодирование шрифтов/иконок при первом рендере) и точечный фикс с измерением до/после.
- Перенесённые из Milestone 22 пункты: тот же протокол на реальном `ConversationsScreen` через `MainActivity` с реальной SMS-историей (с заранее подтверждённой ролью SMS-приложения по умолчанию — см. поправку из peer-review Milestone 22); прямой A/B `performTouchInput` vs `adb shell input swipe` на одном экране в одном прогоне.

**Out of scope:**
- Изменение уже закрытой спеки 0023 задним числом — её выводы (эмерджентность не подтверждена на синтетических данных, Слой 4 фактически не проверил реальные данные) остаются как честно задокументированный исторический результат.
- Полноценная пагинация/виртуализация или архитектурный рефакторинг списка диалогов сверх того, что подтверждено измерением как причина.
- Любые изменения backend/Viewer App.

**Known data quality issues:** `dumpsys gfxinfo framestats` даёт только последние ~120 кадров — для 10 холодных прогонов с достаточным числом кадров на прогон нужно проверить, укладывается ли типичный прогон (несколько свайпов) в это окно, иначе снимать `framestats` сразу после каждого прогона, не накапливая несколько прогонов подряд без чтения.

## Assumptions and Constraints

- 10 холодных прогонов на сценарий (вдвое больше, чем 5 в Milestone 22) — каждый прогон требует полного пересоздания `Activity`/композиции, что медленнее переиспользования одной композиции; ожидаемое время прогона протокола оценивается и честно фиксируется в спеке перед стартом реализации.
- Сегментация — децили по номеру кадра как стартовая гранулярность, но не жёстко финальная: после первого набора данных гранулярность может быть скорректирована (например мельче в начале прогона), если форма распределения это оправдывает — решение принимается по факту, задокументировано в спеке, а не предрешено здесь.
- Системное SMS-приложение измеряется через `adb shell dumpsys gfxinfo framestats` — единственный доступный инструмент для стороннего приложения без доступа к его исходному коду/composition-инфраструктуре; ограничение окна в ~120 кадров учитывается в протоколе замера.
- Критерий закрытия — идентичен Допущению 7 спеки 0023 (Milestone 22): фикс с цифрами ИЛИ «не подтверждено» + новый/уточнённый инструмент + план следующего Milestone.
- Спека 0023 (Milestone 22) не переписывается задним числом — этот Milestone работает с уже зафиксированными данными как с историческим контекстом, новые выводы идут в новую спеку 0024.
