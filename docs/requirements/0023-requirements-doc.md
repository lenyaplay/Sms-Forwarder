## Business Question

Milestone 21 (спека 0022) закрыт как Implemented-partial: инструментарий (`PerfMonitor`/`JankStats`) и фикс холодного старта пустого состояния — сделаны и живо проверены. Причина лага скролла списка диалогов осталась не найдена: три кандидата (`distinctUntilChanged()`, тень `Card`, `SwipeToDismissBox`) не дали воспроизводимого эффекта на реальном устройстве. Дополнительно вскрылась методологическая проблема: единичный замер `adb shell dumpsys gfxinfo` через `adb shell input swipe` ненадёжен на этом устройстве/датасете — идентичный билд и жест дали от 29 до 202 отрендеренных кадров в разных прогонах, что подрывает доверие ко всем прошлым сравнениям.

Владелец продукта выдвинул гипотезу: лаг может быть эмерджентным свойством *комбинации* компонентов экрана, не сводимым ни к одному из них по отдельности. Нужен новый, методологически надёжный эксперимент — изолированный минимальный baseline + послойное добавление реальных компонентов экрана, с замером после каждого слоя, чтобы либо найти слой (или сочетание), на котором джанк впервые появляется, либо получить обоснованный вывод, что эмерджентность на текущем датасете не подтверждается.

## Success Criteria

1. Спека фиксирует изолированный тестовый экран как инструментированный тест (`ComposeTestRule`), не dev-only production-экран — не попадает ни в debug, ни в release APK.
2. Протокол замера: детерминированный programmatic scroll через `ComposeTestRule` (не `adb shell input swipe`), 5 прогонов на каждый слой, отчёт как среднее + разброс (min-max), а не единичное число.
3. Порог «джанк воспроизведён на этом слое»: разница среднего % janky-кадров этого слоя относительно baseline-слоя должна превышать разброс (min-max) baseline-прогонов — не просто «на глаз» и не абсолютное произвольное число.
4. Слои эксперимента и порядок их добавления зафиксированы в спеке явно: (0) минимальный `LazyColumn` с простыми `Text`-строками как baseline → (1) `Card` → (2) тень `Card` → (3) `SwipeToDismissBox` → (4) реальные данные из `ConversationsViewModel`/`ConversationUi`.
5. Финальный критерий закрытия Milestone описан честно и не подменяется искусственным дедлайном (см. Assumptions and Constraints).
6. Реализация не меняет backend-API — вся работа клиентская, ограничена androidTest-инфраструктурой и (при необходимости) новым диагностическим инструментом.

## Scope

**In scope:**
- Новый инструментированный тест (androidTest, `ComposeTestRule`) с изолированным минимальным composable-экраном (простой `LazyColumn` из `Text`-строк, без `Card`/`SwipeToDismissBox`/реального маппинга `ConversationUi`) как baseline для замера.
- Детерминированный programmatic scroll через `ComposeTestRule` (например `performTouchInput { swipe(...) }` или эквивалент), устраняющий шум `adb shell input swipe`, обнаруженный в Milestone 21.
- Замер джанка каждого слоя через существующий `PerfMonitor`/`JankStats` (из Milestone 21) внутри инструментированного теста, 5 прогонов на слой, среднее + разброс.
- Послойное добавление реальных компонентов экрана поверх baseline (`Card` → тень → `SwipeToDismissBox` → реальные данные `ConversationsViewModel`), с замером после каждого слоя и фиксацией, на каком слое (или сочетании) джанк впервые статистически значимо (см. Success Criteria #3) появляется.
- Если конкретная причина найдена — фикс с цифрами до/после, по аналогии с B-разделом Milestone 21, но на надёжной методологии.
- Если причина не найдена даже при надёжной методологии — честная фиксация «эмерджентность на этом датасете не подтверждена / статистически не отличима от baseline» и переход к финальному критерию закрытия (см. ниже).

**Out of scope:**
- Dev-only экран в реальном приложении, доступный из debug-сборки — отклонено владельцем продукта в пользу изолированного инструментированного теста.
- `adb shell input swipe` как основной метод замера этого Milestone (использовался в Milestone 21, показал ненадёжность) — заменяется детерминированным programmatic scroll.
- Полноценная пагинация/виртуализация или архитектурный рефакторинг списка диалогов сверх того, что подтверждено измерением как причина лага.
- Любые изменения backend/Viewer App.

## Assumptions and Constraints

- Тестовый экран — исключительно инструментированный тест (`ComposeTestRule`), не часть реального приложения; не попадает ни в debug, ни в release APK. Выбрано явно вместо dev-only экрана в приложении.
- Протокол замера: 5 прогонов на каждый слой, детерминированный programmatic scroll через `ComposeTestRule` вместо `adb shell input swipe` — устраняет шум ручного/adb-жеста, обнаруженный в Milestone 21.
- Порог «джанк воспроизведён на слое»: разница среднего % janky-кадров этого слоя vs baseline должна превышать разброс (min-max) baseline-прогонов. Если разница внутри разброса baseline — эффект не считается подтверждённым, слой не помечается как причина.
- **Финальный критерий закрытия Milestone 22 (дословно от владельца продукта, отличается от изначально предложенных аналитиком вариантов):** Milestone закрывается либо (a) когда причина лага найдена и подтверждена по протоколу выше, либо (b) когда по итогам полного послойного прохода причина не подтверждена, **и** для дальнейшей диагностики придуман и задокументирован ещё более полезный диагностический инструмент, чем использованный в этом Milestone, вместе с планом следующего Milestone на его основе. Просто «прошли все слои, ничего не нашли, закрываем как есть» — недостаточно; неограниченный проход по времени/усилиям без готового плана «что дальше» — тоже недостаточно. Обязательно нужен либо конкретный фикс, либо конкретный лучший инструмент + план следующего шага.
- Существующий `PerfMonitor`/`JankStats` из Milestone 21 переиспользуется как измерительный механизм внутри новых инструментированных тестов — не заменяется, если только в ходе работы не обнаружится, что он сам недостаточен для programmatic-scroll-сценария (тогда это отдельно фиксируется как открытый вопрос).
