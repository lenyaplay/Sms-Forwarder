## The Question

> Может ли лаг скролла быть эмерджентным свойством комбинации компонентов экрана — и как это проверить методологией, которая не страдает от шума единичных замеров `adb shell input swipe`, обнаруженного в Milestone 21?

---

## What "Done" Looks Like

1. Спека `docs/specs/0023-gateway-scroll-jank-isolation.md` написана — изолированный тестовый экран, надёжный протокол замера, послойный план, критерии приёмки и тесты для каждого пункта.
2. Инструментированный тест с минимальным baseline-экраном (`LazyColumn` из `Text`) существует и измерен по протоколу (5 прогонов, programmatic scroll).
3. Каждый реальный слой экрана (`Card`, тень, `SwipeToDismissBox`, реальные данные) добавлен поверх baseline и измерен тем же протоколом; для каждого — зафиксировано, статистически значим ли джанк относительно baseline (разница > разброса baseline).
4. Итог — либо конкретный подтверждённый фикс с цифрами до/после, либо честно задокументированное «эмерджентность не подтверждена на этом датасете» **вместе с** предложенным более полезным диагностическим инструментом и планом следующего Milestone (обязательное условие закрытия по требованию владельца продукта — см. requirements doc, Assumptions).
5. `docs/roadmaps/Roadmap 2.md` — Milestone 22 обновлён с честной фиксацией итога.

## Scope

| In scope | Out of scope |
|---|---|
| Инструментированный тест (`ComposeTestRule`) с изолированным минимальным composable | Dev-only экран в реальном приложении |
| Детерминированный programmatic scroll (5 прогонов/слой, среднее+разброс) | `adb shell input swipe` как основной метод замера |
| Послойное добавление: baseline → `Card` → тень → `SwipeToDismissBox` → реальные данные `ConversationsViewModel` | Архитектурный рефакторинг/пагинация сверх найденной причины |
| Переиспользование существующего `PerfMonitor`/`JankStats` (Milestone 21) как измерительного механизма | Backend/Viewer App |
| При неудаче — обязательный новый диагностический инструмент + план следующего Milestone | Закрытие Milestone без фикса и без плана «что дальше» |

## Approach (high level)

1. Спека 0023: описать минимальный baseline composable, протокол измерения (5 прогонов, programmatic scroll, среднее+разброс), порог значимости (разница > разброса baseline), точный порядок слоёв.
2. `query-validation` — проверить формулировки протокола/порога на однозначность перед кодом (например: как именно считается «разброс», что делать при выбросах).
3. Реализация: инструментированный тест с baseline-экраном + переиспользование `PerfMonitor`; замер baseline (5 прогонов).
4. Послойное добавление компонентов, замер после каждого слоя, фиксация первого слоя со статистически значимым отличием (если есть).
5. Тесты — сам инструментированный эксперимент и есть основной артефакт; плюс обычные unit/instrumented тесты для любого нового кода (например, вспомогательных функций подсчёта среднего/разброса, если они появятся как переиспользуемый код, а не только тестовая логика).
6. `peer-review-template`, `analysis-qa-checklist`.
7. Обновить спеку (→ `Implemented` или честный partial-статус) и `Roadmap 2.md` (Milestone 22) — с итоговым результатом (фикс с цифрами ИЛИ «не подтверждено» + новый инструмент + план следующего Milestone).

## Constraints and Risks

- Реальный датасет диалогов на устройстве может быть слишком мал для устойчивого sustained-скролла даже при programmatic scroll — если подтвердится, фиксируется явно в спеке как ограничение эксперимента (см. requirements doc, Open Question #5).
- Инструментированный тест исполняется на реальном устройстве (не Robolectric) — время прогона всего протокола (5 слоёв × 5 прогонов = минимум 25 измерений) может быть заметным; спека должна честно оценить ожидаемое время выполнения перед стартом.
- Обязательное условие закрытия при неудаче (новый инструмент + план следующего Milestone) — это более высокая планка, чем просто «прошли все слои»; должно быть заложено в план работы с самого начала, не как запоздалая доработка в конце.
