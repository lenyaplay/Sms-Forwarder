## The Question

> Реальный лаг концентрируется именно в первых скроллах после холодного старта и уменьшается со временем (в отличие от системного приложения) — методология Milestone 22 (усреднение по 5 прогонам с переиспользованием композиции) могла замаскировать это. Как измерить именно холодный/первый эффект, включая возможную концентрацию джанка в первых кадрах одного прогона, а не только между прогонами?

---

## What "Done" Looks Like

1. Спека `docs/specs/0024-gateway-cold-scroll-warmup-diagnosis.md` написана — новый протокол (10 холодных прогонов со свежей Activity, децили внутри прогона), критерии приёмки и тесты.
2. Гипотеза прогрева проверена статистически на новом протоколе (не только на данных Milestone 22 задним числом).
3. То же измерение снято на системном SMS-приложении через `dumpsys gfxinfo framestats` для сравнения.
4. Итог — либо конкретный подтверждённый фикс с цифрами до/после, либо честно задокументированное «прогрев не подтверждён на этом протоколе» + предложенный более точный инструмент/методология + план следующего Milestone (та же схема, что Допущение 7 спеки 0023).
5. `docs/roadmaps/Roadmap 2.md` — Milestone 23 обновлён с честной фиксацией итога.

## Approach (high level)

1. Спека 0024: зафиксировать новый протокол (10 прогонов, свежая Activity на каждый, децили внутри прогона), техническое решение ограничения «`setContent` один раз за тест-метод» (вероятно — отдельные `@Test`-методы per прогон, по аналогии с подходом к слоям в Milestone 22), ожидаемое время выполнения полного протокола.
2. `query-validation` перед кодом — проверить формулировки формулы значимости для сегментов/прогонов, условие «прогрев подтверждён», согласованность с уже принятым в Milestone 22 подходом (`JankComparison.kt`).
3. Реализация: расширение `FrameCounter` для хранения порядкового номера кадра, новый тест-класс/метод(ы) для холодных прогонов с сегментацией, измерение на системном приложении через `framestats`.
4. Живой прогон на TECNO LI9, заполнение таблицы результатов в спеке.
5. Перенесённые из Milestone 22 пункты (реальный экран, A/B инструментов замера) — в рамках той же работы или явно вынесены дальше, если объём не позволяет всё за один заход (решается по ходу реализации, честно фиксируется).
6. Тесты — в рамках той же работы, не отдельным шагом.
7. `peer-review-template`, `analysis-qa-checklist`.
8. Обновить спеку (→ `Implemented` или честный partial-статус) и `Roadmap 2.md` (Milestone 23) — с итоговым результатом.

## Constraints and Risks

- 10 прогонов с полным пересозданием Activity каждый раз может быть заметно медленнее 5 прогонов Milestone 22 (переиспользовавших одну композицию) — время выполнения полного протокола оценивается и честно фиксируется в спеке перед стартом.
- `dumpsys gfxinfo framestats` даёт только последние ~120 кадров — при недостаточном окне для нескольких свайпов подряд нужно снимать данные сразу после каждого прогона, не накапливая.
- Спека 0023 не переписывается задним числом — если новый протокол даст данные, по-новому интерпретирующие результаты Milestone 22, это фиксируется как отдельная новая находка в спеке 0024, с явной ссылкой на 0023, а не правкой уже закрытого документа.
