# Development

Правила разработки проекта sms_forwarder. Цель — чтобы проект был восстановим по документации даже при полной потере кода, и чтобы каждая фича была проверяема автоматически.

## Спецификация прежде кода

Каждая фича (backend или Android) описывается отдельным документом `docs/specs/NNNN-<slug>.md` **до или вместе с** реализацией. Спецификация не зависит от того, реализована фича или нет — она фиксирует назначение, интерфейс и критерии приёмки независимо от кода.

Нумерация — `0001`, `0002`, ... по возрастанию создания, сквозная для backend и Android. Одна спецификация может быть меньше milestone'а из `docs/Roadmap.md` или охватывать несколько.

### Шаблон спецификации

```markdown
# NNNN — Название фичи

**Статус:** Draft | Implemented

## Контекст
Зачем нужна эта фича, что она решает.

## API / интерфейс
Эндпоинты, форматы запросов/ответов, коды ошибок — или, для Android, экраны/классы и их контракты.

## Модель данных
Новые/изменённые таблицы или сущности (если есть).

## Сценарии использования
Основные пользовательские/системные сценарии.

## Критерии приёмки
Конкретный список условий, по которым фича считается готовой.

## Тесты
Какие тест-кейсы покрывают критерии приёмки.
```

После реализации статус меняется на `Implemented`.

## Обязательное использование скилов разработки

Для каждой фичи (backend или Android), от сбора требований до пометки спеки `Implemented`, обязательны следующие шаги — каждый выполняется явным вызовом соответствующего скила, не имитируется вручную "по памяти":

1. **`stakeholder-requirements-gathering`** — до или во время написания спеки, если в задаче есть неоднозначность (модель данных, поведение при конфликтах, ограничения). Результат — раздел «Допущения и решения» в спеке.
2. **`query-validation`** — перед применением любой новой SQL-миграции.
3. **`peer-review-template`** — после реализации, до пометки спеки `Implemented`. Ревью кода на соответствие критериям приёмки и паттернам существующего кода.
4. **`analysis-qa-checklist`** — финальный проход перед `Implemented`: построчная сверка каждого пункта «Критерии приёмки» и «Тесты» спеки с тем, что реально покрыто автотестами.

Прогон тестов и `go vet` — необходимое, но не достаточное условие готовности. Пункты 3 и 4 обязательны отдельно, даже если все тесты уже зелёные: на практике они находят пробелы, которые прохождение тестов не вскрывает (например, эндпоинт защищён логикой, но не покрыт **своим** тестом на конкретный код ошибки, а не общим для нескольких роутов).

## Обязательные автотесты

Ни одна фича — backend или Android — не считается завершённой без автотестов, написанных в рамках той же работы, что и сама фича (не "добавим тесты потом").

- **Backend (Go):** стандартный пакет `testing`, файлы `*_test.go` рядом с тестируемым кодом. Для HTTP-хендлеров — `net/http/httptest`. Для кода, работающего с БД, — реальная SQLite (временный файл или `:memory:`) с применёнными миграциями, не моки.
- **Android (Kotlin):** unit-тесты (JUnit) для логики, инструментальные тесты — где нужна проверка на реальном Android-окружении. Вводятся с момента, когда стартует разработка функциональности приложения (см. `docs/Roadmap.md`, Milestone 6+).

## Скилы для Android-разработки

Для любой задачи в `android/` перед началом работы обязательно загружать скил `android-skills:android-dev` (плагин `android-skills`) — это базовый скил-роутер, который задаёт house-defaults проекта (DI, async, JSON, слои, модель ошибок) и по таблице маршрутизации внутри себя указывает, какой более специфичный скил (`android-skills:compose`, `android-skills:android-retrofit`, `android-skills:kotlin-flows`, `android-skills:android-testing` и т.д.) загрузить дополнительно под конкретную часть задачи (UI, сеть, корутины, тесты, DI, сборка). Таблица маршрутизации не дублируется здесь — она в самом скиле, единый источник истины.

Это дополняет, а не заменяет 4 обязательных скила разработки фичи из раздела выше.

## Структура backend-кода

Слоистая архитектура: `handlers → services → storage`.

- `internal/handlers` — HTTP-слой: парсинг запроса, вызов сервиса, формирование ответа. Не содержит бизнес-логики.
- `internal/services` — бизнес-логика фич, оркестрирует вызовы `storage` и вспомогательных пакетов (`internal/auth` и т.п.).
- `internal/storage` — доступ к БД: репозитории с методами вида `CreateX`, `GetXByY`, без бизнес-логики.
- `internal/config` — конфигурация из переменных окружения с дефолтами.
- `internal/migrations` — SQL-миграции, встроенные через `embed.FS`, применяются автоматически при старте (`storage.Migrate`).

Формат ошибок HTTP API — единый JSON: `{"error": "сообщение"}`. Коды: `400` — невалидный запрос, `401` — не аутентифицирован/невалидные креды, `403` — нет доступа, `404` — не найдено, `409` — конфликт (например, занятый логин), `500` — внутренняя ошибка.

## Запуск

```
cd backend
go build ./...      # сборка
go vet ./...         # статический анализ
go test ./...        # все автотесты
go run ./cmd/server   # запуск сервера
```
