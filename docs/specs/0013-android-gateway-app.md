# 0013 — Android Gateway App (собственное SMS-приложение по умолчанию)

**Статус:** Draft

## Контекст

Новый Milestone (следующий после Milestone 11, `docs/Roadmap.md`). До сих пор источником SMS на устройстве-шлюзе был сторонний `android_income_sms_gateway_webhook` («Gateway App», см. `0003-sms-webhook.md`, где он зафиксирован как «сторонний, неизменяемый»).

При диагностике на физическом устройстве (TECNO LI9, HiOS) в этой сессии выяснено:

1. Manifest стороннего Gateway App не содержит ни одного из четырёх компонентов, обязательных для того, чтобы Android предложил приложение как кандидата на роль SMS-по-умолчанию: `BroadcastReceiver` на `SMS_DELIVER_ACTION`, `BroadcastReceiver` на `WAP_PUSH_DELIVER_ACTION`, `Service` на `RESPOND_VIA_MESSAGE`, `Activity` с `SENDTO` для `sms:`/`mms:`. Он использует только обычный `SMS_RECEIVED` (не `SMS_DELIVER`) с `android:priority="999"` — максимальным доступным приоритетом для не-дефолтного приложения.
2. Пока приложение не является дефолтным SMS-обработчиком, доставка `SMS_RECEIVED` не гарантирована: штатное приложение («Сообщения», `com.transsion.smartmessage` на этом устройстве), будучи дефолтным, может обработать упорядоченную трансляцию первым и вызвать `abortBroadcast()`, из-за чего Gateway App с более низким приоритетом никогда не получает уведомление. Подтверждено косвенно: тест с полным заморозом/фоном приложения показал получение SMS-уведомления штатным приложением при полном отсутствии активности Gateway App в логах в это же окно.
3. Отдельно OEM (Transsion Hiber) замораживает фоновые процессы не-дефолтных приложений жёстче стандартного Doze, добавляя ещё один независимый канал потери сообщений.

Итог: пока не-дефолтное приложение принципиально не может гарантировать приём каждого SMS на этом классе устройств. Единственное надёжное решение — собственное приложение, которое **можно назначить дефолтным SMS-обработчиком**, что даёт ему `SMS_DELIVER_ACTION` (не упорядоченная трансляция, доставляется только дефолтному приложению, `abortBroadcast()` других приложений её не затрагивает) и системную защиту дефолтного SMS-приложения от агрессивного OEM-фриза (см. `Hiber/appStateMachine: ... importantcase is: default_sms` в логах — льгота выдаётся именно текущему дефолтному обработчику).

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Отдельное новое Android-приложение**, не расширение существующего Viewer App. Устанавливается отдельно, может быть назначено дефолтным SMS-приложением. Viewer App остаётся просмотрщиком сообщений через backend и не меняет свою роль.
2. **MVP — полноценный SMS-клиент**, а не только «приёмник + пересылка»: список диалогов (threads), чтение и отправка SMS, работа как обычное SMS-приложение пользователя на телефоне, плюс пересылка входящих на webhook. Причина: приложение будет ежедневным дефолтным SMS-клиентом владельца, «недо-приложение» без нормального UI неприемлемо для постоянного использования.
3. **Формат пересылки на backend** — переиспользуется существующий эндпоинт `POST /webhook?upload_token=...` и существующий формат тела из `0003-sms-webhook.md` (`from`, `text`, `sentStamp`, `receivedStamp`, `sim`) без изменений. Backend не меняется в рамках этой спеки. Отдельно (вне этой спеки, backlog) владелец хочет впоследствии сделать backend способным принимать несколько форматов пересылки и добавить собственный, более строгий формат специально для этого приложения — зафиксировано как открытый вопрос ниже, не блокирует эту спеку.
4. **Multi-SIM поддерживается**: приложение определяет слот SIM, с которого пришло сообщение (через `SubscriptionManager`/`SmsMessage` API, а не эвристику перебора имён полей `Bundle`, как в стороннем Gateway App — у нас есть официальный API, эвристика была нужна стороннему приложению из-за неполноты `SmsMessage`, у нас над этим есть контроль), передаёт его в поле `sim` webhook-запроса, и позволяет пользователю выбрать SIM при отправке нового сообщения (если SIM две).
5. **MMS — не в MVP.** Обычный SMS-клиент по факту также обязан объявить обработку `WAP_PUSH_DELIVER_ACTION`, чтобы быть валидным кандидатом на дефолт, но реализация приёма/отображения самих MMS откладывается (задача — просто не падать/не терять MMS молча). Зафиксировано в backlog.
6. Область (backend `docs/Architecture.md`, `docs/specs/0003-sms-webhook.md`) не меняется в этой спеке.

## Функциональность MVP

Обычные функции SMS-клиента, которые нужны для повседневного использования как дефолтного приложения (список того, что «чаще всего есть» в SMS-приложении, ограниченный тем, что нужно для замены системного):

- Список диалогов (по номеру телефона/контакту), отсортированный по времени последнего сообщения.
- Просмотр истории переписки в диалоге.
- Отправка нового SMS (новому номеру или в существующий диалог), с выбором SIM-слота при двух SIM.
- Быстрый ответ через `RESPOND_VIA_MESSAGE` (обязателен для роли дефолтного SMS-приложения — минимальная реализация, не полноценный UI).
- Уведомления о новых входящих сообщениях.
- Импорт истории SMS, уже находящейся в системном провайдере (`content://sms`), при первом запуске/после назначения дефолтным — иначе после переключения пользователь видит пустой список диалогов вместо своей реальной переписки.
- Пересылка каждого входящего SMS на backend через существующий webhook (см. допущение 3), включая слот SIM (допущение 4).
- Настройка адреса сервера и `upload_token` (переиспользуется тот же паттерн, что и `ServerConfigStore` в Viewer App, но это отдельное приложение — своё независимое хранилище настроек).

Вне MVP (backlog, см. ниже): MMS-контент, архивация/удаление диалогов, поиск по переписке, RCS.

## Архитектура

Новый независимый Gradle-проект `android_gateway/` (по аналогии с `android/` для Viewer App) — отдельный APK с собственным `applicationId` (например, `com.smsforwarder.gateway`, уточнить при реализации, не конфликтует с `android/app`'s `applicationId`). Технологический стек — тот же, что уже принят для Viewer App (Kotlin, Jetpack Compose, MVVM/MVI по конвенции `android-skills:android-dev`), чтобы не вводить второй стек в проект.

Ключевые компоненты (обязательны для роли дефолтного SMS-приложения, требования Android):

- `BroadcastReceiver` на `SMS_DELIVER_ACTION`, guarded `android:permission="android.permission.BROADCAST_SMS"`, `exported="true"` — точка приёма входящих SMS. В отличие от `SMS_RECEIVED` у стороннего Gateway App, это не упорядоченная трансляция и доставляется только текущему дефолтному приложению — не подвержена `abortBroadcast()` другими приложениями.
- `BroadcastReceiver` на `WAP_PUSH_DELIVER_ACTION`, `android:permission="android.permission.BROADCAST_WAP_PUSH"` — минимальная реализация (не роняет MMS, не отображает контент в MVP, см. допущение 5).
- `Service` с `intent-filter` на `android.intent.action.RESPOND_VIA_MESSAGE`, `android:permission="android.permission.SEND_RESPOND_VIA_MESSAGE"` — минимальный быстрый ответ.
- `Activity` с `intent-filter` на `android.intent.action.SENDTO` для схем `sms`/`smsto`/`mms`/`mmsto` — экран отправки/просмотра диалога.
- Стандартный набор разрешений: `RECEIVE_SMS`, `SEND_SMS`, `READ_SMS`, `RECEIVE_MMS`, `READ_CONTACTS` (для отображения имён), `POST_NOTIFICATIONS`.

Пересылка на webhook переиспользует ту же модель, что и сторонний Gateway App (WorkManager, `HttpURLConnection`, ретраи с экспоненциальным backoff, до N попыток) — она была независимо подтверждена рабочей в этой сессии (успешный `201` подтверждён кросс-логами телефона и бэкенда), нет причин её менять, только адаптировать под Kotlin/архитектуру нового приложения.

## Сценарии использования

1. Пользователь устанавливает Gateway App, назначает его дефолтным SMS-приложением в системных настройках (роль появляется в списке кандидатов благодаря наличию всех обязательных компонентов).
2. При первом запуске / после назначения дефолтным — импорт существующей истории SMS из `content://sms` в локальное хранилище приложения, список диалогов не пустой.
3. Входящее SMS → `SMS_DELIVER_ACTION` receiver получает его гарантированно (не upornoyed broadcast, не подвержено чужому `abortBroadcast()`) → сохраняется в диалог, показывается уведомление, дублируется на backend через существующий webhook с определённым слотом SIM.
4. Пользователь открывает диалог, читает историю, отправляет ответ, выбирая SIM (если их две).
5. Пользователь получает MMS/WAP push — приложение не падает и не блокирует основной поток приёма SMS (MVP не отображает содержимое MMS, см. допущение 5).
6. Стороннее приложение отправляет `ACTION_RESPOND_VIA_MESSAGE` (быстрый ответ, например, при отклонении звонка) — сервис отправляет SMS с переданным текстом без открытия UI.

## Критерии приёмки

- Приложение появляется в системном списке кандидатов на «Приложение для SMS по умолчанию» (проверяется на физическом устройстве, включая TECNO LI9/HiOS).
- После назначения дефолтным: входящее реальное SMS доставляется приложению, сохраняется в диалог и появляется в вебхук-логах бэкенда (`docker logs`) — подтверждено на физическом устройстве, включая тест с приложением в фоне (сценарий, который проваливался у стороннего Gateway App).
- История SMS, существовавшая в системе до назначения приложения дефолтным, видна в списке диалогов после первого запуска.
- Отправка SMS из UI приходит получателю (проверено на реальном номере/через второе устройство).
- На устройстве с двумя SIM: входящее сообщение содержит корректный слот SIM и в UI, и в поле `sim` webhook-запроса; при отправке доступен выбор SIM.
- `RESPOND_VIA_MESSAGE` не падает при вызове системой (минимальная проверка — сервис принимает intent и отправляет SMS).
- MMS/WAP push не приводит к падению приложения или потере последующих SMS.
- Формат и эндпоинт webhook-запроса соответствуют `0003-sms-webhook.md` без изменений backend.

## Тесты

- Unit: логика определения SIM-слота (`SubscriptionManager`-based), сборка тела webhook-запроса (соответствие формату `0003`), логика импорта истории из `content://sms` (на fake/mock content resolver).
- Инструментированные (Compose UI): список диалогов, экран переписки, экран отправки с выбором SIM (два SIM — fake), настройка сервера/`upload_token`.
- Ручная сквозная проверка на физическом устройстве (обязательна, аналогично `0009`/`0011`/`0012`): назначение дефолтным, приём реального SMS в фоне и с выключенным экраном, кросс-проверка логов телефона и бэкенда, отправка реального SMS, работа на дуал-SIM устройстве.

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Поддержка backend несколькими форматами пересылки + новый, более строгий собственный формат специально для этого приложения (озвучено владельцем как желаемое направление после этой спеки) — отдельная будущая спека, требует отдельного сбора требований (какой именно новый формат, нужна ли обратная совместимость со старым Gateway App форматом).
- Полноценный приём и отображение MMS-контента.
- Архивация/удаление диалогов, поиск по переписке, RCS.
- Миграция существующих устройств-шлюзов со стороннего Gateway App на новое приложение (порядок действий для пользователя, нужен ли параллельный запуск на время миграции) — не описана в этой спеке, будет отдельным шагом при внедрении.
