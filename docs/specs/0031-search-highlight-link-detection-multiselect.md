# 0031 — Подсветка поиска, распознавание ссылок/телефонов/OTP, множественное выделение сообщений (Milestone 26 остаток)

**Статус:** Implemented

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0031-requirements-doc.md](../requirements/0031-requirements-doc.md) и [docs/requirements/0031-analysis-brief.md](../requirements/0031-analysis-brief.md) — эта спека их источник истины по деталям реализации.*

## Контекст

Milestone 26 закрыт в частях 1 (спека 0028, визуальный полишинг) и 2 (спека 0029, SIM-индикатор/группировка/скрытие клавиатуры). Владелец продукта (2026-09-04) поручил доделать одной спекой оставшиеся 3 пункта бэклога того же Milestone: подсветка совпадений в поиске, распознавание ссылок/телефонов/OTP-кодов в тексте сообщения, Telegram-style множественное выделение сообщений с массовым удалением.

Прочитан текущий код (не предположение):
- `ConversationsScreen.kt`'s `SearchResultsList` (строка ~261) рендерит `SearchResultUi.text` как обычный `Text` — без выделения совпадения с `uiState.query`.
- `ThreadScreen.kt`'s `MessageBubble` (строка ~263): `combinedClickable(onClick = {}, onLongClick = { showMenu = true })` — long-press сразу открывает `DropdownMenu` с единственным пунктом "Удалить" (строки 290, 321-329). Текст сообщения — простой `Text(message.text)` (строка 294), без сегментации.
- `ThreadUiState.kt` — плоская data class, нет поля для множественного выделения.
- `ThreadViewModel.kt` — `onDeleteMessage(messageId: Long)` вызывает `repository.deleteMessage(id)` по одному; массового удаления нет.
- `MessageRepository.kt`'s `deleteMessage(id: Long)` (строка 67) — `NonCancellable`, резолвит `systemSmsId`, удаляет из Room и системного хранилища.

## Допущения и решения

1. **OTP-эвристика — любое отдельное 4-6-значное число** (решение владельца продукта, `AskUserQuestion`) — без учёта контекстных слов ("код", "пароль" и т.п.). Осознанный компромисс: время/год/произвольные короткие числа в тексте сообщения тоже будут подсвечены и кликабельны как "OTP" — не считается дефектом, не исправляется в рамках этой спеки.
2. **Множественное выделение сообщений поддерживается** (решение владельца продукта) — не ограничено одним сообщением за раз.
3. **Приоритет между тремя пунктами — равнозначный** (решение владельца продукта), реализация в порядке нарастания сложности: подсветка поиска → распознавание элементов текста → множественное выделение.
4. **Массовое удаление — без новой DAO/repository-операции**: `ThreadViewModel` вызывает существующий `repository.deleteMessage(id)` для каждого id из набора выделенных, последовательно в одной корутине — набор выделения на практике мал (пользователь выделяет вручную), отдельная batch-операция в `MessageDao` не оправдана (не добавлять абстракцию сверх необходимого).
5. **Хит-тестинг кликабельных сегментов внутри уже кликабельного `MessageBubble`**: `combinedClickable` на `Column`-контейнере обрабатывает только простой tap/long-press по любому месту пузыря, не долетающему до текста. Кликабельные сегменты текста (ссылка/телефон/OTP) реализуются через `ClickableText`/`buildAnnotatedString` с собственными `LinkAnnotation`/`onClick`-обработчиками, которые Compose приоритизирует над внешним `combinedClickable` при точном попадании по символу аннотации (стандартное поведение Compose text click-handling — внутренний `pointerInput` текста перехватывает клик первым). Внешний `combinedClickable` остаётся обработчиком для остальной площади пузыря (long-press → выделение, tap в режиме выделения → toggle).
6. **Режим выделения меняет семантику `onClick` пузыря**: вне режима выделения `onClick` пузыря — no-op (как сейчас), `onLongClick` — входит в режим выделения и выделяет сообщение. Внутри режима выделения (`selectedMessageIds.isNotEmpty()`) `onClick` любого пузыря — toggle его выделения. `onLongClick` — см. пункт 7 (пересмотрено).
7. **Пересмотрено 2026-09-05** (по прямому указанию владельца продукта после живой проверки — исходная версия ниже отменяет более раннюю формулировку "повторный long-press тоже toggle"): первый long-press по невыделенному сообщению — включает режим множественного выделения и выделяет это сообщение (как в п.6). **Повторный long-press по уже выделенному сообщению — включает обычное системное текстовое выделение слова** (курсоры-ручки + контекстное меню Копировать/Выделить всё, через `SelectionContainer`), **не снимая** это сообщение с множественного выделения (оба состояния сосуществуют: сообщение остаётся в `selectedMessageIds`, и при этом активно текстовое выделение слова). Реализация: `Text` сообщения оборачивается в `SelectionContainer` **только когда `isSelected == true`** — пока сообщение не выделено, `SelectionContainer` отсутствует, и `combinedClickable`'s `onLongClick` на внешнем `Box` свободно получает жест (включает выделение); как только сообщение выделено, `SelectionContainer` появляется вокруг того же `Text` и перехватывает следующий long-press для текстового выделения раньше внешнего `combinedClickable` (тот же порядок приоритета "внутренний `pointerInput` первым", что уже описан в п.5 для кликабельных сегментов) — внешний `onLongClick` в этом состоянии становится no-op (не снимает и не переключает выделение сообщения).

## Функциональность

### A. Подсветка поиска (`ConversationsScreen.kt`)

- Новая чистая функция `data/local` или `ui/conversations` (решается в реализации, вероятно `ui/common/TextHighlight.kt` для переиспользования) — `fun highlightedText(text: String, query: String, highlightColor: Color): AnnotatedString`: регистронезависимый поиск всех вхождений `query` в `text`, оборачивает найденные диапазоны `SpanStyle(background = highlightColor)` (или `fontWeight = FontWeight.Bold`, решается по факту визуальной проверки — фон читабельнее на разных фонах пузыря/строки). Пустой `query` — возвращает исходный текст без изменений (защита от полного выделения при пустом запросе).
- `SearchResultsList`'s `Text` заменяется на рендер `highlightedText(result.text, uiState.query, ...)`.

### B. Распознавание ссылок/телефонов/OTP (`ThreadScreen.kt`/`MessageBubble`)

- Новая чистая функция `MessageTextSegmentation.kt` (`ui/thread/` или `ui/common/`) — сегментирует `message.text` на `List<TextSegment>` (`sealed class TextSegment { data class Plain(text); data class Link(text, url); data class Phone(text, number); data class Otp(text, code) }`), regex-based:
  - Ссылка: `https?://\S+` (минимально; `www\.\S+` — по факту реализации, если время позволяет).
  - Телефон: последовательность цифр/`+`/пробелов/дефисов длиной ≥7 значащих цифр (общий международный паттерн, не привязан к конкретной стране — проект международный по факту работы с любыми SMS).
  - OTP: отдельно стоящая (границы слова) последовательность из 4-6 цифр, не входящая в диапазон, уже занятый Link/Phone-сегментом (порядок проверки: сначала Link, затем Phone, затем OTP на оставшемся тексте — не пересекаются).
- `MessageBubble` рендерит `message.text` через `buildAnnotatedString` на основе сегментов: `Plain` — обычный текст; `Link`/`Phone` — `SpanStyle` (подчёркивание/цвет ссылки) + `LinkAnnotation.Clickable` с обработчиком, открывающим `DropdownMenu`-подобное контекстное меню (или `AlertDialog`-подобный выбор действия — решается по факту, `DropdownMenu` для консистентности с уже существующим паттерном проекта); `Otp` — `SpanStyle` (подчёркивание/акцентный цвет) + `LinkAnnotation.Clickable`, обработчик которого немедленно копирует код в `ClipboardManager` (без меню) и показывает `Snackbar`/короткий визуальный отклик (решается по факту — минимум, короткий Toast-подобный отклик, чтобы тап не выглядел "ничего не произошло").
- Действия меню: ссылка → `Intent.ACTION_VIEW` (открыть в браузере) / копировать в `ClipboardManager`; телефон → `Intent.ACTION_DIAL` (позвонить) / `Intent.ACTION_SENDTO` с `smsto:` (написать сообщение) / копировать.

#### B.1. Позиционирование меню действий (уточнение владельца продукта, 2026-09-04)

Текущая реализация открывает `DropdownMenu` в позиции по умолчанию (у левого края родительского `Column`, независимо от места тапа) — это признано неудобным. Требуемое поведение: меню открывается **у места тапа по сегменту** (координата пальца), разворачиваясь **сверху вниз, если снизу достаточно места**; если места до низа экрана не хватает — меню разворачивается **снизу вверх** от точки тапа. Реализация: `DropdownMenu`'s `offset`-параметр вычисляется из координаты клика (доступна через `LinkAnnotation.Clickable`'s обработчик не напрямую — потребуется `pointerInput`/`Modifier.pointerInteropFilter`-подобный перехват позиции последнего тапа перед вызовом обработчика ссылки, точный механизм — на этапе реализации, вероятно через `remember`-хранимую последнюю позицию тапа, обновляемую в `Modifier.pointerInput(Unit) { detectTapGestures { offset -> lastTapOffset = offset } }`, наложенный поверх текста) и высоты доступного пространства до нижнего края экрана (`LocalConfiguration`/`LocalView`/`Modifier.onGloballyPositioned` для позиции самого `MessageBubble` в окне) — если `screenHeight - tapY < оценочная высота меню`, меню открывается с отрицательным `y`-offset (вверх от точки тапа) вместо положительного.

- `ThreadUiState` — новое поле `selectedMessageIds: Set<Long> = emptySet()`, вычисляемое свойство `val isSelectionMode: Boolean get() = selectedMessageIds.isNotEmpty()`.
- `ThreadActions` — новые методы `onToggleMessageSelection(messageId: Long)`, `onClearSelection()`, `onDeleteSelectedMessages()`.
- `ThreadViewModel`: `onToggleMessageSelection` — добавляет/убирает id из `selectedMessageIds`; `onClearSelection` — очищает набор; `onDeleteSelectedMessages` — для каждого id в наборе вызывает `repository.deleteMessage(id)` (последовательно, `NonCancellable` уже гарантирован самим `deleteMessage`), затем очищает набор.
- `ThreadScreen`'s `TopAppBar` — условный рендер: при `uiState.isSelectionMode` показывается contextual-версия (заголовок — счётчик `"${selectedMessageIds.size}"`, `navigationIcon` — крестик (`Icons.Default.Close`) вызывающий `onClearSelection`, `actions` — кнопка "Удалить" (`Icons.Default.Delete`) вызывающая `onDeleteSelectedMessages` через `ConfirmDialog` (переиспользуется существующий, текст "Удалить N сообщений?")); иначе — обычная версия как сейчас.
- `MessageBubble` получает `isSelected: Boolean` и `isSelectionMode: Boolean` (оба из `uiState`, вычисляются в `ThreadContent`): визуальный индикатор выделения (например `background`-оверлей акцентного цвета или чекбокс-иконка в углу пузыря — решается по факту визуальной проверки). `combinedClickable`'s `onClick` — если `isSelectionMode`, вызывает `onToggleMessageSelection(message.id)`, иначе no-op (как сейчас); `onLongClick` — всегда вызывает `onToggleMessageSelection(message.id)` (первый long-press вне режима выделения включает режим и выделяет это сообщение). Старый `DropdownMenu`("Удалить")/`showMenu`/`showDeleteConfirm` на уровне отдельного пузыря — удаляется полностью, заменяется путём через contextual TopBar.

## Критерии приёмки

- Поиск с непустым запросом визуально подсвечивает найденную подстроку в каждом результате `SearchResultsList` (регистронезависимо).
- Ссылка в тексте сообщения кликабельна, открывает меню "открыть в браузере"/"скопировать"; телефонный номер — "позвонить"/"написать сообщение"/"скопировать"; отдельное 4-6-значное число — тап немедленно копирует в буфер, без меню.
- Long-press по сообщению вне режима выделения включает режим и выделяет это сообщение; TopAppBar заменяется на contextual (счётчик, крестик, "Удалить"); tap по другим сообщениям в режиме выделения переключает их выделение; "Удалить" в contextual TopBar удаляет все выделенные сообщения через `ConfirmDialog` и возвращает к обычному TopBar.
- Старое поведение (long-press → сразу меню "Удалить" на одно сообщение) — полностью заменено, не оставлено параллельно.
- Автотесты на каждый пункт (unit на `TextHighlight`/`MessageTextSegmentation`, androidTest на видимость подсветки/кликабельность сегментов/цикл выделения-удаления).
- Полный регресс без perf-пакета и `realbackend` зелёный на TECNO LI9.

### Дополнение (уточнение B.1 + правки по итогам живого использования, 2026-09-04)

- **B.1 реализовано**: `MessageBubble` теперь захватывает позицию тапа (`Modifier.pointerInput` на `PointerEventPass.Initial`, не перехватывая клик у `LinkAnnotation`) и вычисляет `DropdownMenu`'s `offset` от точки тапа; направление (вниз по умолчанию/вверх при нехватке места до низа экрана) — через новую чистую функцию `MenuPositioning.kt`'s `menuOpensUpward(tapY, screenHeight, estimatedMenuHeight)`, юнит-тестируемую отдельно (`MenuPositioningTest.kt`, 3 теста). Визуальная проверка позиционирования на реальном устройстве не выполнена в этой сессии (см. общий блокер живой проверки выше) — сама логика направления протестирована юнитом.
- **OTP через дефис**: по замечанию владельца продукта ("коды шестизначные иногда отправляются через тире типа 204-503") — `otpRegex` в `MessageTextSegmentation.kt` расширен на `\b\d{1,3}-\d{1,3}\b` с фильтром по суммарному числу цифр (4-6), чтобы не подхватывать случайные короткие дефисные последовательности вне диапазона. `TextSegment.Otp.code` теперь копирует только цифры (дефис вырезается) — вставка кода в форму логина не должна включать разделитель. Юнит-тест добавлен.
- **Область тапа для выделения расширена**: по замечанию пользователя ("сейчас чтобы выделить надо кликнуть именно по самому сообщению — поменять чтобы можно было кликать по всей полосе") — `combinedClickable` перенесён с `Column` (сам пузырь) на родительский `Row` (вся строка на всю ширину экрана). Это вскрыло реальный баг с merged semantics tree (см. spec 0032's "Результаты" и `docs/Metrics.md`), исправлено `useUnmergedTree = true` в затронутых тестах.
- Полный регресс `:app:connectedDebugAndroidTest` на TECNO LI9 (устройство отошло от зависания в ходе этой же сессии) — **161/161 зелёный**, включая все перечисленные правки. Статус спеки повышается до **`Implemented`** — открытый пункт остаётся только чисто визуальная демонстрация (не функциональная) позиционирования меню и подсветки поиска на реальном экране.

### Дополнение 2 (визуальная доработка выделения + фикс позиционирования меню, 2026-09-04)

- **Подсветка выделения на всю ширину без горизонтальных отступов**: по замечанию владельца продукта ("подсвечиваться выделенные элементы тоже должны по всей полосе... два выделенных подряд сообщения не имеют промежутков между выделениями") — `background`(при `isSelected`) и `combinedClickable` перенесены на самый внешний `Box`, **до** существующего верхнего паддинга группировки (`isFirstInGroup ? 8dp : 2dp`, спека 0029, не тронут) — то есть заливка занимает всю выделенную под строку область целиком, включая её собственный верхний отступ. Поскольку элементы `LazyColumn` всегда примыкают друг к другу без зазора между собой, заливки двух подряд выделенных сообщений касаются друг друга автоматически — без какой-либо "умной" логики сравнения с соседним сообщением (первая реализация с `isSelectionMergedWithPrevious` была написана и затем сознательно отменена по прямому указанию пользователя как избыточная — см. историю чата; после отмены `MessageGrouping.kt`/`MessageGroupingTest.kt` не содержат следов этой функции, проверено). Между сообщением и разделителем-датой (спека 0032) заливки не будет — `DateSeparatorRow` не участвует в этой логике вообще, отдельный элемент списка. Сам пузырь получил постоянный маленький вертикальный отступ (`padding(vertical = 2.dp)`) от краёв заливки — те самые "маленькие отступы сверху/снизу от сообщения".
- **Фикс позиционирования меню действий у тапа (B.1)**: обнаружена и исправлена реальная причина, почему меню открывалось чуть выше/ниже пальца — `DropdownMenu`'s `offset` считается относительно якоря (`Column`-пузыря, внутри которого он вызван), а не относительно `Box` с текстом, где захватывался тап; локальные координаты тапа внутри `Box` не учитывали собственный `padding(12.dp)` пузыря. Исправлено: теперь захватываются в window-координатах и позиция тапа, и позиция самого `Column`-якоря (оба через `onGloballyPositioned`), а в `DropdownMenu.offset` передаётся их разница — корректно независимо от того, какие паддинги стоят между ними.
- Полный регресс `:app:connectedDebugAndroidTest` на TECNO LI9 — **161/161 зелёный** после обеих правок. Самостоятельный код-ревью (без субагента) не выявил проблем в порядке модификаторов/математике координат; единственный отмеченный (не блокирующий, согласован дизайном) косметический эффект — заливка выделения "залезает" в 8dp-отступ начала новой группы отправителя, если выделенное сообщение — первое в новой группе; это ожидаемо и не является багом.

### Дополнение 3 (диагностика "множественное выделение не работает" + пересмотр п.7, 2026-09-05)

- **Живая диагностика**: пользователь сообщил, что множественное выделение не работает. Прямая проверка на TECNO LI9 (адб: long-press по обычному тексту, long-press точно по подсвеченному OTP/дате-сегменту, тап по второму сообщению, диалог удаления, отмена) показала, что **весь флоу множественного выделения работает корректно** — гипотеза о конфликте `LinkAnnotation` в `Text` с внешним `combinedClickable` не подтвердилась.
- **Реальная причина жалобы** (выяснено через `AskUserQuestion`): пользователь имел в виду не множественное выделение сообщений, а **обычное системное текстовое выделение слова** (курсоры-ручки + меню Копировать), которое пункт 7 спеки изначально осознанно выносил из скоупа. Это не баг кода, а расхождение ожиданий с уже принятым (и до этой сессии не пересматриваемым) решением.
- **Пункт 7 пересмотрен по прямому указанию пользователя** (см. текст решения выше, раздел "Допущения и решения"): первый long-press по невыделенному сообщению — включает множественное выделение (без изменений); повторный long-press по уже выделенному — включает обычное текстовое выделение слова через `SelectionContainer`, не снимая сообщение с множественного выделения.
- **Реализация**: `combinedClickable`'s `onLongClick` изменён на `if (!isSelected) onToggleSelection(message.id)` (перестаёт быть toggle, только "включить"); `Text` сообщения оборачивается в `SelectionContainer` только когда `isSelected == true`.
- **Тесты**: новый `ThreadScreenTest.secondLongPressOnAlreadySelectedMessageDoesNotDeselectIt` — два long-press подряд по одному сообщению, проверяет, что оно остаётся в `selectedMessageIds` после второго. Полный класс `ThreadScreenTest` — **15/15 зелёный** на TECNO LI9 (включая новый тест и уже существующий `longPressEntersSelectionModeAndTapTogglesAnotherMessageThenDeleteClearsSelection`, не сломан). Полный `:app:testDebugUnitTest` зелёный, `compileDebugKotlin`/`compileDebugAndroidTestKotlin` чисто.
- **Честно не проверено живым устройством**: сама активация `SelectionContainer`'а (появление курсоров-ручек и системного меню Копировать при повторном long-press) — автотест это не может проверить (Compose test API не даёт способа заассертить состояние выделения текста), а живая проверка в этой сессии заблокирована посторонним экраном "Не является SMS-приложением по умолчанию" (системный гейт, всплывающий заново при перезапуске активности, не связан с этой правкой) — подтверждена автотестом только половина поведения (сообщение не снимается с выделения), вторая половина (реально ли открывается текстовое выделение) — открытый пункт для следующей живой проверки.
