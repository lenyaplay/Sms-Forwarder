# 0004 — Структурированное логирование запросов

**Статус:** Implemented

## Контекст

При ручном E2E-тестировании webhook (Milestone 3, `0003-sms-webhook.md`) понадобилось временное логирование входящих запросов, чтобы продиагностировать `400` от реального Gateway App. Импровизированный `log.Printf` логировал query-string (с `upload_token`) и сырое тело (номер отправителя, текст SMS) на каждый запрос — что при ревью признано нарушением уже принятого критерия приёмки 0003 («секреты не логируются в открытом виде») и убрано перед merge. Вместо разового кода — оформляем логирование как полноценную часть проекта: полезно для будущей отладки (Milestone 4/5/6) и для диагностики в тестах, но с самого начала спроектировано так, чтобы не утекали секреты/PII.

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Формат — структурированный JSON через `log/slog`** (стандартная библиотека Go, без внешних зависимостей) — на будущее (Milestone 7, деплой) это даст парсинг/агрегацию логов без переписывания кода, хотя сейчас достаточно было бы и текстового формата.
2. **Состав полей на уровне `info`:** `method`, `path`, `status`, `duration_ms`, `user_id` (если запрос аутентифицирован через `RequireAuth`; для `POST /webhook` и `POST /auth/*` — отсутствует, т.к. до JWT-аутентификации). Никогда: query-string целиком, тело запроса, значения заголовков `Authorization`/`X-Signature`.
3. **Уровень `debug`** — дополнительно тело запроса и query-параметры, но с явной редакцией известных секретных полей (`upload_token`, `download_token`, `password`, `Authorization`) перед записью в лог — заменяются на `"[REDACTED]"`. Не логирует весь запрос "как есть" бесконтрольно даже в debug — редакция обязательна на обоих уровнях, различается только *объём* полей, не наличие защиты секретов.
4. **Переключение уровня — через `LOG_LEVEL` (env, `debug` | `info`, по умолчанию `info`)**, по аналогии с существующими `PORT`/`DB_PATH`/`JWT_SECRET` в `internal/config`.
5. **Логирование — middleware уровня `handlers`**, оборачивает весь `mux` (как и было в диагностическом варианте), плюс точечный `slog.Debug` внутри `webhookHandler` для тела (после редакции) — не размазывается по каждому хендлеру отдельно.
6. **Логи пишутся в `stdout`** (как и существующий `log.Printf("listening on :8080", ...)` в `cmd/server/main.go`) — отдельного файла/handler'а вывода не заводим, соответствует однопроцессной модели деплоя из `Architecture.md` §6.
7. **`duration_ms` — целое число миллисекунд** (округление вниз через `time.Since(start).Milliseconds()`), не дробное — упрощает грепанье/фильтрацию логов, точность до мс достаточна.
8. **Не покрывается этой спекой:** ротация файлов логов, отправка во внешнюю систему (ELK/Loki и т.п.), request ID / трассировка между сервисами — осознанный backlog, не нужен на этапе с одним инстансом бэкенда.

## API / интерфейс

Не HTTP API, а внутренний пакет `internal/logging`:

```go
func New(level string) *slog.Logger   // level: "debug" | "info" (регистронезависимо), невалидное значение -> "info"
func RedactQuery(rawQuery string) string  // заменяет known-secret параметры (upload_token, download_token) на [REDACTED], остальное — как есть
func RedactJSONBody(body []byte) string   // best-effort: пытается распарсить как JSON-объект и заменить known-secret поля (password, upload_token, download_token) на "[REDACTED]"; если не JSON-объект — возвращает "[REDACTED]" целиком (осторожность по умолчанию)
```

`internal/config.Config` — новое поле `LogLevel string`, `LOG_LEVEL` env, default `"info"`.

`internal/handlers.NewRouter` принимает `*slog.Logger` (или создаёт из `cfg.LogLevel` — деталь реализации) и оборачивает `mux` в middleware, которая на каждый запрос:
- на `info`: одна запись после обработки — `method, path, status, duration_ms, user_id?`.
- на `debug`: дополнительно `query` (через `RedactQuery`) в той же записи; для `POST /webhook` отдельная `slog.Debug` запись с `body` (через `RedactJSONBody`) до вызова сервиса.

## Модель данных

Нет изменений в БД.

## Сценарии использования

1. Обычная эксплуатация (`LOG_LEVEL` не задан → `info`) — в логах видно, какие эндпоинты дёргают, коды ответов, задержки, без единого секрета или текста SMS.
2. Разработчик локально выставляет `LOG_LEVEL=debug` (например, повторяя E2E из `0003`) — видит query и тело запроса с редакцией токенов, достаточно для диагностики формата payload от Gateway App (как в реальном инциденте, который и породил эту спеку).
3. В тестах (`internal/handlers/*_test.go`) можно перенаправить `slog.Logger` в буфер и проверить, что при `debug` секретные поля не попадают в вывод в открытом виде — тест-предохранитель от повторения инцидента.

## Критерии приёмки

- На `info` (по умолчанию) в логе есть `method`, `path`, `status`, `duration_ms` на каждый запрос; `user_id` присутствует для аутентифицированных запросов и отсутствует для `POST /webhook`/`POST /auth/*`.
- На `info` query-string и тело запроса никогда не появляются в логе ни в каком виде.
- На `debug` query-string присутствует, но `upload_token`/`download_token` в ней заменены на `[REDACTED]`.
- На `debug` тело `POST /webhook` присутствует в отдельной записи, но `password` (если случайно попадёт в JSON), `upload_token`, `download_token` — редактированы; если тело — не JSON-объект (невалидный JSON), логируется `[REDACTED]` целиком, а не сырые байты.
- `LOG_LEVEL=debug`/`LOG_LEVEL=info`/не задан/невалидное значение — обрабатываются (`info` — дефолт и fallback для невалидного).
- Ни при каком уровне заголовки `Authorization` и `X-Signature` не попадают в лог.

## Тесты

- `internal/logging`: `New` (уровень debug/info/невалидный → default), `RedactQuery` (с `upload_token`, с несколькими параметрами, без секретов — не трогает), `RedactJSONBody` (валидный JSON с `password`/`upload_token`, JSON без секретных полей — не трогает остальные поля, невалидный JSON — `[REDACTED]` целиком, пустое тело).
- `internal/handlers`: тест на `info`-уровне — перенаправить логгер в `bytes.Buffer`, дёрнуть `POST /webhook` с телом, содержащим `upload_token` в query и номер телефона в теле, убедиться что в буфере нет ни токена, ни номера, ни текста SMS. Тест на `debug`-уровне — то же самое, но убедиться, что `[REDACTED]` присутствует вместо токена, а остальные (не секретные) поля тела — видны.
