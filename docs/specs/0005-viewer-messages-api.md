# 0005 — Список сообщений устройства (viewer API)

**Статус:** Implemented

## Контекст

Milestone 4 (`docs/Roadmap.md`). Первый пункт этапа («список устройств, доступных пользователю») уже покрыт `GET /devices` из `0002-devices-tokens.md` (см. допущение 7 той спеки) — отдельного эндпоинта заводить не нужно, дублирование запрещено документационным инвариантом (`CLAUDE.md`). Эта спека закрывает второй пункт: чтение сообщений (`messages`, Milestone 3) владельцем и viewer'ами устройства, с пагинацией — список потенциально не ограничен и будет расти постоянно (входящие SMS).

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Эндпоинт — `GET /devices/{id}/messages`**, а не отдельный неймспейс — согласуется с существующей вложенностью ресурсов устройства (`/devices/{id}/download_tokens` и т.п. из 0002).
2. **Пагинация — cursor-based по `id`** (`before_id`, `limit`), не `limit/offset`: сообщения непрерывно вставляются с ростом `id`, offset-пагинация в такой ленте пропускает/дублирует записи при параллельной вставке новых SMS между запросами страниц. `id` в SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` монотонно растёт, поэтому пригоден как курсор.
3. **Сортировка — по `id` по убыванию** (новые сначала), т.к. `id` монотонен и соответствует порядку получения на сервере (в отличие от `sent_stamp`/`received_stamp`, которые из недоверенного источника — Gateway App — и не гарантированно монотонны).
4. **Фильтры в этой версии — только диапазон дат** (`since`/`until`), фильтруются **по `created_at`, а не по `received_stamp`**: `received_stamp` — сырая строка, присланная Gateway App без валидации формата (может быть Unix-эпохой в мс или отсутствовать вовсе — см. `flexibleString` и допущение 5 в `0003-sms-webhook.md`), поэтому сравнение с RFC3339-датой бессмысленно. `created_at` — серверная метка времени вставки записи (`TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`), монотонна вместе с `id`, за счёт чего диапазонный фильтр и cursor-пагинация по `id` не расходятся. Остальные фильтры (поиск по тексту/sender) — уже в Backlog (Milestone 8, `docs/Roadmap.md`), осознанно не входят.
5. **Доступ:** владелец устройства — всегда; viewer — только если есть **активный** `viewer_binding` на это устройство: не отозванный (запись не удалена — при отзыве `download_token` в 0002 связанные `viewer_bindings` удаляются, значит "не отозван" эквивалентно "запись существует") **и** соответствующий `device_download_tokens.expires_at` либо `NULL`, либо в будущем на момент запроса. Решение подтверждено владельцем продукта: при первичной реализации был обнаружен разрыв — `DeviceService.GetDevice`/`ListViewerDevices` (0002/Milestone 2) на тот момент не перепроверяли TTL токена при чтении, только при создании нового `viewer_binding`. По итогам явного решения владельца продукта эта проверка добавлена **во всё API** (`GET /devices`, `GET /devices/{id}`, и этот эндпоинт), а не только здесь — см. правку допущения 7 в `0002-devices-tokens.md`. `ListViewerDevices` (переиспользуется и `DeviceService.GetDevice`, и напрямую этой фичей) теперь джойнит `device_download_tokens` и фильтрует по `expires_at`.
6. **Лимит на `limit`:** от 1 до 100, по умолчанию 50 — защита от чрезмерных выборок без отдельного rate-limiting (тот — в Milestone 7).
7. **404 vs 403** для устройства без отношения к пользователю — как и везде в 0002/0003: `404`, чтобы не палить существование чужого устройства.
8. **Формат ответа сообщения** — все поля `messages` кроме `body_hash` (внутренний технический дедуп-ключ, не нужен потребителю API).

## API / интерфейс

### `GET /devices/{id}/messages`

Требует `Authorization: Bearer <access_token>`. Доступно владельцу устройства или пользователю с активным `viewer_binding` (см. допущение 5).

Query-параметры:
- `limit` — опционально, `1..100`, по умолчанию `50`.
- `before_id` — опционально, `int64`; если передан — возвращаются сообщения с `id < before_id` (страница "старше этой").
- `since` — опционально, RFC3339 timestamp; если передан — только сообщения с `created_at >= since`.
- `until` — опционально, RFC3339 timestamp; если передан — только сообщения с `created_at <= until`.

Ответ `200 OK`:
```json
{
  "messages": [
    {
      "id": 42,
      "device_id": 1,
      "sender": "+1234567890",
      "text": "...",
      "sent_stamp": "2026-08-25T12:00:00Z",
      "received_stamp": "2026-08-25T12:00:01Z",
      "sim": "1",
      "created_at": "2026-08-25T12:00:02Z"
    }
  ],
  "next_before_id": 17
}
```
`sender`/`text` всегда присутствуют (обязательны при приёме webhook, см. `0003-sms-webhook.md`, `ErrMissingSender`/`ErrMissingText`); `sent_stamp`/`received_stamp`/`sim` — `null`, если соответствующее поле не было передано в webhook. `next_before_id` — `id` последнего (самого старого) элемента текущей страницы, для запроса следующей; отсутствует (`null`), если сообщений вернулось меньше `limit` (страница последняя).

Ошибки:
- `400` — `limit` вне диапазона `1..100`; `before_id` не число; `since`/`until` не парсятся как RFC3339; `since > until`.
- `404` — устройства нет, либо у пользователя нет к нему отношения (нет `owner`/активного `viewer_binding`).

## Модель данных

Нет изменений в схеме БД. Возможна новая миграция с индексом под пагинацию — см. ниже.

Запрос к `internal/storage`: `SELECT ... FROM messages WHERE device_id = ? [AND id < ?] [AND created_at >= ?] [AND created_at <= ?] ORDER BY id DESC LIMIT ?`.

Новая миграция `0004_messages_pagination_index.up.sql` (номер следующий по порядку файлов миграций, не по номеру спеки — предыдущая спека 0004 логирования не меняла схему; проверено через `query-validation`):
```sql
DROP INDEX idx_messages_device_id;
CREATE INDEX idx_messages_device_id_id ON messages (device_id, id);
```
Down (`0004_messages_pagination_index.down.sql`):
```sql
DROP INDEX idx_messages_device_id_id;
CREATE INDEX idx_messages_device_id ON messages (device_id);
```
Составной индекс `(device_id, id)` заменяет прежний `idx_messages_device_id` целиком (тот стал избыточным префиксом) и вдобавок эффективно обслуживает `ORDER BY id DESC LIMIT ?` — SQLite обходит B-tree в обратном порядке без отдельной сортировки. Отдельный индекс под `created_at` не заводится: диапазонный фильтр применяется уже поверх суженной по `device_id` выборки, а объём данных (личная история SMS одного устройства) мал — добавлять его сейчас было бы преждевременной оптимизацией (см. Backlog).

Проверка доступа viewer'а (допущение 5) выполняется существующим `DeviceService.GetDevice`, который теперь (см. правку 0002) сам делегирует в обновлённый `storage.ListViewerDevices` с join на `device_download_tokens` и фильтром по `expires_at`.

## Сценарии использования

1. Владелец или viewer открывает ленту устройства → `GET /devices/{id}/messages` без параметров → последние 50 сообщений, самые новые сверху.
2. Приложение подгружает более старые сообщения (скролл вниз) → `GET /devices/{id}/messages?before_id=<next_before_id из предыдущей страницы>`.
3. Пользователь фильтрует историю за конкретный день → `since`/`until`.
4. Viewer, чей `download_token` истёк по TTL (даже без явной ревокации владельцем), теряет доступ к сообщениям устройства — `GET /devices/{id}/messages` → `404` (см. допущение 5); так же он пропадает и из `GET /devices` этого пользователя. Явная ревокация (`DELETE .../download_tokens/{token_id}` из 0002) даёт тот же результат немедленно, не дожидаясь TTL.
5. Запрос к чужому устройству без каких-либо прав → `404`.

## Критерии приёмки

- Владелец получает сообщения своего устройства; viewer с активным (не отозванным и чей `download_token` ещё не истёк) `viewer_binding` — тоже.
- Пользователь без отношения к устройству (не owner, нет `viewer_binding`) → `404`.
- Сообщения отсортированы по `id` по убыванию (новые первыми).
- `before_id` корректно возвращает следующую страницу без пропусков и дублей при параллельной вставке новых сообщений между запросами страниц.
- `next_before_id` отсутствует, когда сообщений меньше `limit` (последняя страница).
- `since`/`until` фильтруют по `created_at`; `since > until` → `400`.
- `limit` вне `1..100` → `400`; невалидный `before_id`/`since`/`until` → `400`.
- `body_hash` никогда не попадает в ответ API.
- После явного отзыва `download_token` (0002) viewer, подключённый через него, получает `404` на этот эндпоинт.
- После истечения `download_token` по TTL (без явной ревокации) viewer, подключённый через него, тоже получает `404` на этот эндпоинт.

## Тесты

- `internal/storage`: `ListMessagesForDevice` — пагинация (`before_id`, `limit`, поведение на пустой странице/последней странице), фильтр `since`/`until` (включая границы), сортировка по `id DESC`, изоляция по `device_id`. `ListViewerDevices` — исключает `viewer_binding`, чей `download_token` истёк по TTL (регрессия к правке допущения 7 в 0002).
- `internal/services`: `MessageService.ListMessages` — авторизация через `DeviceService.GetDevice` (owner/viewer/ни то ни другое → `ErrDeviceNotFound`), делегирование фильтров и пагинации в storage, `since > until` → `ErrInvalidDateRange`.
- `internal/handlers`: HTTP end-to-end — владелец видит все сообщения; viewer с активным binding — видит; viewer без отношения — `404`; пагинация по нескольким страницам без дублей/пропусков; фильтры по датам; невалидные query-параметры → `400`; `body_hash` отсутствует в JSON-ответе; отзыв токена → `404` для этого viewer'а; истечение токена по TTL (без ревокации) → `404` для этого viewer'а.
