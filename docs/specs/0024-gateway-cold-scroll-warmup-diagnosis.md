# 0024 — Диагностика лага именно первых скроллов после холодного старта (гипотеза «прогрева») (Android Gateway App)

**Статус:** Implemented — гипотеза прогрева подтверждена на уровне «внутри прогона» уверенно и воспроизводимо (см. «Результаты»). Конкретная причина концентрации в первом дециле и Сценарий D **не переносятся в отдельный Milestone** — продолжаются в рамках этого же Milestone 23 как отдельная спека (следующая по номеру), см. `docs/roadmaps/Roadmap 2.md`, Milestone 23 «Фаза 2».

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0024-requirements-doc.md](../requirements/0024-requirements-doc.md) и [docs/requirements/0024-analysis-brief.md](../requirements/0024-analysis-brief.md) — эта спека их источник истины по деталям реализации.*

## Контекст

Продолжение [0023-gateway-scroll-jank-isolation.md](0023-gateway-scroll-jank-isolation.md) (Milestone 22, Implemented-partial): протокол «5 прогонов, сброс позиции скролла на одной и той же композиции» показал все слои (0-3, синтетика) статистически неотличимыми (~2.8% janky). Владелец продукта указал на методологическую дыру (2026-09-02): реальный лаг концентрируется именно в **первых** скроллах после холодного старта и заметно уменьшается при повторной прокрутке туда-сюда — у системного SMS-приложения такого «прогрева» нет. 5 прогонов Milestone 22 сами по себе уже являются тем «прокручиванием туда-сюда», которое всё улучшает — усреднённые числа могли уже отражать прогретое состояние, а не холодный старт.

Второе уточнение владельца продукта: даже «первый прогон целиком» — слишком грубая единица. Джанк может концентрироваться в первых ~10% кадров одного прогона; единое janky%-число на весь прогон это маскирует так же, как усреднение по прогонам маскировало разницу между первым и последующими прогонами.

Сырые данные Milestone 22 (Слой 0) уже дают слабый намёк: `2.94% / 2.74% / 2.74% / 2.78% / 2.74%` — первый прогон выше остальных, но выборка (5 прогонов, все на одной композиции) недостаточна и структурно не может отделить «холодное первое отображение» от «прогретое состояние после N сбросов позиции».

Спека 0023 не переписывается задним числом — эта спека вводит новый, отдельный протокол и новые данные.

## Допущения и решения

1. **10 холодных прогонов на сценарий** (вдвое больше, чем 5 в Milestone 22) — каждый прогон получает полностью свежий `Activity`/композицию, не сброс позиции скролла на старой. Технически: `ComposeTestRule.setContent` можно вызвать один раз за тест-метод (ограничение, найденное в Milestone 22) — значит «свежая композиция на каждый прогон» реализуется как **отдельный `@Test`-метод на каждый прогон** (по аналогии с тем, как Milestone 22 сделал отдельный `@Test`-метод на каждый слой): JUnit гарантированно пересоздаёт `@Rule`-цепочку (включая `ActivityScenarioRule` внутри `createAndroidComposeRule`) заново на каждый тестовый метод — это и даёт настоящий «холодный» запуск, а не искусственную имитацию.
2. **Сценарии, к которым применяется новый протокол** (не все 5 слоёв Milestone 22 — 5 слоёв × 10 прогонов = 50 тест-методов избыточно для проверки гипотезы прогрева): (A) Слой 0 (baseline, синтетика) — минимальный случай; (B) Слой 3 (полный синтетический стек: `Card` + тень + `SwipeToDismissBox`) — максимальный случай из Milestone 22, где эффект прогрева (если есть) должен быть заметнее всего. Если оба сценария покажут одинаковую (или её отсутствие) картину прогрева — этого достаточно для вывода по гипотезе; сценарии 1-2 (только `Card` без `SwipeToDismissBox`) не дублируются отдельно, поскольку Milestone 22 уже показал их статистически неотличимыми от Слоя 0/3 на прогретых данных.
3. **Сегментация — децили по номеру кадра внутри прогона**, как стартовая гранулярность. **Защита от post-hoc data dredging (найдено `query-validation`)**: решение о корректировке гранулярности фиксируется **до** того, как считается или интерпретируется сравнение «ранний vs поздний набор» (Допущение 6) — то есть аналитик смотрит только на форму распределения janky% по 10 стандартным децилям Сценария A (просто визуальный график/таблица «дециль → janky%», без вычисления `compareJank` на этом этапе), решает нужна ли более мелкая гранулярность **только по форме этой кривой** (например: явный, визуально резкий пик в одном-двух первых децилях против плоского хвоста — критерий «резкий» означает, что дециль 1 отличается от медианы децилей 3-10 больше чем на порядок величины, не на проценты), фиксирует решение и обоснование в «Результаты» **одной записью, сделанной до** вычисления итогового сравнения «ранний vs поздний», и не пересматривает гранулярность впоследствии, если итоговое сравнение окажется неожиданным (подтверждающим или опровергающим гипотезу). Если форма кривой не даёт явного повода — гранулярность остаётся децильной без изменений.
4. **`FrameCounter` расширяется**: вместо только `total`/`jank`-счётчиков — список записей `(порядковый номер кадра, isJank: Boolean)`, из которого postfactum вычисляются как агрегированный janky% (для сравнения с Milestone 22), так и janky% по каждому децилю/сегменту.
5. **Системное приложение — через `adb shell dumpsys gfxinfo <package> framestats`**, единственный практичный инструмент для стороннего не-Compose приложения (нет доступа к `ComposeTestRule`/`JankStats` внутри чужого процесса). `framestats` отдаёт сырые per-frame timestamps последних ~120 кадров — при недостаточном окне для 10 прогонов подряд, `framestats` считывается сразу после каждого прогона (не накапливается несколько прогонов без чтения), жест воспроизводится через `adb shell input swipe` (единственный доступный способ ввода для чужого приложения — `performTouchInput` работает только внутри собственного `ComposeTestRule`-процесса).
   **Несопоставимость определений джанка (найдено `query-validation`, признано явно, не скрыто)**: `JankStats.isJank` (используется для Gateway App, Сценарии A/B/D) — это эвристика самой библиотеки `androidx.metrics.performance`, учитывающая не только превышение кадрового бюджета (~16.6ms), но и внутренние детали буферизации/пропуска кадров Android; ручной расчёт по `framestats` (Сценарий C, системное приложение) в лучшем случае — это простое сравнение межкадрового интервала с бюджетом ~16.6ms из сырых `FRAME_TOTAL`-таймингов. Эти два определения **не гарантированно совпадают** по конкретным кадрам. Прямое числовое сравнение «Gateway App X% janky (JankStats) против системного Y% janky (framestats)» в этой спеке используется **только как порядковый ориентир** (показывает ли системное приложение вообще заметный эффект прогрева или нет), а не как строгое количественное сравнение «на сколько именно хуже/лучше» — это ограничение фиксируется в «Результаты» рядом с любым таким сравнением, а не подразумевается молча.
6. **Порог значимости прогрева** — по аналогии с `JankComparison.kt` (Milestone 22): разница среднего janky% между «первым» набором и «поздним» набором должна превышать разброс (min-max) внутри позднего набора, иначе прогрев не считается статистически подтверждённым. Реализуется как переиспользование существующего `compareJank`, а не новая формула.
   **Точное определение «раннего» и «позднего» наборов (найдено `query-validation` — было не специфицировано)**: применяется **на двух независимых уровнях**, оба обязательны и фиксируются в «Результаты» отдельно:
   - **Между прогонами** (Сценарии A/B/D, 10 прогонов каждый, используется агрегированный janky% каждого прогона как единое число): «ранний набор» = прогоны 1-3, «поздний набор» = прогоны 8-10 (первые/последние 3 из 10 — оставляет средние 4 прогона вне сравнения намеренно, как переходную зону, не участвующую ни в одной из двух групп).
   - **Внутри прогона** (по децилям, для каждого прогона отдельно, где 10 деций дают ровно 10 точек): «ранний набор» = дециль 1 (первые 10% кадров прогона), «поздний набор» = децили 6-10 (последняя половина прогона) — асимметрично специально: гипотеза владельца продукта именно про «первые ~10%», не про «первую половину», поэтому ранний набор — узкий (1 дециль), поздний — широкий (5 децилей) как стабильный ориентир «типичного прогретого состояния» этого же прогона.
   Если гранулярность скорректирована по Допущению 3 — эквивалентные пропорции (первые ~10% узко, оставшаяся часть широко) пересчитываются под новую гранулярность и фиксируются явно.
7. **Критерий закрытия Milestone (идентичен Допущению 7 спеки 0023, дословно подтверждён владельцем продукта 2026-09-02)**: Milestone закрывается, если **либо** (a) конкретная причина прогрева найдена и подтверждена с фиксом и цифрами до/после, **либо** (b) полный проход завершён без статистически значимого результата **и** предложен более полезный диагностический инструмент/уточнённая методология + план следующего Milestone.
8. **Перенесённые из Milestone 22 пункты** (реальный `ConversationsScreen` через `MainActivity` с реальной SMS-историей и заранее подтверждённой ролью SMS-приложения по умолчанию; прямой A/B `performTouchInput` vs `adb shell input swipe` на одном экране) — включаются как сценарий (C), если объём работы в рамках этого захода позволяет; если нет — явно переносятся в следующий Milestone с фиксацией причины, не молчаливо теряются.

## Функциональность

### A. Расширенный `FrameCounter` и сегментация

- `FrameCounter` дополняется хранением последовательности `(frameIndex: Int, isJank: Boolean)` — либо через `MutableList`, либо через параллельные массивы, в зависимости от того, что проще для последующего децильного разбиения. Существующие `total`/`jank`/`jankyPercent` сохраняются для обратной совместимости с логикой Milestone 22 (агрегированное сравнение слоёв).
- Новая чистая функция (по аналогии с `JankComparison.kt`, тестируемая unit-тестом) — принимает последовательность `(frameIndex, isJank)` и число сегментов, возвращает `List<Double>` (janky% на каждый дециль/сегмент). Имя и точная сигнатура фиксируются в реализации, документируются здесь по факту.

### B. Холодные прогоны (Сценарии A и B)

- Для каждого сценария — 10 отдельных `@Test`-методов (`scenarioA_coldRun01`…`scenarioA_coldRun10`, аналогично для B), каждый вызывает `composeRule.setContent { ... }` ровно один раз (гарантированно свежая Activity/композиция благодаря JUnit `@Rule`-пересозданию между тест-методами), выполняет фиксированную последовательность свайпов (тот же `performTouchInput { swipeUp() }`×`SWIPES_PER_RUN`, что в Milestone 22, для сравнимости), собирает per-frame данные через `JankStats`, логирует агрегированный + подецильный janky%.
- Порядок выполнения — `MethodSorters.NAME_ASCENDING` (та же техника, что в Milestone 22), результаты каждого прогона копятся в `companion object`-состоянии для итоговой сводки в последнем прогоне сценария.
- **Оценка времени выполнения** (честно фиксируется до старта): 10 прогонов × полный релонч Activity/композиции на сценарий, ×2 сценария — заметно дольше 5 прогонов Milestone 22 (переиспользовавших композицию); ожидаемое время фиксируется по факту первого прогона в «Результаты», не оценивается заранее вслепую.

### C. Системное приложение (сравнение)

- `adb shell dumpsys gfxinfo <package> reset` перед каждым из 10 прогонов, `adb shell input swipe` (фиксированные координаты/длительность, воспроизводимые вручную или скриптом), `adb shell dumpsys gfxinfo <package> framestats` сразу после — извлекаются per-frame timestamps. Janky-кадр для этого сценария определяется просто как межкадровый интервал (`FRAME_TOTAL`) больше ~16.6ms из сырых таймингов `framestats` — **не идентичное определение**, что `JankStats.isJank` использует для Gateway App (см. Допущение 5, «Несопоставимость определений джанка») — числа не складываются в единую сквозную шкалу с Сценариями A/B/D, только в порядковый ориентир «есть эффект прогрева или нет».
- Выполняется вручную/скриптом (Bash/PowerShell + `adb`), не через `ComposeTestRule` (недоступен для чужого приложения) — результат фиксируется в спеке как таблица, не как автотест (аналогично тому, как Milestone 21/22 фиксировали внешние `dumpsys`-замеры системного приложения текстом, не тестом).

### D. Реальный экран (Сценарий C, перенесённый из Milestone 22, если объём позволяет)

- Тот же протокол (10 холодных прогонов, децили) применяется к реальному `ConversationsScreen` через `MainActivity` (`@HiltAndroidTest`, `createAndroidComposeRule<MainActivity>()`, по образцу `DeliveryResetActivityTest.kt`) — **с явно подтверждённой ролью SMS-приложения по умолчанию и реальной SMS-историей на устройстве перед прогоном** (условие, упущенное в Milestone 22 для Слоя 4 — не повторяется).
- Прямой A/B `performTouchInput` vs `adb shell input swipe` на этом же экране — если время/объём позволяют в рамках этого Milestone, иначе явно переносится дальше с фиксацией причины.

- Если Сценарий C (реальный экран) не реализован в рамках этого захода — явно зафиксировано как перенесённый пункт с причиной, не потеряно молча.

Зелёные.

Переиспользует `IsolatedScrollTestScreen`/`syntheticRows`/константы из `ScrollJankLayerTest` (сделаны `internal`) и общий `FrameCounter` (расширен: хранит `(frameIndex, isJank)`, вынесен из `ScrollJankLayerTest` в top-level `internal class` того же файла, используется обоими тест-классами).

## Результаты

Прогон на TECNO LI9, 2026-09-02, `:app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=...ColdScrollWarmupTest` — 20/20 методов зелёные (10 холодных прогонов × 2 сценария).

**Решение по гранулярности (Допущение 3), зафиксировано ДО вычисления early/late-сравнения**: форма кривой Сценария A (см. таблицу ниже) оказалась предельно резкой — дециль 1 у КАЖДОГО из 10 прогонов равен 25.00%, децили 2-10 у каждого прогона равны ровно 0.00% (разброс 0.00 по всем 10 прогонам на каждой позиции) — джанк буквально не встречается нигде, кроме первого дециля. Это далеко превышает критерий «на порядок величины» из Допущения 3. Гранулярность оставлена децильной как есть (не измельчена дальше в рамках этого захода) — более тонкое разбиение именно внутри дециля 1, чтобы локализовать конкретный кадр, зафиксировано как открытый вопрос/предложение для следующего Milestone, а не выполнено здесь задним числом (чтобы не создавать post-hoc data dredging: гранулярность решена один раз, до расчёта сравнения, и не пересматривается).

### Вывод по гипотезе прогрева

- **Внутрипрогонная концентрация джанка в первых ~10% кадров — подтверждена уверенно и воспроизводимо**: в обоих сценариях, во всех 20 холодных прогонах без единого исключения, весь джанк (100% janky-кадров каждого прогона) находится строго в первом дециле; децили 2-10 идеально чистые (0.00%, нулевой разброс). Это именно то явление, о котором говорил владелец продукта во втором уточнении.
- **Межпрогонный эффект (первые 3 прогона против последних 3) — НЕ подтверждён**: направления противоположны между Сценарием A (WORSE) и Сценарием B (BETTER), а сама разница (0.03-0.05 процентных пункта) сопоставима с шагом квантования при малом числе кадров на прогон (~40) — при таком шаге 1 кадр меняет агрегированный процент на ~2.5 п.п., поэтому наблюдаемая разница в 0.03-0.05 п.п. физически не может быть результатом целого лишнего/недостающего джанк-кадра и, вероятнее всего, является усреднением по прогонам с/без ровно одного джанк-кадра в неглавных сегментах, не имеет отношения к «прогреву». **Честно зафиксировано как QA-находка**, не скрыто.
- Причина концентрации в первом дециле **не исследована в этом заходе** (не идентифицирован конкретный кадр/механизм — холодная композиция, JIT, что-то ещё) — фикса с цифрами до/после нет.
- Сценарий D (реальный экран через `MainActivity`) **не выполнен в этом заходе** — перенесён (см. «Открытые вопросы») по причине объёма: 20 холодных прогонов на синтетике + замер системного приложения уже заняли отдельный полный проход, третий полноценный протокол (10 прогонов на реальных данных с подтверждением роли SMS-приложения) требует отдельного захода, чтобы не размывать проверку уже полученного результата.

**Критерий закрытия этой спеки (Допущение 7) — вариант (b)**: конкретной причины с фиксом нет, но получен уверенный, воспроизводимый, статистически чистый (нулевой разброс) результат — точная локализация эффекта до одного дециля (~10% первых кадров прогона) — вместе с предложенным следующим шагом (см. «Открытые вопросы»). Сама Milestone 23 при этом **не закрывается** — по решению владельца продукта (2026-09-02) причина уже достаточно конкретизирована, чтобы продолжать поиск фикса в рамках той же Milestone, а не откладывать в отдельную будущую Milestone; следующая спека (требования собираются отдельно) реализует конкретное предложение из «Открытых вопросов» ниже.

## Открытые вопросы / Backlog

- Точное число кадров, укладывающееся в окно `framestats` (~120) — на практике не стало проблемой: 3 свайпа системного приложения дали 167-172 кадра, что уже близко к границе окна; при добавлении свайпов в будущих заходах это стоит перепроверить.
- **Перенесено на Milestone 24**: Сценарий D (реальный `ConversationsScreen`/`MainActivity`, реальная SMS-история, заранее подтверждённая роль SMS-приложения по умолчанию) — не выполнен в этом заходе, причина зафиксирована в «Результаты» (объём: 20 холодных прогонов + замер системного приложения уже заняли полный проход).
- **Предложение для Milestone 24** (конкретизация находки этого Milestone, а не расплывчатое «продолжить»): локализовать джанк внутри самого первого дециля — либо более мелкой сегментацией (например по отдельным кадрам, не по децилям) именно первых ~10% кадров каждого холодного прогона, либо прямым логированием того, что происходит на первых нескольких кадрах после `setContent` (recomposition count, время первого `LazyColumn`-layout, JIT-компиляция через `dumpsys jit`/systrace) — чтобы перейти от «эффект есть и он в начале» к «эффект вызван конкретно X» и получить фикс с цифрами (Допущение 7, вариант a). Заодно выполнить перенесённый Сценарий D тем же уточнённым протоколом.
- Межпрогонный (между-раннами) эффект признан неподтверждённым при текущем разрешении измерения (~40 кадров/прогон → шаг квантования ~2.5 п.п.) — если он всё же интересен, увеличение числа свайпов на прогон (больше кадров → тоньше шаг) было бы предпосылкой для повторной проверки, а не большее число прогонов.
- `FrameSegmentation.segmentJankyPercents` отдаёт лишний кадр остатка ПЕРВЫМ сегментам при делении не нацело — на реальном прогоне (40 кадров / 10 децилей) это не сработало (делится ровно), но при другой длине прогона/гранулярности стоит иметь в виду: это может слегка смещать сравнение «ранний vs поздний» в пользу ранних сегментов (у них на 1 кадр больше знаменателя) — найдено при `peer-review-template`, не исправлялось, так как не проявилось на фактических данных и не является дефектом самой функции (документированное, детерминированное поведение).
