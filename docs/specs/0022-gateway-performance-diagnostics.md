# 0022 — Измеримая диагностика производительности, инструментарий по требованию, быстрый холодный старт (Android Gateway App)

**Статус:** Implemented (частично — см. «Критерии приёмки»/«Открытые вопросы»: инструментарий и фикс холодного старта сданы полностью и живо проверены; конкретная причина лага скролла на реальных данных устройства осталась не найдена, честно задокументирована как нерешённая)

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0022-requirements-doc.md](../requirements/0022-requirements-doc.md) и [docs/requirements/0022-analysis-brief.md](../requirements/0022-analysis-brief.md) — эта спека их источник истины по деталям реализации.*

## Контекст

Запрошено напрямую владельцем продукта (2026-08-29, зафиксировано в `docs/roadmaps/Roadmap 2.md`, Milestone 21): после фикса нестабильных лямбд в списке диалогов (Milestone 18) подлагивание скролла на живом устройстве сохранилось. Нужны цифры вместо гипотез, и постоянный (но не всегда включённый) инструментарий измерения — не разовый профилировочный прогон.

Владелец продукта уже вручную снял baseline (`adb shell dumpsys gfxinfo` на списке диалогов, TECNO LI9): **55.56% janky-кадров (15/27), 90p 150ms/95p 250ms** при бюджете кадра ~16.6ms, GPU-время в норме (6–9ms) — узкое место на UI-потоке, не на GPU.

Анализ кода этой сессии (не предположение) подтвердил:
- `ConversationsScreen.kt` — `LazyColumn` со строкой `SwipeToDismissBox` вокруг `Card` (дефолтная M3-тень); `ConversationsViewModel.kt` пересобирает `List<ConversationUi>` на **каждую** эмиссию `Flow` из `observeConversations`, без `distinctUntilChanged()`.
- `GatewayApp.kt` — нулевая perf-инфраструктура, только `ContentObserver` на `content://sms`.
- `ConversationsUiState` не различает «`Flow` ещё не эмитил» и «`Flow` эмитил пустой список» — оба состояния выглядят как `conversations = emptyList()`, поэтому холодный старт всегда на короткое время показывает «Нет сообщений», даже если данные уже есть в Room.
- `SmsDeliverReceiver.onReceive` — запись в Room (`messageRepository.storeAndForward`) всегда **предшествует** показу уведомления (awaited, последовательно) — значит пункт про push-уведомление (см. ниже, п.4) не отдельная гонка, а то же самое следствие пустого-состояния-бага.

## Допущения и решения

1. **On-demand-инструментарий — один общий переключатель**, не набор точечных: раздел «Диагностика» на экране «Настройки», один `Switch` разом включает и `JankStats`-замер Compose-экранов, и таймеры длительности фоновых операций. Работает на любой сборке (не debug-only гейт) — осознанный пользовательский инструмент, не dev-заглушка (решение владельца продукта).
2. **Куда пишутся метрики — оба места**: logcat (тег `PerfMonitor`, `Log.i`) и файл в app-private storage (`context.filesDir/perf/perf-log.txt`, дозапись, без ротации в рамках этой спеки — личный масштаб использования, размер файла не риск).
3. **Порог «лаги скролла исправлены» — выводится из сравнения с системным SMS-приложением**, не назначается заранее числом. В рамках реализации снимается `dumpsys gfxinfo` системного приложения (`com.transsion.smartmessage` на TECNO LI9) на сопоставимом списке диалогов, и найденное число фиксируется здесь по факту замера (см. «Критерии приёмки» — плейсхолдер до реализации, обновляется вместе со статусом `Draft → Implemented`).
4. **Исследование мгновенного отображения списка в системном приложении**: сначала внешние легальные замеры (`adb shell am start -W`, `dumpsys`, собственные логи Gateway App). Если этого недостаточно для понимания механизма — статический анализ APK системного приложения (`apktool`/`jadx`), **разрешено владельцем продукта явно** (2026-09-02) исключительно для изучения применённых техник (интероперабельность/обучение) — результат идёт в эту спеку как текстовое описание техники, никакой код или ресурсы из чужого APK не копируются и не адаптируются.
5. **Холодный старт: пустой экран без текста** (не спиннер) до первой эмиссии `Flow` — рабочее решение аналитика, мотивация: спиннер сам может мигнуть на быстрых устройствах, создавая новое визуальное дребезжание вместо старого. **Подлежит живой перепроверке на устройстве** в рамках реализации (шаг 10 плана) — если ощущается как регресс, фиксируется как открытый вопрос в этой же спеке, не меняется втихую.
6. **Пункт про push-уведомление (Roadmap п.4) не отдельная фича** — покрывается тем же фиксом, что и общий кейс холодного старта (п.5), поскольку Room-запись уже гарантированно предшествует показу уведомления (см. «Контекст»). Отдельного кода не требуется.
7. **Фиксы лагов скролла — только измеренные**: каждый кандидат (`distinctUntilChanged()` на Flow, стоимость `SwipeToDismissBox`, стоимость тени `Card`) применяется по одному, с замером `dumpsys gfxinfo` до/после через реальный `PerfMonitor`. Отклонённые гипотезы (не давшие измеримого эффекта) фиксируются здесь же, а не молча отбрасываются.

## Функциональность

### A. On-demand perf-инструментарий

- Новая зависимость `androidx.metrics:metrics-performance:1.0.0-beta01` в `app/build.gradle.kts` (через `libs.versions.toml`) — версии `1.0.0`/`1.0.0-beta02` требуют `compileSdk 35`, проект на `compileSdk 34` (см. Constraints в `docs/requirements/0022-analysis-brief.md`); `beta01` — последняя, совместимая с текущим `compileSdk` без отдельного апгрейда.
- Новый `data/perf/PerfMonitor.kt` (Hilt `@Singleton`):
  - `fun attachTo(window: Window)` — регистрирует `JankStats` через `JankStats.createAndTrack(window) { frameData -> ... }`, логирует кадры с `frameData.isJank == true`. **Технический нюанс, найденный только на реальном устройстве** (не предполагался в плане): `JankStats.createAndTrack` требует уже существующий `DecorView` (`window.peekDecorView() != null`) — вызов из `MainActivity.onCreate()` до `setContent {}` крашил приложение на старте (`IllegalStateException`, воспроизведено на TECNO LI9 при первом инструментированном прогоне). Исправлено вызовом внутри `setContent { SideEffect { perfMonitor.attachTo(window) } }` — `SideEffect` гарантированно выполняется уже после того, как Compose создал `DecorView`.
  - `suspend fun <T> measure(operationName: String, block: suspend () -> T): T` — оборачивает блок, замеряет `System.nanoTime()` до/после, логирует длительность под `operationName`, вызывает `block()` без изменений независимо от включённости мониторинга (если выключен — просто не логирует, не влияет на поведение).
  - Оба пути читают `GatewayConfigStore.isDiagnosticsEnabled()` перед записью — выключенный переключатель не пишет таймеры. Для `JankStats` конкретно: `attachTo` вызывается один раз, идемпотентно (повторный вызов на уже присоединённое `Window` — no-op), а включение/выключение в рантайме управляется через нативное свойство `JankStats.isTrackingEnabled` (подтверждено: API предоставляет этот флаг из коробки), которое `PerfMonitor` обновляет через `GatewayConfigStore.addOnDiagnosticsEnabledChangeListener(...)` — новый метод, реализованный поверх `SharedPreferences.OnSharedPreferenceChangeListener` (фильтрует по ключу `diagnostics_enabled`), а не через отдельный `Flow`, поскольку `GatewayConfigStore` в проекте нигде больше не экспонирует `Flow`-обёртки над своими настройками (сохранён существующий паттерн работы с `SharedPreferences`, не введён новый механизм ради одной этой настройки).
  - Запись — `Log.i("PerfMonitor", ...)` и дозапись строки в `context.filesDir/perf/perf-log.txt` через `FileOutputStream(file, /* append = */ true)`, диспетчеризованная на отдельный `CoroutineScope(SupervisorJob() + Dispatchers.IO)` внутри `PerfMonitor` — **важно**: `JankStats`-колбэк исполняется на потоке, которым управляет сам `JankStats` (по умолчанию главный поток), поэтому синхронная запись в файл там создавала бы новый джанк вместо диагностики существующего; асинхронная диспетчеризация — не опционально, а обязательное условие корректности этой фичи.
- `GatewayConfigStore.kt`: `isDiagnosticsEnabled(): Boolean` (default `false`) / `setDiagnosticsEnabled(Boolean)` — тот же паттерн boolean-настройки, что `isForwardingPaused`.
- `MainActivity.kt`: `PerfMonitor.attachTo(window)` вызывается один раз на уровне всего приложения (внутри `setContent { SideEffect { ... } }`, см. выше) — покрывает JankStats-замером все экраны под этой Activity, а не только список диалогов, что ближе к духу требования «диагностика экранов», не только одного конкретного.
- `SmsHistoryImporter.importIfNeeded()`/`WebhookRequestWorker.doWork()`: обёрнуты в `perfMonitor.measure("history_import") { ... }` / `perfMonitor.measure("webhook_delivery") { ... }`.
- `SettingsScreen.kt`: новый раздел «Диагностика» — заголовок + один `Switch` (тест-тег `DIAGNOSTICS_SWITCH`), подпись поясняет, что метрики пишутся в файл на устройстве.

### B. Диагностика лагов скролла списка диалогов

**Живые замеры на TECNO LI9 (2026-09-02), реальные данные устройства** (реальная переписка, накопленная в предыдущих сессиях; жёсткий вход в область — device role переключался между Gateway App и системным приложением через `adb shell cmd role add-role-holder`):

| Приложение | Total frames | Janky | 90p | 95p | GPU 90p |
|---|---|---|---|---|---|
| Системное (`com.transsion.smartmessage`, тот же жест `adb shell input swipe`×5) | 230 | 0.87% (2) | 11ms | 13ms | 5ms |
| Gateway App, до фиксов (этот же жест) | 29 | 65.52% (19) | 200ms | 200ms | 6ms |
| Gateway App, после `distinctUntilChanged()` | 33 | 66.67% (22) | 150ms | 250ms | 6ms |
| Gateway App, после пробного отключения тени `Card` (поверх предыдущего) | 32 | 71.88% (23) | 117ms | 150ms | 7ms |
| Gateway App, без `SwipeToDismissBox`, прогон 1 из 4 | 202 | 11.39% (23) | 46ms | 89ms | 17ms |
| Gateway App, без `SwipeToDismissBox`, прогоны 2-4 из 4 | 29-36 | 79-91% | 93-150ms | — | 5ms |

Холодный старт (`adb shell am start -W`): системное — `TotalTime: 515ms`; Gateway App — `TotalTime: 1566ms`.

**Кандидаты и итог:**
1. `ConversationsViewModel.observeConversations`: `.distinctUntilChanged()` на исходный `Flow<List<ConversationEntity>>` — **применено, но НЕ дало измеримого улучшения скролла** (65.52% → 66.67%, в пределах шума при такой малой выборке кадров). Оставлено в коде: это независимо корректное улучшение (не пересобирать список при повторной идентичной эмиссии, например от несвязанного `ContentObserver`-срабатывания), просто не адресует именно лаг скролла — жест сплошного пальцевого скролла по уже загруженному списку не порождает новых эмиссий `Flow` вообще, так что гипотеза была структурно неверной с самого начала (задним числом очевидно).
2. Отключение тени `Card` (`CardDefaults.cardElevation(0.dp)`) — **протестировано и ОТКЛОНЕНО**: не дало измеримого улучшения (66.67% → 71.88%, тот же шумовой диапазон), при этом является нежелательной визуальной регрессией без обоснования — изменение **отменено**, код вернулся к дефолтной тени.
3. Стоимость `SwipeToDismissBox` на строку — **протестировано (2026-09-02, отдельный заход по запросу владельца продукта), результат неоднозначный, требует осторожной интерпретации**. Временно заменил `SwipeToDismissBox` на обычный `Card` (без жеста архивации/удаления), тот же реальный датасет, тот же жест. Первый прогон дал резкое улучшение: **11.39% janky (было 65.52%), 202 отрендеренных кадра (было 29)** — выглядело как подтверждение гипотезы. **Три последующих контрольных прогона на том же коде (без переустановки) вернулись к исходному диапазону: 79.31% / 83.33% / 90.91% janky, 29–36 кадров.** Единственный «хороший» прогон не воспроизвёлся — вероятнее всего, жест `adb shell input swipe` в тот раз случайно вызвал настоящий продолжительный флинг (200+ кадров вместо обычных ~30), а не код стал быстрее. Изменение **отменено** (возвращён `SwipeToDismissBox`), гипотеза формально не подтверждена и не опровергнута.
4. **Методологическая находка, важнее самого результата п.3**: `Total frames rendered` за идентичный жест на идентичном билде колебался от 29 до 202 между запусками — сам по себе жест `adb shell input swipe` через `adb` недостаточно детерминирован на этом устройстве/датасете, чтобы доверять **однократному** замеру `dumpsys gfxinfo`. Это ретроактивно ослабляет доверие ко всем остальным сравнениям в этом разделе (baseline vs `distinctUntilChanged()` vs отключение тени `Card`) — каждое из них было снято **одним** прогоном, не усреднено по нескольким. Возможно, что `distinctUntilChanged()`/тень `Card` тоже "не дали эффекта" из-за того же шума измерения, а не потому что эффекта действительно нет. Ни один вывод B-раздела не следует читать как окончательный без повторных замеров с усреднением по 3-5 прогонам.
5. **Итоговый вывод сессии**: 50-й перцентиль времени кадра у Gateway App держится на ~65-77мс почти во всех прогонах (кроме одного выброса) даже при малом датасете; GPU-время в норме (5-7мс) везде — узкое место стабильно на UI-потоке. Ни один протестированный кандидат не дал воспроизводимого улучшения. Причина осталась **не подтверждена измерением**, а не устранена — и, что важнее, сама методология однократного замера `dumpsys gfxinfo` на этом устройстве оказалась недостаточно надёжной для итоговых выводов «фикс X не сработал». Порог из Допущения п.3 недостижим в рамках этой сессии — нужна либо более надёжная методология измерения (усреднение по прогонам, детерминированный программный скролл вместо `adb shell input swipe`), либо больший датасет, либо оба (см. «Открытые вопросы»).

### C. Пустое состояние при холодном старте

- `ConversationsUiState.kt`: новое поле `hasLoadedOnce: Boolean = false` (transient UI-флаг, четырёхсекционная модель state — не персистится).
- `ConversationsViewModel.kt`: `observeConversations`'s `collect { ... }` выставляет `hasLoadedOnce = true` при первой обработанной эмиссии (включая эмиссию с пустым списком).
- `ConversationsScreen.kt`, `ConversationsContent`: условие показа «Нет сообщений»/«Архив пуст» меняется с `conversations.isEmpty() && !isImporting` на `hasLoadedOnce && conversations.isEmpty() && !isImporting`. До `hasLoadedOnce == true` — пустой `LazyColumn` без текста (см. Допущения п.5). `hasLoadedOnce` получил дефолт `true` в сигнатуре `ConversationsContent` (не влияет на реальный экран — `ConversationsScreen` всегда передаёт актуальное значение из `uiState`; дефолт существует только чтобы не трогать вызовы `ConversationsContent` в уже существующих превью/тестах, где параметр не передавался).
- **Живая проверка на TECNO LI9** (2026-09-02): холодный старт с реальной SMS-историей на устройстве — приложение показывает список диалогов сразу, без визуально заметного мигания текстом «Нет сообщений» на старте; краш, которым проявился отдельный найденный баг с `JankStats` (см. раздел A), при этой же живой проверке был обнаружен и исправлен до продолжения.

## Критерии приёмки

- Переключатель «Диагностика» в Настройках включает/выключает и `JankStats`-замер, и таймеры фоновых операций одним действием; при выключении — ни logcat, ни файл не пополняются.
- Метрики видны и в `adb logcat` (тег `PerfMonitor`), и в `context.filesDir/perf/perf-log.txt` на устройстве.
- Холодный старт списка диалогов не показывает текст «Нет сообщений»/«Архив пуст» до первой эмиссии `Flow`, если в Room уже есть данные для показа.
- Входящее SMS, для которого уже показано push-уведомление к моменту холодного старта, не приводит к показу пустого состояния при следующем открытии списка (следствие предыдущего пункта, отдельно не тестируется как новая логика).
- **Не выполнено полностью** — процент janky-кадров списка диалогов на реальном датасете устройства (65.52% до фиксов) остался практически неизменным после протестированных кандидатов (66.67%/71.88%, см. раздел «Функциональность» → B); порог, выведенный из сравнения с системным приложением (0.87%), оказался недостижим протестированными средствами на имеющихся данных. Не блокирует `Implemented` по той же логике, что и предыдущие milestone'ы этого проекта (0018, 0020): создан реальный, работающий инструментарий диагностики (часть A) и явно задокументирован остаток проблемы как неразрешённый, а не выдан за решённый — см. «Открытые вопросы».
- Найденная техника мгновенного отображения списка системным приложением: `adb shell cmd package resolve-activity` показал реальный компонент — `com.transsion.smartmessage/com.android.messaging.ui.conversationlist.ConversationListActivity`. Пакетное имя класса (`com.android.messaging.*`) указывает, что это форк открытого AOSP Messaging (`packages/apps/Messaging` в AOSP), а не проприетарная OEM-реализация с нуля — эта кодовая база исторически построена на `CursorLoader`/`Cursor`-адаптере поверх `SQLiteDatabase` напрямую (инкрементальные изменения курсора вместо полной пересборки List на каждое обновление), архитектурно другой подход, чем у Gateway App (Room `Flow` → `List<ConversationUi>` пересборка на VM-слое). Этот вывод получен через легальные внешние средства (`adb`, публичное знание об AOSP Messaging), без статического анализа/декомпиляции APK — décompiler не потребовался, поскольку имя пакета/класса само по себе оказалось достаточно информативным идентификатором кодовой базы; если потребуется более глубокое изучение конкретных техник, `apktool`/`jadx`-анализ остаётся доступным следующим шагом (см. Допущения п.4), не проведён в этой сессии за отсутствием необходимости.

## Тесты

## Открытые вопросы / Backlog

- **Главный нерешённый вопрос**: конкретная причина лага скролла списка диалогов на реальных данных устройства осталась не подтверждена измерением. Реальный датасет на TECNO LI9 слишком мал и сам жест `adb shell input swipe` недостаточно детерминирован (Total frames rendered варьировался 29-202 между идентичными прогонами — см. раздел B, п.4), что делает однократные замеры на нём ненадёжными. Следующий шаг (не в рамках этой сессии) — переделать методологию измерения (усреднение по 3-5 прогонам минимум, либо программно управляемый скролл через инструментированный тест вместо `adb shell input swipe` для детерминизма) и/или собрать замер на синтетически расширенном датасете (сотни диалогов, как уже допускалось в 0020 для похожей проблемы).
- Кандидат «стоимость `SwipeToDismissBox` на строку» протестирован (см. раздел B, п.3) с неоднозначным результатом: один из четырёх прогонов показал резкое улучшение (65.52% → 11.39% janky), не воспроизведшееся в трёх контрольных — правдоподобнее всего случайная удача с жестом `adb`, а не эффект кода, но формально гипотеза не опровергнута, только не подтверждена воспроизводимо. Изменение отменено (жест архивации/удаления важнее непроверенного выигрыша). Требует повторной проверки с надёжной методологией (см. пункт выше), прежде чем принимать решение окончательно.
- Cпека 0020 (Implemented) уже устраняла контакт-резолвинг и отсутствующий индекс как причины медленного старта списка; эта спека (0022) добавляет ещё один слой — устранение видимого пустого состояния до первой эмиссии, а также подтверждает, что GPU не является узким местом (6-7мс во всех замерах) — сужает круг подозреваемых для будущей диагностики до UI-thread composition/layout работы Compose, не рендеринга.
- Инструментарий (часть A) сам добавляет накладные расходы при включении (файловый I/O, пусть и асинхронный) — не измерен собственный оверхед `PerfMonitor` на глубину его влияния на реальные метрики; для личного использования (включается вручную, не постоянно) риск принят, не блокирует.
