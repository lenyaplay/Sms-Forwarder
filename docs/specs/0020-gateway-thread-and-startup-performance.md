# 0020 — Мгновенная навигация в треде и ускорение холодного старта списка диалогов (Android Gateway App)

**Статус:** Implemented

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0019-0021-requirements-doc.md](../requirements/0019-0021-requirements-doc.md) и [docs/requirements/0019-0021-analysis-brief.md](../requirements/0019-0021-analysis-brief.md) — эта спека их источник истины по деталям реализации. SQL/индекс проверены через `query-validation` перед фиксацией архитектуры (см. раздел «Архитектура»).*

## Контекст

Запрошено напрямую владельцем продукта (2026-08-29): при большой истории (тысячи сообщений) открытие треда не должно требовать видимой прокрутки к нужной позиции (как в Telegram), а холодный старт приложения не должен заметно тормозить перед показом списка диалогов. Анализ кода подтвердил две конкретные, разные по природе причины (не предположение — прочитан реальный код):

1. **`ThreadScreen.ThreadContent`**: `LaunchedEffect(uiState.messages.size) { listState.animateScrollToItem(uiState.messages.lastIndex) }` — при **каждом** открытии треда (в т.ч. с уже загруженной с диска историей в тысячи сообщений) выполняется анимированная прокрутка через весь путь от начала списка до конца, а не мгновенное позиционирование.
2. **Переход из поиска не позиционируется вовсе**: `SearchResultsList`/`ConversationsScreen` вызывает `onOpenThread(message.sender)` — тред открывается и сразу докручивается (тем же анимированным путём) к **последнему** сообщению диалога, а не к найденному. Найденное историческое сообщение ([0014](0014-gateway-search-archive-delete.md)) визуально не достижимо без ручной прокрутки пользователем.
3. **`ConversationsViewModel.observeConversations`**: на каждую эмиссию `Flow` из `MessageDao.observeConversations` пересчитывает `displayNameFor(sender)` через `ContactNameResolver` (синхронный `ContentResolver.query` к `content://contacts`) **для каждого диалога заново**, без кеша — уже задокументированное known limitation Milestone 12 («Найдено `peer-review-template` и исправлено» в Milestone 12: «раскрытое ограничение производительности... приемлемо на ожидаемом масштабе... для будущей оптимизации»), теперь фактически являющееся источником жалобы на холодный старт.
4. **`MessageDao.observeConversations`**: SQL с коррелированным подзапросом `WHERE m.createdAt = (SELECT MAX(createdAt) FROM messages WHERE sender = m.sender)` — без индекса на `(sender, createdAt)` каждый диалог требует полного скана `messages` для подзапроса.

## Допущения и решения

1. **Мгновенная навигация — два входа** (решение владельца продукта): (а) обычное открытие треда — сразу к последнему сообщению, без анимации; (б) переход по клику на результат поиска — сразу к найденному сообщению, без анимации и без промежуточного отображения последнего.
2. **«Без анимации» ≠ «без анимации никогда»** — анимация (`animateScrollToItem`) остаётся уместной только для уже открытого треда, когда в него приходит новое сообщение при активном экране (короткий, предсказуемый скролл на 1 позицию — не тысячи). Различие: используется `LaunchedEffect(Unit)` (один раз при первом композиции экрана, `scrollToItem` без анимации, к целевой позиции) отдельно от уже существующего `LaunchedEffect(uiState.messages.size)` (анимированная докрутка при изменении размера списка **после** первого открытия).
3. **Целевая позиция для перехода из поиска** — по индексу найденного сообщения в списке `messages` треда (`ThreadUiState.messages` уже отсортирован `ORDER BY createdAt ASC`, соответствует порядку `LazyColumn`), не по времени — проще и не требует дополнительного запроса.
4. **Причина холодного старта — обе (контакты + SQL), обе устраняются**, не выбирается одна: (а) кеш `ContactNameResolver` по номеру в самом `ConversationsViewModel` (in-memory `MutableMap`, инвалидация не нужна — контакты пользователя меняются редко, а промах кеша просто означает разовый повторный резолвинг после следующей эмиссии; если пользователь изменит контакт в адресной книге, обновлённое имя подхватится при следующем холодном старте — не в рамках этой спеки живое отслеживание изменений адресной книги); (б) новый составной индекс Room `@Index(["sender","createdAt"])` на `MessageEntity` — проверен через `query-validation`, ускоряет коррелированный `MAX`-подзапрос (индекс-скан вместо полного скана таблицы на каждый диалог), не даёт полного решения для внешнего `ORDER BY` (не блокирует — личный масштаб использования, тот же вывод, что уже принят для аналогичных вопросов в 0014/0015/0016).
5. Кеш контактов — только в `ConversationsViewModel` (список диалогов, самый частый источник резолвинга при каждой эмиссии); `ThreadViewModel.contactNameResolver.displayNameFor(sender)` резолвится один раз за создание `ViewModel` (уже не проблема — единичный вызов на один тред, не пересчитывается на каждую эмиссию).

## Функциональность

### Мгновенная навигация в треде

- `ui/nav/NavGraph.kt`: маршрут `Routes.THREAD` получает опциональный query-параметр `messageId` (`"thread/{sender}?messageId={messageId}"`), по умолчанию отсутствует/`0`. `ConversationsScreen`'s `onOpenThread` расширяется до `(sender: String, messageId: Long?) -> Unit`; обычный клик по диалогу передаёт `null`, клик по результату поиска передаёт `message.id`.
- `ThreadViewModel` читает `messageId` из `SavedStateHandle` (по аналогии с уже читаемым `sender`), кладёт в `ThreadUiState.scrollToMessageId: Long?`.
- `ThreadContent`: `LaunchedEffect(Unit)` (не зависит от `messages.size`) — как только `uiState.messages` не пуст, вычисляет целевой индекс (`scrollToMessageId`, если задан и найден в списке, иначе `lastIndex`) и вызывает `listState.scrollToItem(targetIndex)` (без анимации), один раз. Существующий `LaunchedEffect(uiState.messages.size) { animateScrollToItem(lastIndex) }` остаётся, но должен не срабатывать на первом же появлении списка повторно поверх уже выполненного `scrollToItem` — при реализации проверить порядок эффектов (например, через флаг «первая прокрутка уже выполнена» в `remember`, чтобы `animateScrollToItem` включался только при последующих изменениях `messages.size`, не при самом первом).

### Ускорение холодного старта списка диалогов

- `ConversationsViewModel`: `MutableMap<String, String?>` как in-memory кеш `sender -> displayName`; `observeConversations` резолвит через `ContactNameResolver` только для `sender`, отсутствующих в кеше, иначе берёт закешированное значение.
- `MessageEntity.kt`: `@Entity(tableName = "messages", indices = [Index(value = ["sender", "createdAt"])])`.
- `GatewayDatabase.kt`: `version = 6`, новая `MIGRATION_5_6` — `CREATE INDEX IF NOT EXISTS index_messages_sender_createdAt ON messages(sender, createdAt)`.
- `di/DatabaseModule.kt`: регистрация `MIGRATION_5_6`.

## Архитектура

- `ui/nav/NavGraph.kt` — route-строка и `navArgument("messageId")` (`NavType.LongType`, `defaultValue = 0L`), `ThreadScreen`/`ThreadViewModel` читают его как `null` при `0L`.
- `ui/conversations/ConversationsScreen.kt`/`ConversationsViewModel.kt` — сигнатура `onOpenThread`, добавление кеша контактов.
- `ui/thread/ThreadScreen.kt`/`ThreadUiState.kt`/`ThreadViewModel.kt` — `scrollToMessageId`, второй `LaunchedEffect`, флаг «первая прокрутка выполнена».
- `data/local/db/MessageEntity.kt`, `GatewayDatabase.kt`, `di/DatabaseModule.kt` — индекс и миграция (проверено `query-validation`, см. выше в «Контекст»/«Допущения»).
- Backend/Viewer App не затронуты.

## Критерии приёмки

- Открытие треда с историей в несколько сотен/тысяч сообщений показывает последнее сообщение сразу, без визуально заметной прокрутки через весь список (проверяется отсутствием промежуточных кадров — `scrollToItem`, не `animateScrollToItem`, на первом открытии).
- Клик по результату полнотекстового поиска открывает тред сразу на найденном сообщении (видно на экране без ручной прокрутки), не на последнем сообщении диалога.
- Новое входящее сообщение в уже открытом треде по-прежнему анимированно докручивается (не регрессия — короткая анимация на 1 позицию сохраняется).
- Список диалогов на холодном старте (после импорта истории, не считая сам разовый импорт — он отдельная операция) не пересчитывает имя контакта повторно для диалога, уже отрезолвленного в этой сессии работы `ViewModel`.
- `observeConversations`-запрос использует новый индекс (не строгий количественный критерий на личном масштабе — проверяется по `EXPLAIN QUERY PLAN` при реализации, что коррелированный подзапрос больше не делает `SCAN messages`, а `SEARCH messages USING INDEX`).

## Тесты

- Инструментированный (Compose): `ThreadScreenTest` — открытие с `messageId=null` показывает последнее сообщение видимым сразу; открытие с `messageId=<id из середины списка>` показывает именно это сообщение видимым; оба теста замораживают `composeRule.mainClock` (`autoAdvance = false`, один кадр) — иначе (подтверждено peer review) тест не отличил бы `scrollToItem` от `animateScrollToItem`, так как idle-синхронизация Compose-тестов сама доводит анимацию до конца прежде чем проверить assert. Третий тест подтверждает, что новое сообщение в уже открытом треде по-прежнему докручивается анимированно (регресс на ветку `else`).
- Инструментированный: `ConversationsScreenTest.contactNameIsNotReResolvedOnRepeatedEmissionsForTheSameSender` — повторная эмиссия `observeConversations` с тем же отправителем не вызывает `ContactNameResolver.displayNameFor` повторно (`verify(..., times(1))`).
- Room: `MIGRATION_5_6` открывается на реальной БД без ошибки — покрыта тем же способом, что и предыдущие миграции (реальное открытие БД через `DatabaseModule` в инструментированных тестах и на устройстве), выделенного `MigrationTestHelper`-теста в проекте по-прежнему нет ни для одной миграции — не новый пробел этой спеки.
- `EXPLAIN QUERY PLAN` для `observeConversations`-запроса — воспроизведён локально (Python `sqlite3`, схема идентична реальной) вместо `adb`/устройства: без индекса коррелированный подзапрос делает `SEARCH messages` (полный скан на каждый диалог), с индексом — `SEARCH messages USING COVERING INDEX index_messages_sender_createdAt (sender=?)`. Критерий приёмки подтверждён напрямую, не косвенно.
- Ручная проверка на физическом устройстве (2026-08-29, TECNO LI9, реальная накопленная история из предыдущих milestone'ов): тред «Perekrestok» (6 реальных SMS) открывается сразу с видимыми сообщениями без сбоя; поиск по уникальной подстроке одного из более ранних (не последнего) сообщений треда, клик по результату — тред открылся с этим сообщением на экране, без краша. Оговорка: реальные тестовые диалоги на устройстве малы (единицы-десятки сообщений) — сценарий «тысячи сообщений, видимая прокрутка отсутствует» проверен строго только инструментированным тестом с 200 синтетическими сообщениями и заморозкой clock, не живым устройством с такой же историей; холодный старт субъективно не хронометрирован отдельно в этой сессии.

## Открытые вопросы / Backlog

- Кеш контактов не инвалидируется при изменении адресной книги в течение сессии — обновление подхватывается только при следующем холодном старте приложения (пересоздании `ConversationsViewModel`). Не блокирует — тот же класс допущения, что уже принят для других данных на личном масштабе использования.
- Устранение внешнего `ORDER BY m.createdAt DESC`-сортировки без индекса, покрывающего его напрямую, не выполнено — не блокирует на личном масштабе (сотни-тысячи диалогов), зафиксировано как открытый вопрос на случай будущего роста.
