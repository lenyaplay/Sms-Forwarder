# 0014 — Поиск, архивация и удаление диалогов (Android Gateway App)

**Статус:** Implemented

## Контекст

`docs/specs/0013-android-gateway-app.md` изначально вынес поиск/архивацию/удаление диалогов в backlog как «вне MVP». Milestone 12 (`docs/Roadmap.md`) с тех пор реализовал полноценный список диалогов и переписку (этапы 1–4), но без поиска, архивации и удаления — обычные функции SMS-клиента, без которых приложение неудобно использовать при накоплении истории. Пользователь явно запросил реализацию этой функциональности как следующий шаг.

## Допущения и решения (собраны в интервью с владельцем продукта)

1. **Поиск — полнотекстовый по всей переписке**, а не только по последнему видимому сообщению в списке диалогов. Ищет по всем сообщениям в Room, не только по последнему в диалоге — иначе не найдёт сообщение внутри давнего треда, если оно не последнее.
2. **Архивация включена в эту версию**, не отложена на будущий этап: у диалога появляется отдельный статус (архивирован/нет), список диалогов по умолчанию показывает только неархивированные, есть переключение на архив.
3. **Удаление — и целого диалога, и отдельных сообщений**: из списка диалогов/свайпом в треде можно удалить весь диалог (все сообщения с этим отправителем); внутри треда можно точечно удалить отдельное сообщение.
4. **Удаление — чисто локальное действие в Room на этом этапе.** Backend и Viewer App не меняются в рамках этой спеки: уже доставленные копии сообщений остаются на бэкенде и в Viewer App как есть. Владелец продукта явно попросил зафиксировать в backlog будущее направление: пометка «удалено» на бэкенде + отображение в Viewer App со значком корзины — отдельная будущая спека, требующая изменений backend API (вне текущей спеки, см. «Открытые вопросы»).
5. **Подтверждение обязательно перед любым удалением** (диалога или отдельного сообщения) — действие необратимо, корзины/отмены нет на этом этапе.
6. Область (backend, Viewer App, формат webhook `0003-sms-webhook.md`) не меняется в этой спеке.

## Функциональность

- **Поиск**: поле поиска на экране списка диалогов (или отдельный режим поиска), ищет по тексту (`MessageEntity.text`) всех сообщений; результат — либо список диалогов, содержащих совпадение (с подсветкой/сниппетом), либо переход сразу к найденному сообщению внутри треда (уточняется при реализации, не блокирует Draft).
- **Архивация**: новое поле статуса диалога (например, `isArchived` на уровне диалога — реализация зависит от модели данных, см. «Архитектура»); свайп/меню действия на строке диалога — «Архивировать»/«Разархивировать»; список диалогов по умолчанию скрывает архивированные; отдельный экран/фильтр «Архив».
- **Удаление диалога**: свайп/меню действия на строке диалога или кнопка в треде — «Удалить диалог», с диалогом подтверждения, удаляет все `MessageEntity` с данным `sender`.
- **Удаление сообщения**: долгое нажатие/меню на сообщении в треде — «Удалить», с диалогом подтверждения, удаляет одну строку `MessageEntity`.

## Архитектура

Новый независимый Gradle-модуль не требуется — расширение существующего `android_gateway/`:

- `MessageEntity`/`MessageDao` (`data/local/db/`) — добавить поле статуса архивации (на диалог, не на отдельное сообщение — нужно решить при реализации, архивация диалога, скорее всего, per-conversation, а не per-message: либо отдельная таблица `conversations` с полем `isArchived`, либо флаг на каждом `MessageEntity` данного отправителя — предпочтительно первое, чтобы не рассинхронизировать статус между сообщениями одного диалога при появлении нового сообщения; уточнить при реализации).
- `MessageDao` — новые запросы: полнотекстовый поиск (`LIKE` или Room FTS — решить при реализации исходя из ожидаемого объёма данных, обычный `LIKE` может быть достаточен для личного использования), удаление по `sender`, удаление по `id`, фильтрация `observeConversations()` по архивному статусу.
- `MessageRepository` — методы `searchMessages(query)`, `archiveConversation(sender)`/`unarchiveConversation(sender)`, `deleteConversation(sender)`, `deleteMessage(id)`.
- UI: `ConversationsScreen` — поле/иконка поиска, свайп-действия или меню на строке (архивировать/удалить), фильтр «Архив»/«Активные»; `ThreadScreen` — удаление отдельного сообщения; общий переиспользуемый диалог подтверждения (`AlertDialog`, по образцу уже существующего `NewMessageDialog`).

## Критерии приёмки

- Поиск находит сообщение по тексту в любом месте истории переписки (не только в последнем сообщении диалога), включая случаи, когда совпадающее сообщение не последнее в диалоге.
- Архивированный диалог не отображается в основном списке, отображается в архиве; действие обратимо (разархивировать).
- Удаление диалога требует подтверждения и после подтверждения полностью убирает все сообщения этого диалога из Room и из UI.
- Удаление отдельного сообщения требует подтверждения и убирает только это сообщение, не затрагивая остальную историю диалога.
- Backend/Viewer App не затронуты — доставленные ранее копии сообщений остаются видны в Viewer App без изменений.

## Тесты

- Unit: логика фильтрации архивных/неархивных диалогов, если вынесена в чистую функцию; построение поискового SQL-запроса, если применимо.
- Инструментированные (Room): `MessageDao` — поиск по тексту находит сообщение не только по последнему в диалоге; удаление по `sender` удаляет все строки диалога и не затрагивает другие; удаление по `id` удаляет одну строку; фильтрация по архивному статусу.
- Инструментированные (Compose): поле поиска фильтрует список диалогов; диалог подтверждения перед удалением; архивация скрывает диалог из основного списка и показывает в архиве.
- Ручная проверка на физическом устройстве: поиск находит реальное старое сообщение, архивация/разархивация работает, удаление диалога и отдельного сообщения работает с подтверждением, backend/Viewer App не затронуты.

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Пометка сообщений как «удалено» на backend (новое поле/эндпоинт в `0003-sms-webhook.md`/`0005-viewer-messages-api.md`) + отображение в Viewer App со значком корзины вместо полного удаления с бэкенда — отдельная будущая спека, требует изменений backend API, явно вынесено пользователем в backlog при сборе требований для этой спеки.
- Точная модель хранения архивного статуса (per-conversation vs per-message) — решить при реализации, не блокирует написание спеки.
- Выбор между `LIKE`-поиском и Room FTS — решить при реализации исходя из реального объёма данных на устройстве.
