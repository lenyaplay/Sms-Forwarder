# 0011 — Экран создания устройства, исправление запроса разрешения на камеру, тёмная тема

**Статус:** Implemented

## Контекст

Обнаружено при ручном тестировании Milestone 9 (спека `0010`) на физическом устройстве (2026-08-27): в приложении нет способа создать новое устройство (смятить первый `upload_token`) — только управление уже существующим устройством (`DeviceDetailScreen`, спека `0010`). Это было осознанным решением спек `0007` (допущение 9) и `0010` (контекст) — создание устройства сочли административным действием вне UI, через прямой вызов `POST /devices`. Пользователь явно решил пересмотреть это ограничение для этой спеки (см. допущения ниже) — процесс `CLAUDE.md` требует не менять утверждённое решение самовольно, а зафиксировать явное решение пользователя, что здесь и сделано через `AskUserQuestion`.

Дополнительно при том же ручном тестировании найдены два независимых дефекта:
1. `AddDeviceScreen` (спека `0007`) проверяет разрешение на камеру только один раз при первой композиции (`remember { ContextCompat.checkSelfPermission(...) }`) и не имеет пути запроса разрешения — если разрешение ещё не выдано, кнопка «Scan QR code instead» вообще не показывается, и нет способа его запросить из приложения.
2. Тёмная тема технически уже существует (`Theme.kt` следует системной теме через `isSystemInDarkTheme()`), но `SmsForwarderViewerTheme` не оборачивает контент в `Surface` — из-за этого `Text`/`Icon` без явного цвета берут дефолтный `LocalContentColor` (чёрный) вместо `MaterialTheme.colorScheme.onBackground`, при том что фон окна (XML-тема `Theme.MaterialComponents.DayNight.NoActionBar`) в тёмном режиме системы становится тёмным — итог: тёмный текст на тёмном фоне почти везде.

## Допущения и решения (assumptions log)

Зафиксировано через `AskUserQuestion` перед написанием этой спеки:

1. **Экран создания устройства — добавляется, это явный пересмотр решения спек 0007/0010.** Пользователь подтвердил: создание устройства (минтинг `upload_token` через `POST /devices`) должно быть доступно из приложения, а не только через прямой вызов API. Прежнее решение («вне UI») не действует для новых устройств начиная с этой спеки; спеки `0007`/`0010` не редактируются задним числом — это новое решение поверх старого, задокументированное здесь.
2. **Точка входа — кнопка на `DeviceListScreen`**, отдельно от существующей кнопки «Add device» (присоединение по `download_token`). Реализация: FAB на `DeviceListScreen` открывает `DropdownMenu` с двумя пунктами — «Join by token» (существующий флоу, спека `0007`) и «Create new device» (новый флоу, эта спека) — вместо второго FAB или отдельного экрана-меню, минимальное изменение существующего UI.
3. **После создания устройства** экран показывает смятый `upload_token` (полностью, для копирования — не маскируется, в отличие от `DeviceDetailScreen`, где токен уже используется и не должен светиться на экране лишний раз; здесь это единственный момент, когда пользователь вообще может увидеть и скопировать токен для настройки Gateway App) с кнопкой «Done» → возврат на список устройств.
4. **Экран создания не проверяет уникальность имени на клиенте** — совпадает с текущим поведением бэкенда (нет уникальности имени устройства в `0002-devices-tokens.md`), клиент не изобретает дополнительных правил.
5. **Исправление QR-разрешения**: кнопка «Scan QR code» видна всегда (не только когда разрешение уже выдано). По нажатию — если разрешения нет, показывается системный диалог запроса (`rememberLauncherForActivityResult(RequestPermission)`); если пользователь дал разрешение — открывается сканер; если отказал — остаётся текстовая подсказка «Grant camera permission to scan a QR code, or enter the token manually» на месте сканера. Состояние разрешения перепроверяется по возврату из системного диалога, а не фиксируется один раз при композиции.
6. **Тёмная тема**: остаётся системной (следует `isSystemInDarkTheme()`), никакого ручного переключателя в приложении не добавляется в этой версии — пользователь подтвердил, что проблема именно в контрасте (тёмный текст на тёмном фоне), а не в отсутствии ручного переключателя. Исправление — оборачивание контента темы в `Surface(color = MaterialTheme.colorScheme.background, contentColor = MaterialTheme.colorScheme.onBackground)` в `SmsForwarderViewerTheme` (`ui/theme/Theme.kt`), стандартный паттерн Compose Material3 для распространения цвета контента. Кастомизация цветовой палитры (сейчас используются дефолтные `lightColorScheme()`/`darkColorScheme()` без брендовых цветов) — вне scope, не запрашивалась.

## API / интерфейс

Изменений на бэкенде нет. На Android-стороне всё уже подключено спекой `0010`: `ApiService.createDevice()`, `DeviceRepository.createDevice(name): Result<DeviceCreateResponse>` — новый экран только вызывает существующий метод, ничего нового в сетевом слое не добавляется.

## Экраны и сценарии

### 1. Создание устройства (новый, `ui/createdevice/CreateDeviceScreen.kt` + `CreateDeviceViewModel.kt`)
- Поле «Device name», кнопка «Create» → `DeviceRepository.createDevice(name)`.
- Успех → экран переключается на показ `upload_token` (полный текст, копируемый) + кнопка «Done» → `onDone()` (возврат на список устройств, список обновляется).
- Ошибка (сетевая/HTTP) → сообщение об ошибке под полем, без потери введённого имени.
- Пустое имя → кнопка неактивна / клиентская валидация "Device name is required" без похода в сеть (симметрично другим формам в проекте, напр. `RegisterViewModel`).

### 2. `DeviceListScreen` (изменение существующего)
- FAB меняет поведение: по нажатию открывает `DropdownMenu` с пунктами «Join by token» (→ существующий `onAddDevice`, ведёт на `AddDeviceScreen`) и «Create new device» (→ новый `onCreateDevice`, ведёт на `CreateDeviceScreen`).

### 3. `AddDeviceScreen` (исправление существующего)
- Кнопка «Scan QR code» всегда видима.
- Нажатие: если разрешения нет — запрос через `ActivityResultContracts.RequestPermission`; колбэк обновляет состояние разрешения (не однократный `remember` от старого значения).
- Разрешение выдано → показывается сканер (существующий `QrScannerView`, без изменений).
- Разрешение отклонено → текстовая подсказка вместо сканера (как сейчас), но кнопка «Scan QR code» остаётся доступной для повторной попытки.

### 4. Тёмная тема (исправление существующего, `ui/theme/Theme.kt`)
- `SmsForwarderViewerTheme` оборачивает `content` в `Surface(color = MaterialTheme.colorScheme.background, contentColor = MaterialTheme.colorScheme.onBackground, content = content)` внутри `MaterialTheme { ... }`.
- Затрагивает все существующие экраны одинаково (общая точка входа в `MainActivity.kt`) — точечных правок по экранам не требуется.

## Критерии приёмки

- На `DeviceListScreen` FAB открывает меню с двумя пунктами; «Create new device» ведёт на новый экран, «Join by token» — на существующий `AddDeviceScreen` (поведение не изменилось).
- Успешное создание устройства на `CreateDeviceScreen` показывает реальный `upload_token`, полученный от бэкенда (`POST /devices`), и после «Done» новое устройство появляется в списке (роль `owner`).
- На `AddDeviceScreen` кнопка «Scan QR code» видна независимо от текущего статуса разрешения; при отсутствии разрешения нажатие показывает системный диалог; после выдачи разрешения (без пересоздания экрана/активности) открывается сканер.
- При системной тёмной теме весь текст/иконки на всех экранах читаемы (нет тёмного текста на тёмном фоне) — проверяется вручную на устройстве с включённой тёмной темой ОС.

## Тесты

- **Unit (JVM):** `CreateDeviceViewModel` — успех (возвращает `upload_token`), сетевая/HTTP-ошибка, пустое имя не уходит в сеть.
- **Instrumented/UI:** `CreateDeviceScreenTest` — успешное создание показывает токен и кнопку Done; ошибка показывает сообщение. `DeviceListScreenTest` — новый тест: клик по FAB показывает оба пункта меню, клик по каждому вызывает соответствующий колбэк. `AddDeviceScreenTest` — новый тест: кнопка сканирования видна без выданного разрешения (используя `GrantPermissionRule`/явную проверку обоих состояний разрешения, где это осуществимо в инструментированном тесте; часть сценария — реакция на системный диалог — не автоматизируется штатными средствами Compose-тестов и проверяется вручную, отмечается явно).
- **Тёмная тема**: автотестами контраст не проверяется (нет практичного способа в Compose UI test без скриншот-тестирования, которое не настроено в проекте) — только ручная проверка на устройстве/эмуляторе с системной тёмной темой, отражается в разделе «Проверено вручную» при переводе в Implemented.

**Проверено вручную**: полный сценарий (настройка сервера → регистрация → логин → создание устройства → появление в списке → создание второго устройства без перезапуска приложения → `AddDeviceScreen` без выданного разрешения → системный диалог → выдача разрешения → сканер открывается сразу → системная тёмная тема на всех экранах) прогнан на физическом устройстве через `adb` (скриншоты + `uiautomator dump` для точных координат тапов).

В процессе найдены и исправлены два реальных дефекта, не описанных в исходной версии этой спеки (задокументированы здесь постфактум, до перевода в Implemented, по правилу «спека отражает то, что реально построено»):

- **Bug A (обнаружен вручную)**: `DeviceListViewModel` подгружал список устройств только один раз в `init()`. Поскольку `hiltViewModel()` привязывает ViewModel к `NavBackStackEntry` экрана, а не пересоздаёт его при `popBackStack()`, только что созданное устройство не появлялось в списке после `CreateDeviceScreen` → Done — список оставался пустым до полного перезапуска процесса приложения. Это прямое нарушение критерия приёмки №2. Исправлено: `DeviceListScreen` подписывается на `LocalLifecycleOwner` через `DisposableEffect` + `LifecycleEventObserver` и вызывает `viewModel.refresh()` на `Lifecycle.Event.ON_RESUME` — у `NavBackStackEntry` в Navigation-Compose свой `LifecycleOwner`, поэтому `ON_RESUME` срабатывает и при возврате внутри приложения, не только при возврате из фона. Регрессионный тест: `DeviceListScreenTest.screenRefreshesDeviceListOnResume` (использует `ActivityScenario.moveToState()` для реального прогона через lifecycle, не прямой вызов `refresh()`).
- **Bug B (обнаружен через самопроверку `android-skills:android-dev` по тому же классу проблемы)**: та же самая устарелость состояния была и в `AddDeviceScreen` — `hasCameraPermission` обновлялось только через колбэк `rememberLauncherForActivityResult`, поэтому разрешение, выданное через системные Настройки, пока приложение свёрнуто, не подхватывалось при возврате. Исправлено тем же паттерном (`DisposableEffect` + `ON_RESUME` + повторная проверка `ContextCompat.checkSelfPermission`). Регрессионный тест: `AddDeviceScreenTest.permissionGrantedFromSystemSettingsWhileBackgroundedIsPickedUpOnResume` (реальный `pm revoke`/`pm grant` через `UiAutomation.executeShellCommand` + `ActivityScenario.moveToState()`).

`./gradlew :app:connectedDebugAndroidTest` — 35 тестов, 0 падений. `./gradlew :app:testDebugUnitTest` — все зелёные. `peer-review-template` пройден (1 should-fix, не блокирующий: двухтаповое открытие `AddDeviceScreen` через меню вместо одного тапа — осознанное изменение UX, покрыто тестом).
