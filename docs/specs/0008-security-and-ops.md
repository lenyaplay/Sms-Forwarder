# 0008 — Безопасность и эксплуатация

**Статус:** Implemented

## Контекст

Milestone 7 (`docs/Roadmap.md`). Бэкенд функционально полон через Milestone 6 (auth, устройства/токены, приём SMS, REST-чтение, realtime, Android viewer), но не готов к эксплуатации: нет защиты от злоупотребления webhook/auth-эндпоинтами, нет TLS в деплое, нет контейнеризации, нет структурированных логов и health-check для мониторинга/оркестрации.

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Rate-limiting — по `upload_token` для webhook, отдельно по IP для `/auth/*`.** Webhook аутентифицирован токеном устройства — лимит по токену защищает конкретный скомпрометированный/сбойный шлюз, не зависит от смены IP/NAT. `/auth/*` (`login`, `register`, `refresh`) не имеет токена до входа — лимит по IP защищает от brute-force.
2. **Лимиты: ~60 запросов/мин на ключ, burst 10, ответ `429` с заголовком `Retry-After`.** SMS от одного шлюза обычно не приходят пачками быстрее этого; burst покрывает всплеск при восстановлении связи у шлюза после разрыва.
3. **Область действия — только `POST /devices/{id}/messages` (webhook) и `/auth/login`, `/auth/register`, `/auth/refresh`.** `GET /devices`, `GET /devices/{id}/messages`, `GET /events`, `POST /devices/bindings`, `POST /auth/logout` — трафик уже аутентифицированных пользователей, не лимитируется в этом milestone.
4. **TLS терминируется на существующем nginx (вне этого репозитория/бэкенда).** У владельца уже развёрнут nginx (через 3x-ui) с другими сайтами на том же сервере; sms_forwarder добавляется отдельным server-блоком на свой домен/поддомен с сертификатом, управляемым существующей инфраструктурой. Go-сервер в Docker-контейнере слушает только plain HTTP на internal-порту, наружу не публикуется напрямую. Задача этой спеки — только подготовить бэкенд к работе за реверс-прокси (например, корректная обработка `X-Forwarded-For` для rate-limiting по IP) и задокументировать пример nginx-конфига; сама настройка nginx/сертификата — вне репозитория, не часть кода этой спеки.
5. **Docker: один контейнер бэкенда, SQLite-файл — в именованном Docker volume.** Volume переживает пересоздание контейнера (обновление образа), не зависит от конкретного host-пути.
6. **Логи — structured JSON в stdout.** Поля: `time`, `level`, `method`, `path`, `status`, `latency_ms`, `request_id`. Тело запроса, заголовок `Authorization` и любые токены (`upload_token`, `download_token`, `access_token`, `refresh_token`) никогда не логируются. Формат позволяет собирать логи через стандартные Docker-логдрайверы/агрегаторы без дополнительного парсинга.
7. **Health-check — `GET /healthz` проверяет доступность БД** (лёгкий `SELECT 1`/`PingContext`), а не просто отвечает `200` безусловно — иначе health-check остаётся зелёным, даже когда SQLite-файл недоступен (например, проблема с volume), что делает его бесполезным для оркестрации/мониторинга.
8. **Одна спецификация `0008` на весь Milestone 7.** Все три пункта — части одной темы «готовность к эксплуатации», реализуются и ревьюятся вместе; отдельные спеки добавили бы дублирование контекста без практической пользы при таком объёме.

## API / интерфейс

Новое:
- `GET /healthz` — без аутентификации. `200 {"status":"ok"}` если БД отвечает; `503 {"status":"unavailable","error":"..."}` если `PingContext` к БД возвращает ошибку.
- Ответ `429` от rate-limiter на limited-эндпоинтах: `{"error": "rate limit exceeded"}`, заголовок `Retry-After: <секунды до сброса окна>`.

Без изменений в остальных эндпоинтах (не в контракте — только добавляется rate-limiting middleware и логирование поверх существующих хендлеров).

## Модель данных

Нет изменений в схеме БД. Rate-limiter хранит состояние (счётчики по ключу) в памяти процесса (`golang.org/x/time/rate` — token bucket на ключ), не в БД — приемлемо для однопроцессного деплоя (текущая архитектура, без горизонтального масштабирования на нескольких инстансах).

## Docker / деплой

- `Dockerfile` (multi-stage): builder-стадия — `go build` статического бинаря; финальная стадия — минимальный образ (`scratch`/`alpine`) с бинарём и embed-миграциями.
- `docker-compose.yml` (пример для деплоя): один сервис `backend`, именованный volume под путь к SQLite-файлу, порт публикуется только на loopback/internal-сеть (не наружу — наружу смотрит nginx).
- Пример конфигурации nginx (в `docs/` или `deploy/`, не выполняемый код) — server-блок с `proxy_pass` на internal-порт контейнера, `proxy_set_header X-Forwarded-For`, для справки; не тестируется автотестами (вне репозитория/CI).
- Приложение должно доверять `X-Forwarded-For` от reverse-proxy для определения клиентского IP (rate-limiting по IP для `/auth/*`) — конфигурируемо (доверенный прокси задаётся через переменную окружения, чтобы не доверять этому заголовку от произвольного клиента, если однажды бэкенд окажется без прокси перед собой).

## Сценарии использования

1. Шлюз шлёт больше 60 webhook-запросов/мин по одному `upload_token` (например, зациклился на ретраях из-за бага) → после исчерпания burst получает `429` с `Retry-After`, не кладёт БД лишней нагрузкой.
2. Кто-то перебирает пароли на `/auth/login` с одного IP → после превышения лимита получает `429`, дальнейшие попытки с того же IP блокируются до сброса окна.
3. Оркестратор (или человек) дергает `GET /healthz` → получает `200`, если сервис и БД живы, `503` — если БД недоступна (например, volume не примонтирован) — сигнал для рестарта/алерта.
4. Оператор смотрит `docker logs` → видит JSON-строки по каждому запросу (метод, путь, статус, латентность), без утечки токенов/паролей в лог.
5. Деплой обновления: `docker compose up -d --build` пересоздаёт контейнер бэкенда, SQLite-файл в volume не теряется.

## Критерии приёмки

- Webhook-эндпоинт (`POST /devices/{id}/messages`) ограничен по `upload_token`: ~60 req/min, burst 10; превышение → `429` + `Retry-After`, запрос не доходит до бизнес-логики/БД.
- `/auth/login`, `/auth/register`, `/auth/refresh` ограничены по IP-клиента (с учётом `X-Forwarded-For` от доверенного прокси): та же схема лимита.
- Остальные эндпоинты (`GET /devices`, `GET /devices/{id}/messages`, `GET /events`, `POST /devices/bindings`, `POST /auth/logout`) не ограничены в этом milestone.
- `GET /healthz` возвращает `200` при живой БД и `503` при недоступной, без аутентификации.
- Каждый HTTP-запрос логируется одной JSON-строкой в stdout с полями `time`, `level`, `method`, `path`, `status`, `latency_ms`, `request_id`; тело запроса, `Authorization`, `upload_token`, `download_token`, `access_token`, `refresh_token` не попадают в лог ни в каком виде.
- `Dockerfile` собирает рабочий образ; контейнер запускается и проходит health-check.
- SQLite-файл смонтирован в именованный Docker volume; пересоздание контейнера (`docker compose up -d --build`) не теряет ранее сохранённые данные.
- Пример nginx-конфига задокументирован (для ручного применения оператором на существующем сервере, не выполняется автотестами).

## Тесты

- **Backend (Go):**
  - Rate-limiter middleware: запросы в пределах лимита проходят; превышение лимита/burst даёт `429` с `Retry-After`; лимит корректно разделён по ключу (разные `upload_token`/IP не влияют друг на друга); окно сбрасывается по истечении времени (тест с управляемым `time.Now`/фейковым clock, не реальный `sleep` на минуту).
  - `GET /healthz`: `200` при рабочей БД (`httptest` + реальная SQLite с миграциями, как в остальных тестах storage-слоя); `503` при закрытой/недоступной БД-коннекшн (например, закрытый `*sql.DB` перед вызовом хендлера).
  - Логирующий middleware: тест, что лог-запись не содержит подставленных в тестовый запрос секретов (заголовок `Authorization`, тело с токеном) — например, через перехват `io.Writer`, в который пишутся логи, и проверку содержимого на отсутствие подстроки секрета.
  - Определение клиентского IP из `X-Forwarded-For`: доверенный прокси → берётся IP из заголовка; недоверенный источник → берётся IP TCP-соединения, заголовок игнорируется (тест на оба случая — важно, чтобы клиент не мог подделать `X-Forwarded-For` и обойти лимит по IP).
- Docker/nginx-конфигурация — не покрывается автотестами (вне scope Go test suite), проверяется вручную деплоем на реальном сервере владельца; фиксируется как явное ограничение, аналогично прежним ручным E2E-дисклеймерам (`0003-sms-webhook.md`).

**Проверено вручную через Docker** (`docker build` + `docker compose up`, локально в среде разработки после запуска Docker Desktop): `GET /healthz` → `200 {"status":"ok"}`; `/auth/login` после превышения burst → `429 {"error":"rate limit exceeded"}` с `Retry-After: 60`; именованный volume переживает `docker compose up -d --force-recreate` — пользователь, зарегистрированный до пересоздания контейнера, успешно логинится после. Пример nginx-конфига (`deploy/nginx.example.conf`) по-прежнему не тестируется автоматически и не применялся на реальном сервере владельца — только локальная Docker-часть проверена.

## Открытые вопросы / Backlog

- Горизонтальное масштабирование (несколько инстансов бэкенда за балансировщиком) потребует вынести состояние rate-limiter из памяти процесса (например, в Redis) — не актуально при текущем однопроцессном деплое, не входит в это MVP-по-эксплуатации.
- Rate-limiting на `GET /events` (SSE, долгоживущие соединения) и на остальные аутентифицированные эндпоинты — если понадобится после наблюдения реальной нагрузки.
- Автоматизация деплоя (CI/CD, автоматическое обновление образа на сервере) — вне этого milestone.
