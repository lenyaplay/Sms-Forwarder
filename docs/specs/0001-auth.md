# 0001 — Авторизация пользователей

**Статус:** Implemented

## Контекст

Пользователи (владельцы устройств-шлюзов и просматривающие) должны входить в систему по логину и паролю и получать токены для доступа к остальному API. Это базовая фича, от которой зависят все последующие защищённые эндпоинты (устройства, сообщения). См. `docs/Architecture.md`, раздел 4.

## API / интерфейс

Все запросы и ответы — `application/json`.

### `POST /auth/register`

Запрос: `{"login": "string", "password": "string"}`

- `login` — непустая строка, уникальна.
- `password` — минимум 8 символов.

Ответ `201 Created`: `{"access_token": "...", "refresh_token": "..."}`
Ошибки: `400` — невалидные поля; `409` — логин уже занят.

### `POST /auth/login`

Запрос: `{"login": "string", "password": "string"}`

Ответ `200 OK`: `{"access_token": "...", "refresh_token": "..."}`
Ошибки: `400` — невалидные поля; `401` — неверный логин или пароль.

### `POST /auth/refresh`

Запрос: `{"refresh_token": "string"}`

Ответ `200 OK`: новая пара `{"access_token": "...", "refresh_token": "..."}`. Старый refresh-токен отзывается (ротация).
Ошибки: `400` — отсутствует поле; `401` — токен не найден, отозван или истёк.

### `POST /auth/logout`

Запрос: `{"refresh_token": "string"}`

Ответ `200 OK`: `{}`. Помечает refresh-токен отозванным (идемпотентно — повторный вызов тоже 200).
Ошибки: `400` — отсутствует поле.

## Токены

- **Access-токен** — JWT (HS256), claim `sub` = user_id (строка), `exp`. TTL 15 минут. Подписан `JWTSecret` из конфига. Stateless, в БД не хранится.
- **Refresh-токен** — случайная строка (32 байта из `crypto/rand`, base64url), отдаётся клиенту в сыром виде. В БД (`refresh_tokens.token_hash`) хранится только SHA-256 хэш. TTL 30 дней. При каждом успешном `/auth/refresh` — ротация: старая запись помечается `revoked_at`, создаётся новая.
- Пароли — только bcrypt-хэш (`password_hash`), в открытом виде нигде не хранятся и не логируются.

## Модель данных

Использует существующие таблицы из `internal/migrations/0001_init.up.sql`, без изменений схемы:
- `users(id, login, password_hash, created_at)`
- `refresh_tokens(id, user_id, token_hash, expires_at, revoked_at, created_at)`

## Сценарии использования

1. Новый пользователь регистрируется → сразу получает пару токенов (залогинен).
2. Существующий пользователь логинится по логину/паролю → получает пару токенов.
3. Access-токен истёк → клиент вызывает `/auth/refresh` с refresh-токеном → получает новую пару, старый refresh-токен становится непригоден.
4. Пользователь выходит (`/auth/logout`) → refresh-токен отозван, дальнейший `/auth/refresh` с ним невозможен.

## Критерии приёмки

- Регистрация с новым логином → `201`, оба токена присутствуют и непустые.
- Повторная регистрация с тем же логином → `409`, новый пользователь не создан.
- Login с верным паролем → `200` с токенами; с неверным паролем или несуществующим логином → `401`.
- Refresh с валидным токеном → новая пара токенов, старый токен становится недействителен (повторное использование → `401`).
- Refresh с невалидным/просроченным/уже отозванным токеном → `401`.
- Logout → возвращает `200`, после него `/auth/refresh` этим токеном → `401`.
- Пароль в таблице `users` хранится как bcrypt-хэш, не как открытый текст.

## Тесты

- `internal/auth`: хэширование/проверка пароля (совпадающий/несовпадающий пароль); генерация и парсинг access-JWT (валидный, просроченный, невалидная подпись); генерация refresh-токена и его хэша (детерминированность хэша, уникальность значений).
- `internal/storage`: `CreateUser` + `GetUserByLogin`/`GetUserByID`; конфликт при дублирующемся логине; `SaveRefreshToken`/`GetRefreshTokenByHash`/`RevokeRefreshToken`.
- `internal/services`: `AuthService` — регистрация (успех/дубликат), login (успех/неверный пароль/несуществующий логин), refresh (успех с ротацией/повторное использование отозванного/просроченный), logout.
- `internal/handlers`: HTTP-сценарии end-to-end через `httptest` — все критерии приёмки выше, включая коды ответов и формат JSON.
