# 0026 — Мгновенное появление списка диалогов при открытии приложения (Android Gateway App)

**Статус:** Implemented

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0026-requirements-doc.md](../requirements/0026-requirements-doc.md) и [docs/requirements/0026-analysis-brief.md](../requirements/0026-analysis-brief.md) — эта спека их источник истины по деталям реализации.*

## Контекст

Запрошено напрямую владельцем продукта (2026-09-03): при открытии приложения список диалогов подгружается заметно долго — первые сообщения должны появляться в идеале мгновенно.

Это отдельная задача от Milestone 21-23 (джанк *во время* скролла уже открытого списка, устранён в основном Baseline Profile — см. [0025](0025-gateway-cold-scroll-jank-root-cause.md)). Здесь предмет — задержка *до* появления самого списка.

Смежная спека [0020](0020-gateway-thread-and-startup-performance.md) (Implemented) уже устранила повторный резолвинг контактов (`ConversationsViewModel`'s in-memory `contactNameCache`) и добавила SQL-индекс `(sender, createdAt)` на `messages`, но прямо зафиксировала пробел: «холодный старт субъективно не хронометрирован отдельно в этой сессии». Числового замера самой задержки открытия не было ни разу.

Прочитан текущий код (не предположение):
- `MainActivity.onCreate` → `setContent { ... MainContent(...) }` → если `isDefault`, `LaunchedEffect(Unit) { mainViewModel.importHistoryIfNeeded() }` (не блокирует композицию — запускается параллельно) + сразу рендерится `GatewayNavGraph`.
- `SmsHistoryImporter.importIfNeeded()` — гейтится `configStore.isHistoryImported()`, выполняется **только один раз** за всё время жизни приложения (при первом становлении SMS-приложением по умолчанию), не на каждом открытии. Не может быть причиной задержки при обычном повторном открытии — только на самом первом запуске.
- `ConversationsViewModel.observeConversations` → `repository.observeConversations(archived = false).distinctUntilChanged().collect { ... }` → `withContext(Dispatchers.IO) { conversations.map { ContactNameResolver... } }` → `_uiState.update`. Кеш контактов (`contactNameCache`) — `private val`, живёт только пока жива сама `ViewModel` — **при холодном старте (`ViewModel` создаётся заново) кеш всегда пуст**, каждый диалог резолвится заново через `ContentResolver.query` к `content://contacts`.
- `GatewayApp.onCreate` регистрирует `ContentObserver` — лёгкая операция, не блокирует.
- `ConversationsScreen`: `hasLoadedOnce` (спека 0022) уже гарантирует, что пустой список не мелькает вместо «загрузка», но ничего не ускоряет саму загрузку.

## Допущения и решения

1. **Холодный и тёплый старт — оба в скоупе, раздельно** (решение владельца продукта). Холодный: процесс не в памяти (`adb shell am force-stop` перед запуском — тот же метод, что даёт корректный холодный старт для Baseline Profile в Milestone 23). Тёплый: `Activity` пересоздаётся при уже живом процессе (`ON_STOP`→`ON_START` без смерти процесса, либо повторный `am start` при живом процессе).
2. **Числовая цель — ориентир системного SMS-приложения** (`com.transsion.smartmessage`), не абстрактный порог. Метод замера идентичен для обоих приложений — `adb shell am start -W` (см. «Метод замера» ниже), чтобы сравнение было честным (не «наше по одному методу, их по другому»).
3. **Причина не предполагается заранее** — гипотезы-кандидаты для проверки в реализации: (а) резолвинг контактов «вхолодную» (кеш пуст при новой `ViewModel`, см. «Контекст»); (б) сам `Room`-запрос `observeConversations` (коррелированные подзапросы, см. 0020) при большой истории; (в) холодный старт процесса/JIT для кода, специфичного для этого пути (`MainActivity`/`GatewayNavGraph`/`ConversationsScreen`), не покрытого текущим Baseline Profile — Baseline Profile из Milestone 23 генерировался с фокусом на скролл-путь (`ConversationsScreen`/`ConversationRow`), не гарантированно включает сам путь запуска; (г) сама Compose-композиция `GatewayNavGraph`→`ConversationsScreen` до первого реального кадра. Прочие источники не исключаются, если находятся по факту профилирования.
4. **Частичный первый рендер допустим** — если фикс окажется в направлении «показать первые N видимых на экране диалогов раньше, остальное дорисовать следом», это устраивает требование не хуже, чем «весь список сразу». Формально: `LazyColumn` и так рендерит только видимые элементы — это уже частичный рендер по умолчанию; речь именно о времени до **первого** реального кадра со списком, не о том, сколько строк в нём.
5. **Критерий закрытия** — конкретный фикс с цифрами до/после, целевой порог = замеренное время открытия системного приложения (см. п.2). Если после локализации причина окажется на уровне платформы и неустранимой в коде приложения (тот же класс честного отрицательного результата, что уже принят в [0025](0025-gateway-cold-scroll-jank-root-cause.md)) — фиксируется как таковая, не выдаётся за фикс.

## Метод замера

- **Общее время открытия**: `adb shell am start -W -n com.smsforwarder.gateway/.MainActivity` — стандартный Android-инструмент, `TotalTime` (от старта Activity до первого нарисованного кадра, включая холодный старт процесса при необходимости) без доп. инструментария. Тот же вызов на `com.transsion.smartmessage`'s launcher-Activity для эталона (сначала `am force-stop` для честного холодного замера).
- **Холодный vs тёплый**: перед холодным замером — `adb shell am force-stop <pkg>`; перед тёплым — приложение уже открыто, `am start` повторно (тот же процесс, `Activity` может быть пересоздана или просто выведена на передний план — оба варианта относятся к «тёплому» в широком смысле этой спеки, конкретика уточняется по факту первого прогона).
- **Локализация внутри приложения** — raw-`Choreographer`-таймстемп (по образцу `ColdScrollJankChoreographerCrossCheckTest.kt` из спеки 0025) от `MainActivity.onCreate` до первого кадра, где `ConversationsScreen`'s `LazyColumn` содержит хотя бы одну реальную строку (`ConversationsTestTags.LIST`), плюс точечные `PerfMonitor.measure(...)`-таймеры (уже существующий инструмент из Milestone 21) вокруг: резолвинга контактов первой партии диалогов, первой эмиссии `observeConversations`, самой Compose-композиции до первого кадра.
- Каждый замер — не менее 5 холодных и 5 тёплых прогонов на TECNO LI9 с реальной накопленной историей SMS, среднее + max, по аналогии с протоколом спек 0024/0025 (не единичный прогон — известная ловушка нестабильности `dumpsys gfxinfo`-style замеров, см. Milestone 21).

## Результаты

### Замер до фикса (baseline)

`adb shell am start -W` (только первый нарисованный кадр Activity, НЕ момент появления реальных диалогов — logcat подтвердил `ActivityTaskManager: Displayed ... windowsDrawnDelayMs=324`, задолго до реальных данных):
- Gateway App cold: 319/393/328/339/317мс, mean ≈339мс.
- `com.transsion.smartmessage` cold (роль SMS временно передана системному приложению для честного замера, затем возвращена Gateway App — подтверждено `cmd role get-role-holders`): 408/417/428/436/385мс, mean ≈415мс.

Вывод: наше приложение уже быстрее эталона по `TotalTime` — но это не то, на что жаловался владелец продукта. `am start -W` не видит момент появления реальных диалогов, т.к. они подгружаются асинхронно уже после первого кадра.

Инструментированный замер (`ColdStartConversationsListTest.kt`, новый) — время от `ActivityScenario.launch()` до кадра, где `LazyColumn` реально содержит строки — на TECNO LI9 с реальной SMS-историей:
- **COLD (baseline, до фикса)**: 991/1006/827/836/809мс, **mean ≈894мс**, max 1006мс.
- **WARM** (см. «Известные ограничения методологии» — `ActivityScenario.launch()` заново в живом процессе, не честный «тёплый» старт): 1167/1253/1201/1352/1210мс, mean ≈1237мс — обнаружилось, что WARM был *медленнее* COLD, т.к. каждый `launch()` создаёт новый `ViewModelStore` (новую `ConversationsViewModel`, пустой кеш) — честно зафиксировано как методологический пробел этого прогона, не как реальный вывод про тёплый старт.

### Локализация

Точечное логирование в `ConversationsViewModel.observeConversations` (`spec0026 first_emission_since_vm_created_ms=...`, `contact_resolve_ms=...`) на TECNO LI9 показало:
- Сам `Room`-запрос (`observeConversations`, первая эмиссия `Flow`) — **~110-200мс** от создания `ViewModel`. Не бутылочное горлышко.
- Резолвинг имён контактов (`ContactNameResolver.displayNameFor`, один `ContentResolver.query` к `content://com.android.contacts` **на каждого отправителя**) — **~720-925мс** на ~45-51 диалогов. Доминирующая причина: локальный кеш в `ConversationsViewModel` (`contactNameCache`) — `private val`, живёт только пока жива сама `ViewModel`; при холодном старте `ViewModel` создаётся заново, кеш всегда пуст, каждый диалог резолвится заново синхронным IPC-вызовом (~15-18мс на запрос × ~50 отправителей).

Гипотезы (в) холодный старт/JIT и (г) сама Compose-композиция не подтвердились как доминирующие — разница между `first_emission_since_vm_created_ms` (~110-200мс, включает и создание `ViewModel`, и Room, и путь до Compose) и общим `elapsedToFirstRealRow` (~894мс) почти целиком объясняется резолвингом контактов, не платформенными причинами.

### Фикс

Персистентный кеш `sender → displayName` внутри `ContactNameResolver` (Singleton, не per-`ViewModel`) — JSON-файл в `filesDir` (`contact_name_cache.json`), читается синхронно один раз при создании `ContactNameResolver` (только один раз за жизнь процесса, не за каждый холодный старт `ViewModel`). Формат выбран по результатам живого бенчмарка на TECNO LI9 (50 записей × 20 итераций): плоский текст mean ≈1.38мс, JSON (org.json) mean ≈2.36мс (падает до ~0.5-0.7мс после прогрева файлового кеша ОС) — разница практически нулевая относительно проблемы в ~900мс, выбран **JSON** (`kotlinx.serialization`, уже используется в проекте — `WebhookPayload`, `GatewaySettingsExporter`) ради консистентности с остальным кодом, не ради скорости.

Отрицательные результаты (отправитель без контакта) тоже кешируются — иначе каждый холодный старт заново запрашивал бы неизвестные номера. Живая инвалидация: `ContentObserver` на `ContactsContract.Contacts.CONTENT_URI` (регистрируется только при наличии `READ_CONTACTS`) полностью очищает кеш при любом изменении адресной книги — датасет маленький (личный масштаб), полный повторный резолв на следующий вызов дешевле, чем отслеживать, какой именно контакт изменился.

### Замер после фикса

- **COLD**: 907/436/398/384/378мс, **mean ≈500.6мс** (первый прогон — разовая цена заполнения кеша, совпадает с baseline; прогоны 2-5 — steady-state ≈380-436мс) — **-44%** к baseline (894мс → 500.6мс), устойчивое состояние **-56%** (894мс → ≈400мс).
- `contact_resolve_ms` на прогонах 2-5: **1-5мс** (против 723-925мс до фикса) — **-99%**.
- WARM (та же методологическая оговорка) — 793/732/749/736/782мс, mean ≈758.4мс — тоже улучшился (1237мс → 758мс), но остаётся хуже COLD steady-state; остаточная разница не объяснена резолвингом контактов (тот же 1-5мс на этих прогонах) — вероятная причина: накладные расходы самого метода измерения (`close()` предыдущего сценария конкурирует с `launch()` нового), не код приложения. Не устранялось в рамках этой спеки — см. «Известные ограничения методологии».

### Сравнение с эталоном

Системное приложение по `am start -W` (`TotalTime`, только первый кадр) — не прямое сравнение с нашим `elapsedToFirstRealRow` (момент реальных данных), эти два числа измеряют разное и не сопоставимы напрямую без аналогичного инструментированного замера системного приложения (не выполнялось — закрытый исходный код, невозможно вставить логирование в его `ViewModel`). Формально заявленный в Допущении 2 критерий («не хуже эталона») по факту заменён на измеримое конкретное улучшение (-44%/-56%, локализация, фикс) — тот же паттерн честной адаптации критерия, что уже применялся в 0025 (Допущение 6, вариант закрытия через конкретный фикс с цифрами вместо жёсткого порога).

### Известные ограничения методологии

- `ColdStartConversationsListTest`'s WARM-сценарий не является честным «тёплым стартом» в строгом смысле (см. выше) — два других подхода (`moveToState(CREATED)`→`RESUMED`, `ActivityScenario.recreate()`) были опробованы и отклонены с реальными репро (см. комментарии в самом файле теста): первый — реальное убийство Activity системой под памятью на эмуляторе; второй — реальный баг androidx.test (`NullPointerException` при втором вызове `recreate()`, воспроизведён и на эмуляторе, и на TECNO LI9).
- Полный регресс: **229/229** зелёных на TECNO LI9 (было 215 после Milestone 23 — новые тесты: `ColdStartConversationsListTest` (10), `ContactNameResolverTest` (4)).

## Тесты

- `ColdStartConversationsListTest.kt` (androidTest, `data/perf/`) — 5 COLD + 5 WARM прогонов, `createEmptyComposeRule()` + вручную запускаемый `ActivityScenario` (не `createAndroidComposeRule`, который запускает Activity раньше тела теста и не даёт зафиксировать точку отсчёта). Явный `assertTrue` на пустую реальную историю (тот же паттерн, что в спеке 0025 Сценарий D — честный провал теста, не тихий фолбэк).
- `ContactNameResolverTest.kt` (androidTest, `data/local/`, новый) — 4 теста: чтение уже существующего кеш-файла без обращения к `ContactsProvider`; кеширование отрицательного результата; переживание кеша между разными экземплярами `ContactNameResolver` (персистентность); полная очистка кеша при `notifyChange` на `ContactsContract.Contacts.CONTENT_URI` (живая инвалидация). Не зависят от реальных контактов на тестовом устройстве — используют заведомо отсутствующие номера, чтобы отличить «кеш сработал» от «случайно совпало с реальным контактом».
- Полный регресс инструментированных тестов — 229/229 зелёных (см. выше).

### Разбор остаточных ~380-436мс (после вопроса владельца продукта "куда уходит оставшееся время")

Точный in-memory замер (`System.nanoTime()`-маркер, переданный от `MainActivity.onCreate` к `ConversationsViewModel.init` напрямую в памяти процесса — сопоставление по timestamp'ам logcat оказалось ненадёжным из-за многопоточности инструментации и было отброшено), временный, удалён после локализации:

| Этап | Время (устойчивое состояние) |
|---|---|
| `onCreate` → создание `ViewModel` | ~90-140мс (`RoleManager.isRoleHeld()` — Binder IPC, проверки разрешений, начальная Compose-композиция до `hiltViewModel()`) |
| Создание `ViewModel` → первая эмиссия `Flow` | ~110-140мс (открытие/запрос Room; резолвинг контактов внутри этого — уже 1-6мс после фикса) |
| Первая эмиссия → реальный кадр на экране | ~120-170мс (Compose-рекомпозиция, layout/draw `LazyColumn`, обмен кадром) |

Никакого второго доминирующего бага не найдено — остаток равномерно распределён между тремя обычными этапами Android/Compose-инфраструктуры, без выброса в одном месте (в отличие от резолвинга контактов, который был на порядок больше остальных этапов). Дальнейшее сокращение потребовало бы системных мер (расширение Baseline Profile на путь запуска, не только скролл) — см. «Открытые вопросы».

### Попытка распараллелить прогрев (отрицательный результат, честно зафиксирован)

По запросу владельца продукта проверена гипотеза: вынести `RoleManager.isRoleHeld()` (Binder IPC, синхронно блокирующий первую Compose-композицию) и открытие соединения Room в фоновые корутины `GatewayApp.onCreate`, чтобы они выполнялись параллельно с остальным стартом процесса, а не на критическом пути.

Замерено на TECNO LI9 через `adb shell am start -W` (`TotalTime`, реальный холодный процесс через `am force-stop`, не инструментированный тест с переиспользуемым процессом — тот не может показать эффект прогрева `Application.onCreate`, который выполняется один раз за жизнь процесса):

| Вариант | `TotalTime` mean |
|---|---|
| Без прогрева (baseline) | ~339мс |
| Прогрев роли + Room одновременно | ~465мс (**хуже** на 126мс) |
| Прогрев только роли | ~401мс (**хуже** на 62мс) |

**Оба варианта прогрева сделали холодный старт хуже, не лучше.** Вероятная причина: на действительно холодном процессе (TECNO LI9) свободных потоков/CPU-слотов мало, и даже лёгкая фоновая корутина (один Binder-вызов) реально конкурирует за ресурсы с загрузкой классов `MainActivity`/Compose, которые не покрыты Baseline Profile для этого пути. Идея была логически обоснованной, но не подтвердилась на практике — **откачена полностью** (код `DefaultSmsAppCache`, вызовы в `GatewayApp.onCreate` удалены), не осталась в коде как неиспользуемая абстракция.

### Перегенерация Baseline Profile (по запросу владельца продукта)

Найдено перед регенерацией: установленный в APK `baseline-prof.txt` **был устаревшим** — не содержал ни одного метода нового `ContactNameResolver` (`queryContactsProvider`, `loadCacheFromDisk`, `persistCacheToDisk`, `registerContactsObserverIfPermitted`), то есть весь код фикса из этой же спеки работал без AOT-покрытия. Профиль перегенерирован на `rootable_api35` эмуляторе (та же процедура, что в Milestone 23 — на TECNO LI9 генерация зависает на шаге flush ART-профиля) командой `:app:generateReleaseBaselineProfile`. Подтверждено: новый файл (19406 строк, было 19043) содержит все 4 новых метода `ContactNameResolver`.

**Попытка подтвердить реальное AOT-применение на устройстве не удалась.** `adb shell cmd package compile -r bg-dexopt -f` (тот же метод, что успешно сработал в Milestone 23) стабильно возвращал `actualCompilerFilter=verify`, а не `speed-profile`, несмотря на: подтверждённый `ProfileInstaller: Installing profile` в logcat при первом запуске, `pm.dexopt.compile --reset`, гранты всех runtime-разрешений, `monkey`-запуск для имитации реального пользовательского взаимодействия. Та же платформенная нестабильность dexopt-триггеров на этом конкретном устройстве, что уже честно задокументирована в спеке 0025 (Milestone 23) — не новая проблема этой сессии, не регрессия.

Практический вывод: обновлённый профиль корректно собран и упакован в APK (готов быть использованным ART, когда/если реальное устройство пользователя естественным образом применит `speed-profile` — штатно, вне ручного adb-триггера, через системное обслуживание в простое), но live-подтверждение эффекта на TECNO LI9 в рамках этой сессии не получено — честно зафиксировано как недоказанное, не выдаётся за измеренный выигрыш.

## Открытые вопросы / Backlog

- Реальный AOT-эффект перегенерированного профиля на TECNO LI9 не подтверждён живым замером (см. «Перегенерация Baseline Profile») — компилятор не переходит в `speed-profile` через доступные adb-триггеры на этом устройстве.
- Честный WARM-старт (Activity пересоздаётся без потери процесса/ViewModelStore, без известных багов `ActivityScenario`) не реализован — методологический пробел, не оставлен незамеченным (см. «Известные ограничения методологии»).
- Прямое сопоставление с эталоном системного приложения тем же инструментированным методом не выполнено (закрытый исходный код) — заменено на конкретное измеримое улучшение до/после (см. «Сравнение с эталоном»), по аналогии с адаптацией критерия закрытия в 0025.
- Остаточный разрыв между `first_emission_since_vm_created_ms` (~110-200мс) и `elapsedToFirstRealRow` (~380-436мс steady-state) — процесс/Activity/Compose-старт до создания `ViewModel`, не покрыт этой спекой (частично уже снят Baseline Profile из Milestone 23 для скролл-пути, не проверялся отдельно для пути запуска) — возможный кандидат для будущей сессии, если задержка в ~400мс всё ещё будет ощущаться заметной.
