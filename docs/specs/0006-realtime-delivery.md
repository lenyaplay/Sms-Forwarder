# 0006 — Realtime-доставка сообщений (SSE)

**Статус:** Implemented

## Контекст

Milestone 5 (`docs/Roadmap.md`). До сих пор единственный способ узнать о новом SMS — периодически опрашивать `GET /devices/{id}/messages` (Milestone 4). Эта фича добавляет push-канал: подписанный клиент узнаёт о новом сообщении сразу после его приёма на `/webhook` (Milestone 3), без поллинга. REST-эндпоинт остаётся источником истины и используется для fallback при разрыве соединения и для начальной загрузки истории — realtime-канал ничего не заменяет, только дополняет.

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Транспорт — SSE (Server-Sent Events), не WebSocket.** Канал строго однонаправленный (server→client), клиенту не нужно ничего отправлять по тому же соединению. SSE реализуется на стандартном `net/http` без внешних зависимостей, браузерный клиент (`EventSource`) сам делает авто-реконнект — meньше кода и на сервере, и потенциально в будущем Web-просмотрщике (Backlog Milestone 8). Минус — Android (Milestone 6) не имеет встроенного SSE-клиента как браузер, потребуется обычный HTTP-клиент, читающий `text/event-stream` построчно (не блокер, но заметка для Milestone 6).
2. **Payload — полное сообщение**, в том же JSON-формате, что и элемент массива `messages` в `GET /devices/{id}/messages` (0005) — сериализация не дублируется в двух местах, клиенту не нужен дополнительный REST-запрос на каждое событие.
3. **Одно SSE-соединение может подписываться на несколько устройств одновременно** (`GET /events?device_ids=1,2,3`) — пользователь с несколькими устройствами (как owner, так и viewer на разных) получает единый поток, а не открывает по соединению на каждое.
4. **Аутентификация — `access_token` query-параметром** при открытии соединения (`GET /events?device_ids=...&access_token=...`), а не заголовком `Authorization`. Причина: браузерный `EventSource` не поддерживает произвольные заголовки при подключении — единственный практичный способ передать токен. Это то же компромиссное решение, что уже принято для query-based `upload_token`/`download_token` в 0002/0003; `access_token` добавляется в список известных секретов `internal/logging` (`RedactQuery`), чтобы не логироваться в открытом виде — расширение уже существующего механизма редакции (Milestone/спека 0004), не новый.
5. **Авторизация подписки на каждый `device_id`** — тот же `DeviceService.GetDevice(ctx, userID, deviceID)`, что и в `GET /devices/{id}/messages` (0005): owner или пользователь с активным `viewer_binding`. Если хотя бы один `device_id` из списка недоступен пользователю — весь запрос на подключение отклоняется `404` до открытия потока (не открывается поток с частичной подпиской и не присылается ошибка внутри уже открытого SSE — проще для клиента: либо подключился на всё, либо получил чёткую ошибку сразу).
6. **Отзыв/истечение `viewer_binding` во время уже открытого соединения не обрывает его активно.** Проверка доступа выполняется только в момент подключения (допущение 5). Причина: активный обрыв потребовал бы, чтобы каждая операция ревокации/наступления TTL в `DeviceService`/`storage` знала о живых SSE-соединениях и умела их находить и закрывать — существенно усложняет реализацию без веской необходимости для MVP на одном процессе. Последствие: если доступ отозван посреди сессии, пользователь может получить ещё несколько push-событий до разрыва соединения самим клиентом (переподключение/закрытие вкладки), но любой последующий `GET /devices/{id}/messages` уже вернёт `404` — источник истины (REST) остаётся корректным всегда, push — best-effort. Осознанное ограничение MVP, см. Backlog.
7. **Broadcast — in-process, в памяти**, без внешнего брокера (Redis и т.п.) — соответствует однопроцессной модели деплоя (`docs/Architecture.md` §6, тот же вывод уже сделан в допущении 6 спеки `0004-request-logging.md`). При будущем горизонтальном масштабировании потребуется вынести хаб во внешний pub/sub — явный Backlog, не блокирует MVP.
8. **Публикация события — синхронно после успешной вставки сообщения** в `MessageService.IngestWebhook`, до возврата ответа на `/webhook`. Дедуплицированные повторные доставки (тот же `body_hash`) **не** публикуют повторное событие — realtime-канал отражает только реально новые сообщения, симметрично с тем, что REST-дедуп уже возвращает существующую запись без создания новой.
9. **Fallback на REST-поллинг — целиком клиентское поведение**, сервер не предоставляет отдельного API под него: клиент при разрыве соединения продолжает опрашивать уже существующий `GET /devices/{id}/messages?since=<время последнего полученного сообщения>` до восстановления SSE. Отдельный "last delivered id"-маркер на сервере не нужен — курсор и так есть на клиенте (последнее полученное сообщение), а `since`-фильтр по `created_at` уже поддержан в 0005.
10. **Heartbeat/keep-alive** — сервер отправляет SSE-комментарий (`: ping\n\n`) каждые 30 секунд неактивности, чтобы прокси/балансировщики не закрывали простаивающее соединение по таймауту (частая практика для SSE за reverse-proxy) — не несёт данных, клиент его игнорирует.

## API / интерфейс

### `GET /events?device_ids=1,2,3&access_token=<token>`

Ответ — поток `Content-Type: text/event-stream`, HTTP-соединение остаётся открытым. `device_ids` — обязателен, список через запятую, от 1 до 20 id (защита от чрезмерной подписки без отдельного rate-limiting, аналогично `limit` в 0005). `access_token` — обязателен (вместо заголовка `Authorization`, см. допущение 4).

Каждое событие о новом сообщении:
```
event: message
data: {"id":42,"device_id":1,"sender":"+1234567890","text":"...","sent_stamp":"...","received_stamp":"...","sim":"1","created_at":"..."}

```
(поля идентичны элементу `messages[]` из `GET /devices/{id}/messages`, включая отсутствие `body_hash`). Heartbeat (допущение 10):
```
: ping

```

Ошибки (до апгрейда в `text/event-stream`, обычный JSON-ответ):
- `400` — `device_ids` отсутствует, пуст, содержит не-число, содержит больше 20 элементов, или `access_token` отсутствует.
- `401` — `access_token` невалиден (протухший/неверный JWT).
- `404` — хотя бы один `device_id` недоступен пользователю (не owner и нет активного `viewer_binding`) — тот же критерий, что в 0005.

Соединение закрывается сервером при: ошибке записи клиенту (клиент отключился), остановке сервера (graceful shutdown), таймауте `r.Context()` (стандартное поведение `net/http` при закрытии клиентом).

## Модель данных

Нет изменений в схеме БД. Никакого persistent-состояния подписок не заводится — хаб полностью в памяти процесса, живёт ровно пока живо соединение.

## Сценарии использования

1. Клиент открывает `GET /events?device_ids=1&access_token=...` при старте приложения (после первичной загрузки истории через `GET /devices/{id}/messages`) → держит соединение открытым.
2. Приходит SMS на телефон → Gateway App шлёт `/webhook` → `IngestWebhook` создаёт сообщение → тот же вызов публикует событие в хаб → все SSE-соединения, подписанные на этот `device_id`, немедленно получают `event: message`.
3. Повторная доставка того же webhook (retry Gateway App) → дедуп на REST-уровне (0003/0005), событие повторно не публикуется.
4. Соединение обрывается (сеть, фон приложения) → клиент детектит разрыв (`EventSource.onerror` либо таймаут чтения) → переключается на поллинг `GET /devices/{id}/messages?since=<last>` → при восстановлении сети снова открывает `/events`.
5. Владелец отзывает `download_token` viewer'а, у которого уже открыто SSE-соединение → соединение не рвётся сразу (допущение 6), но следующий `GET /devices/{id}/messages` этого viewer'а → `404`.
6. Пользователь с устройствами 1 (owner) и 2 (viewer) открывает одно соединение `?device_ids=1,2` → получает события по обоим в общем потоке, различая по полю `device_id` в каждом событии.

## Критерии приёмки

- Подключение к `/events` без `device_ids` или с невалидным элементом списка → `400`.
- Подключение без `access_token` или с невалидным → `401`.
- Подключение с `device_id`, недоступным пользователю → `404`, поток не открывается.
- После успешной вставки нового сообщения все подписанные на этот `device_id` открытые соединения получают `event: message` с полным JSON сообщения в течение разумного времени (тест — синхронно/near-synchronously в рамках одного процесса).
- Дублирующая (дедуплицированная) webhook-доставка не порождает повторное SSE-событие.
- Соединение с несколькими `device_ids` получает события от всех них в общем потоке.
- Событие никогда не содержит `body_hash`.
- `access_token` из query-строки никогда не попадает в открытом виде в логи (`internal/logging.RedactQuery`).
- Отзыв/истечение доступа не обрывает уже открытое соединение (допущение 6) — фиксируется явным тестом, чтобы поведение оставалось документированным решением, а не забытым пробелом.
- Heartbeat отправляется на простаивающем соединении (тест с укороченным интервалом).

## Тесты

- `internal/realtime` (новый пакет — hub): подписка/отписка, публикация события доходит до всех подписчиков `device_id`, публикация на `device_id` без подписчиков не паникует и не блокирует, отписка при закрытии соединения (нет утечки подписчиков — проверить `len(subscribers)` после закрытия), конкурентный доступ через горутины (без `-race`: инструмент требует cgo, недоступного в текущем окружении разработки — тот же осознанный компромисс, что и выбор `modernc.org/sqlite` без cgo для всего проекта; тест ловит гонки логически через `sync.Mutex`-защищённую структуру, `-race` можно прогнать локально при наличии cgo-тулчейна).
- `internal/services`: `MessageService.IngestWebhook` — публикует событие в хаб при успешной вставке, не публикует при дедупе (мок/стаб хаба или счётчик вызовов).
- `internal/handlers`: HTTP end-to-end через `httptest` — открыть `/events`, отправить `/webhook`, прочитать событие из потока (с таймаутом на чтение); невалидные `device_ids`/`access_token` → `400`/`401`; недоступный `device_id` → `404` без апгрейда в SSE; мульти-устройство в одном соединении; `body_hash` отсутствует в событии; `access_token` не в логах (переиспользовать паттерн `logging_test.go` из 0004).

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Активный обрыв соединения при ревокации/истечении доступа — осознанно отложено (допущение 6).
- Вынос хаба во внешний pub/sub (Redis и т.п.) при горизонтальном масштабировании — не нужен на этапе одного процесса.
- WebSocket, если в будущем понадобится client→server трафик по тому же каналу (например, отметки "прочитано") — не нужен для MVP push-уведомлений.
