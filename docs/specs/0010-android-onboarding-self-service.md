# 0010 — Многопользовательский онбординг и самообслуживание (Android)

**Статус:** Implemented

## Контекст

Milestone 9 (`docs/Roadmap.md`, планируется добавить этой спекой). Цель, сформулированная пользователем: сделать сервис удобным для всех пользователей самостоятельно, без прямых вызовов backend API. Сейчас (спека `0007`, MVP) в Android Viewer App: логин по уже существующему аккаунту (регистрация — только напрямую через `POST /auth/register`, минуя UI), захардкоженный server URL (`10.0.2.2:8080` для эмулятора), только сторона «ввести/отсканировать чужой `download_token`» — нет UI ни для генерации приглашения, ни для управления токенами устройства. Бэкенд уже поддерживает всё нужное (`0001-auth.md`, `0002-devices-tokens.md`) — эта спека добавляет только Android UI поверх существующих эндпоинтов, без изменений на бэкенде.

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Регистрация — открытая.** Экран регистрации в приложении вызывает существующий `POST /auth/register` без инвайт-кода или подтверждения администратора — любой, у кого есть адрес сервера, может создать аккаунт. Ограничение доступа к серверу (кто вообще может до него достучаться) — на усмотрение владельца развёртывания (firewall, VPN и т.п.), вне scope этой спеки.
2. **Server URL — настраиваемый экран, не константа.** Обязателен для мультипользовательского самостоятельного развёртывания на разных серверах. **Ограничение**: смена URL применяется через выход из приложения и повторный вход (пересоздание сетевого стека при активном логине не входит в scope — усложнение не оправдано для этого milestone). При первом запуске без сохранённого URL пользователь обязан пройти экран «Настройка сервера» до экрана логина.
3. **QR-код для приглашения (генерация) — добавляется.** Владелец устройства генерирует `download_token` (`POST /devices/{id}/download_tokens`) и показывает его как QR прямо в приложении — закрывает сценарий «пригласить второй аккаунт посмотреть SMS» полностью внутри UI, без прямых вызовов API. Используется генерация QR (не камера) — новая зависимость `com.google.zxing:core` (генератор без камеры/UI-обвязки ZXing, минимальный футпринт; сканирование уже использует CameraX+ML Kit из спеки `0007`, для генерации они не подходят).
4. **Базовый экран управления токенами устройства — добавляется.** Для владельца устройства: список выданных `download_token` с отзывом (`GET`/`DELETE /devices/{id}/download_tokens...`), просмотр текущего `upload_token` с перевыпуском (`POST /devices/{id}/upload_token`). «Базовый» значит без редактирования `label`/TTL через UI в этой версии — используются серверные дефолты; ручная установка TTL — Backlog.
5. **Распространение APK — вне scope.** Эта спека — только функциональность приложения. Способ доставки собранного APK пользователям (файл, внутренний трек, F-Droid) — отдельный будущий вопрос, не блокирует эту спеку.
6. **Регистрация не выполняет автоматический логин.** После успешной `201` от `POST /auth/register` пользователь возвращается на экран логина с уже заполненным логином (без пароля) — минимизирует новый код (не нужно дублировать логику сохранения токенов из `LoginViewModel` в отдельном пути), симметрично поведению большинства auth-форм.
7. **Экран регистрации не проверяет сложность пароля на клиенте сверх минимума длины** (совпадает с тем, что уже делает/не делает бэкенд — если бэкенд не валидирует сложность, клиент тоже не изобретает новых правил; проверить фактическое поведение `POST /auth/register` при реализации и не расходиться с ним).
8. **Экран «Настройка сервера» не проверяет валидность URL сетевым запросом на этом экране** — только базовая проверка формата (непустой, `http://`/`https://` префикс). Реальная проверка достижимости происходит естественным образом при следующем логине/регистрации (ошибка сети покажется на том экране, где она произошла) — не дублирует эту логику отдельным «Test connection» действием в этой версии (Backlog).
9. **Хранилище server URL — обычный (не Keystore-шифрованный) локальный стор**, в отличие от токенов (`TokenStore`, спека `0007`). URL сервера не секрет, шифрование не требуется — упрощение, не безопасность через неясность.

## API / интерфейс

Изменений на бэкенде нет — используются существующие эндпоинты:

- `POST /auth/register` (`0001-auth.md`) — экран регистрации.
- `POST /devices/{id}/download_tokens`, `GET /devices/{id}/download_tokens`, `DELETE /devices/{id}/download_tokens/{token_id}` (`0002-devices-tokens.md`) — генерация QR-приглашения и список/отзыв токенов.
- `POST /devices/{id}/upload_token` (`0002-devices-tokens.md`) — перевыпуск upload-токена устройства.
- `GET /devices/{id}` (`0002-devices-tokens.md`) — подтягивание текущего `upload_token`/списка токенов для экрана управления.

На Android-стороне: `ApiService` расширяется недостающими методами (`createDevice` уже частично используется тестами `0009`, но отсутствует в `ApiService` — добавляется вместе с `createDownloadToken`, `listDownloadTokens`, `revokeDownloadToken`, `reissueUploadToken`), с соответствующими DTO (`device_handlers.go`'s `deviceResponse`/`downloadTokenResponse` — поля см. `0002-devices-tokens.md`).

## Экраны и сценарии

### 1. Настройка сервера (новый, первый экран при пустом сохранённом URL)
- Поле ввода адреса сервера (например, `https://my-server.example.com`), базовая валидация формата (допущение 8).
- Сохранение → переход на экран логина.
- Доступен повторно из экрана логина («Изменить сервер») и из нового экрана настроек (см. ниже).

### 2. Регистрация (новый)
- Поля логин/пароль (+ подтверждение пароля), кнопка «Зарегистрироваться» → `POST /auth/register`.
- `201` → возврат на экран логина с предзаполненным логином (допущение 6).
- `409` (логин занят) → сообщение об ошибке, без выхода с экрана.
- Ссылка «Уже есть аккаунт? Войти» на экране логина ведёт сюда, и обратно.

### 3. Генерация QR-приглашения (новый, доступен с экрана деталей устройства владельца)
- Кнопка «Пригласить просмотр» → `POST /devices/{id}/download_tokens` → отображение результата как QR-кода (ZXing) + текстового значения токена (копирование).
- Ошибка создания токена (403 — не владелец, 500) → сообщение об ошибке.

### 4. Управление токенами устройства (новый, доступен с экрана деталей устройства владельца)
- Текущий `upload_token` (замаскированный/полный по тапу) + кнопка «Перевыпустить» (`POST /devices/{id}/upload_token`) с подтверждением (перевыпуск делает старый недействительным — Gateway App на устройстве перестанет слать данные, пока не обновить токен там).
- Список выданных `download_token` (`GET .../download_tokens`) с меткой создания/использования и кнопкой отзыва по каждому (`DELETE .../download_tokens/{token_id}`) с подтверждением.
- Только для владельца (`role == "owner"`) — для viewer-роли этот экран/кнопки не показываются вовсе (роль уже приходит в `GET /devices`, спека `0002` допущение 7).

### 5. Настройки (новый, минимальный)
- Текущий server URL (не редактируется на этом экране; переход на экран «Настройка сервера» пункт 1) + предупреждение «требуется повторный вход» при переходе туда.
- Logout (уже существует, `0007`) — переносится сюда из текущего места, если применимо, либо остаётся как есть — решается при реализации по факту текущего размещения.

## Модель данных

Нет изменений в серверной схеме. На клиенте — новый локальный (не Keystore-шифрованный, допущение 9) стор для server URL, читаемый синхронно при старте приложения до построения сетевого стека (аналогично тому, как сейчас `NetworkModule.provideBaseUrl()` отдаёт константу — меняется на чтение из этого стора с фоллбэком на экран «Настройка сервера», если пусто).

## Критерии приёмки

- При первом запуске без сохранённого URL — показывается экран «Настройка сервера» раньше экрана логина; после сохранения — обычный флоу логина/регистрации.
- Успешная регистрация создаёт аккаунт на бэкенде и возвращает на экран логина с предзаполненным логином; занятый логин показывает ошибку без падения.
- Смена server URL на экране настроек и повторный вход подключают приложение к новому серверу (проверяется явным логином на новый адрес после смены).
- Владелец устройства может сгенерировать QR с `download_token`, и этот же токен, введённый вручную на другом аккаунте, успешно привязывает устройство (сквозной сценарий «владелец генерирует → viewer сканирует/вводит → устройство появляется у viewer'а»).
- Владелец устройства видит список выданных `download_token` и может отозвать любой — после отзыва этот токен больше не принимается `POST /devices/bindings` (`401`).
- Владелец может перевыпустить `upload_token` — новый токен отображается, старый перестаёт приниматься `POST /webhook`.
- Viewer (не владелец) не видит экран управления токенами/кнопку генерации приглашения для устройств, где он не владелец.

## Тесты

- **Unit (JVM):** валидация формата URL на экране настройки сервера; ViewModel-логика экрана регистрации (успех/409/сетевая ошибка); ViewModel-логика управления токенами (список/отзыв/перевыпуск, включая обработку 403 для не-владельца — на случай прямого вызова в обход UI-скрытия).
- **Instrumented/UI:** экран настройки сервера (валидный/невалидный URL); экран регистрации (успех переводит на логин с предзаполненным логином, занятый логин показывает ошибку); экран генерации QR (кнопка → QR отображается); экран управления токенами (список отображается, кнопки отзыва/перевыпуска вызывают подтверждение и обновляют список).
- **Против реального бэкенда** (пакет `com.smsforwarder.viewer.realbackend`, спека `0009`): сквозной сценарий «регистрация через экран → логин → генерация QR-приглашения → второй аккаунт вводит токен → устройство появляется» — новый тест в этом же пакете, тем же паттерном (реальный `ApiService`, не фейк), закрывающий цепочку регистрация+инвайт целиком, которую спека `0009` не покрывала (там пользователи заводились напрямую через API, а download_token минтился напрямую через HTTP, а не через UI).

**Проверено вручную**: полный сценарий (регистрация → логин → создание устройства → генерация download_token → редемпшн вторым аккаунтом → список токенов → отзыв → повторный редемпшн отклонён 401 → перевыпуск upload_token → старый токен отклонён `/webhook` 401, новый принят 201) прогнан через реальный бэкенд в Docker — по HTTP напрямую (сверка wire-контракта DTO) и через реальные экраны (`RegisterScreen`/`LoginScreen`/`DeviceDetailScreen`/`AddDeviceScreen`) в новом инструментированном тесте `RealBackendOnboardingTest` (пакет `com.smsforwarder.viewer.realbackend`). `./gradlew :app:connectedDebugAndroidTest` (без бэкенда) — 26 тестов, 0 падений, `realbackend`-пакет по-прежнему изолирован.
