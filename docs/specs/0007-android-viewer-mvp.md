# 0007 — Android Viewer App (MVP)

**Статус:** Implemented

## Контекст

Milestone 6 (`docs/Roadmap.md`). Бэкенд полностью готов через Milestone 5: авторизация (`0001-auth.md`), устройства/токены (`0002-devices-tokens.md`), приём SMS (`0003-sms-webhook.md`), REST-чтение сообщений (`0005-viewer-messages-api.md`), realtime-push (`0006-realtime-delivery.md`). Эта фича — первый реальный клиент этих API: минимальное Android-приложение для просмотра пересланных SMS. До сих пор существует только пустой Kotlin-шаблон проекта (Milestone 0).

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Привязка устройства по `download_token` не требует нового серверного эндпоинта.** `POST /devices/bindings` (`0002-devices-tokens.md`) уже принимает `download_token` от любого аутентифицированного пользователя и создаёт `viewer_binding`. Android-экран «добавить устройство» — это просто клиент этого существующего эндпоинта, без изменений на бэкенде.
2. **UI — Jetpack Compose.** Меньше boilerplate для ленты с realtime-обновлением, чем Views/XML; стандарт для новых Android-проектов.
3. **Сетевой стек — Retrofit + OkHttp, DI — Hilt.** Retrofit для обычных REST-вызовов (`/auth/*`, `/devices*`); `GET /events` (SSE) читается отдельным OkHttp-запросом с построчным разбором `text/event-stream` вручную — готового SSE-клиента в OkHttp/Retrofit нет (см. допущение 1 спеки `0006`, зафиксировано заранее).
4. **Хранение токенов — прямой Android Keystore API**, не `EncryptedSharedPreferences`-обёртка. Access и refresh токены шифруются ключом, привязанным к Keystore устройства, перед записью в `SharedPreferences`/файл.
5. **Тестирование — unit-тесты (JVM, без эмулятора) + instrumented/UI-тесты (Espresso/Compose testing на эмуляторе/устройстве).** Оба уровня обязательны для этой фичи, согласуется с общим правилом «автотесты обязательны» (`docs/DEVELOPMENT.md`), адаптированным под Android: unit — для ViewModel/repository/парсинга SSE-потока; instrumented/UI — минимум по одному smoke-тесту на экран (логин, список устройств, добавление по токену, лента).
6. **QR-код — в этом же MVP**, не откладывается в Backlog. Роадмап явно упоминает QR как часть Milestone 6 («ручной ввод / QR-код») — оставляем обе опции ввода `download_token`.
7. **Realtime — только foreground.** SSE-соединение (`GET /events`) живёт, пока приложение активно на экране (`Activity`/`ViewModel` с жизненным циклом, привязанным к видимому экрану). Фоновая доставка (когда приложение свёрнуто/закрыто) — через FCM push, это отдельный явный пункт `docs/Roadmap.md` Milestone 8 (Backlog), не входит в это MVP. При сворачивании приложения SSE-соединение закрывается клиентом; при возврате на экран — открывается заново, история досинхронизируется через `GET /devices/{id}/messages?since=<last>` (та же логика, что клиентский fallback при разрыве сети, допущение 9 спеки `0006`).
8. **Refresh-токен ротация** — при истечении access-токена клиент вызывает `POST /auth/refresh` (`0001-auth.md`) прозрачно (единая точка — OkHttp `Authenticator`/interceptor), без участия пользователя; при невалидном/отозванном refresh-токене — разлогинивание и возврат на экран логина.
9. **Экран логина не включает регистрацию.** `POST /auth/register` уже существует на бэкенде (`0001-auth.md`), но экран регистрации в UI — не обязателен для MVP: предполагается, что пользователь уже зарегистрирован (например, через тот же бэкенд-API напрямую или предыдущим релизом). Если потребуется — отдельный backlog-пункт, не блокирует этот milestone.

## API / интерфейс

Изменений на бэкенде нет — Android-клиент использует существующие эндпоинты:

- `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` (`0001-auth.md`)
- `GET /devices` (`0002-devices-tokens.md`, допущение 7)
- `POST /devices/bindings` (`0002-devices-tokens.md`)
- `GET /devices/{id}/messages` (`0005-viewer-messages-api.md`) — начальная загрузка ленты и REST-поллинг fallback
- `GET /events` (`0006-realtime-delivery.md`) — realtime push, foreground only

## Экраны и сценарии

### 1. Экран логина
- Поля логин/пароль → `POST /auth/login`.
- Успех: access+refresh сохраняются через Keystore-шифрование, переход на список устройств.
- Ошибка (`401` неверные креды, сетевая ошибка) — сообщение об ошибке на экране, без выхода из него.

### 2. Список устройств
- `GET /devices` при открытии экрана.
- Отображение: имя устройства, роль (`owner`/`viewer`).
- Пустой список — состояние "нет устройств, добавьте по токену".
- Переход на ленту сообщений по тапу на устройство.
- Кнопка/переход на экран добавления устройства.

### 3. Добавление устройства по `download_token`
- Поле ручного ввода токена (текст) **или** сканирование QR-кода (камера) → результат сканирования подставляется в то же поле.
- `POST /devices/bindings` с введённым/отсканированным токеном.
- `201` → устройство появляется в списке (обновление списка или переход назад с успехом).
- `401` (токен неизвестен/истёк/отозван) → сообщение об ошибке.
- `409` (уже есть binding, либо владелец пытается добавить себе своё устройство) → сообщение об ошибке.

### 4. Лента сообщений устройства
- При открытии: `GET /devices/{id}/messages` (первая страница, без параметров) → отображение, новые сверху (порядок уже гарантирован сервером, допущение 3 спеки `0005`).
- Подгрузка старых сообщений при скролле вниз → `before_id` из `next_before_id`.
- Открытие SSE-соединения `GET /events?device_ids=<id>&access_token=<access_token>` — новые сообщения добавляются в начало ленты по мере получения `event: message`.
- Разрыв соединения (сетевая ошибка/`onerror` эквивалент в ручном SSE-клиенте) → клиент переключается на периодический REST-поллинг `GET /devices/{id}/messages?since=<created_at последнего полученного сообщения>` до восстановления сети → пере-открытие SSE.
- Экран уходит в фон (`onStop`) → SSE-соединение закрывается явно; возврат в foreground (`onStart`) → повторное открытие SSE + один `since`-запрос для досинхронизации пропущенного за время в фоне.

## Модель данных

Нет изменений в серверной схеме БД. На клиенте — локальное хранилище токенов (Keystore-шифрованный `SharedPreferences`/файл), в остальном приложение stateless относительно сервера (не заводится локальная БД/кэш сообщений на этом MVP — при каждом открытии ленты грузится заново с сервера; офлайн-кэш — не входит в scope, потенциальный Backlog).

## Критерии приёмки

- Успешный логин сохраняет токены и переводит на список устройств; неверные креды показывают ошибку без падения.
- Список устройств показывает owned и viewer устройства с ролью; пустой список показывает соответствующее состояние.
- Ввод валидного `download_token` вручную добавляет устройство в список.
- Сканирование QR с тем же значением токена даёт тот же результат, что ручной ввод.
- Невалидный/отозванный/просроченный токен → показывается ошибка, устройство не добавляется.
- Лента показывает сообщения новыми сверху, пагинация подгружает более старые без дублей/пропусков.
- Новое сообщение, пришедшее пока лента открыта на экране, появляется без ручного обновления (через SSE).
- При разрыве SSE-соединения лента продолжает получать новые сообщения через поллинг-fallback (может быть с задержкой, но без потери сообщений при следующем `since`-запросе).
- При сворачивании и возврате в приложение лента досинхронизируется (не показывает дыру в истории).
- Access-токен истёк во время сессии → прозрачный refresh без разлогинивания пользователя (пока refresh-токен валиден).
- Refresh-токен невалиден/отозван → пользователь возвращается на экран логина.
- Токены на диске зашифрованы через Keystore (не хранятся открытым текстом).
- Logout явно отзывает refresh-токен на сервере (`POST /auth/logout`) и очищает локальное хранилище.

## Тесты

- **Unit (JVM):**
  - Парсинг `text/event-stream` построчно (`event:`, `data:`, `: ping` игнорируется, накопление многострочного `data:` при необходимости) — на синтетических входных потоках, включая обрыв соединения посередине события.
  - ViewModel/repository логики: переключение на поллинг-fallback при ошибке SSE; переход в fallback и обратно; дедуп при пересечении сообщений между SSE-событием и последующим `since`-поллингом (по `id`).
  - Refresh-токен interceptor: успешный silent refresh, невалидный refresh → триггер логаута.
  - Сохранение/чтение токенов через Keystore-обёртку (мокнутый или тестовый Keystore-провайдер, если тестовое окружение не даёт реальный Keystore).
- **Instrumented/UI (Espresso/Compose testing):**
  - Экран логина: успешный вход переводит на список устройств; неверные креды показывают ошибку.
  - Список устройств: отображение owned/viewer записей, пустое состояние.
  - Добавление устройства: успешный ввод токена добавляет устройство в список; ошибочный токен показывает сообщение об ошибке.
  - Лента сообщений: отображение начальной страницы, подгрузка при скролле.
  - (Реальное end-to-end SSE в UI-тесте не гарантируется стабильным на CI — REST-часть покрывается instrumented-тестами против поднятого тестового бэкенда/мока, SSE-логика — unit-тестами парсера и fallback выше; при необходимости живой SSE проверяется вручную, аналогично ручному E2E из Milestone 3.)

**Известное ограничение окружения тестирования** (осознанное, не забытый пробел — аналогично отсутствию `-race` в бэкенде из-за отсутствия cgo, спека `0006`): `connectedDebugAndroidTest` прогонялся и на эмуляторе, и на слабом физическом устройстве; на физическом устройстве один Compose UI тест (`AddDeviceScreenTest`) периодически ловит `IllegalStateException: No compose hierarchies found` — известный тайминг-флейк `createComposeRule()` на медленном железе, не воспроизводится на эмуляторе, не связан с логикой приложения.

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Экран регистрации в UI (`POST /auth/register` уже есть на бэкенде) — не входит в MVP (допущение 9).
- Локальный офлайн-кэш сообщений (локальная БД, просмотр без сети) — не входит в MVP.
- Push-уведомления через FCM при свёрнутом/закрытом приложении — отдельный пункт `docs/Roadmap.md` Milestone 8.
- Точечное управление несколькими `download_token` устройства (просмотр списка, отзыв) с самого Android-клиента — на MVP управление токенами предполагается через владельца (веб/API напрямую), Android viewer только потребляет `download_token` для привязки.
- `@Preview` для каждого экрана (`LoginScreen`, `DeviceListScreen`, `AddDeviceScreen`, `MessageFeedScreen`) и для переиспользуемых компонентов (например, `MessageCard`) — для быстрой итерации по UI в Android Studio без сборки/запуска приложения. Не входило в MVP, добавить отдельно.
