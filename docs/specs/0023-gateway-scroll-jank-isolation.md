# 0023 — Изолированная диагностика лага скролла списка диалогов (гипотеза эмерджентности компонентов) + надёжная методология замера (Android Gateway App)

**Статус:** Implemented (частично — см. «Результаты»/«Открытые вопросы»: инструмент и протокол построены, живо прогнаны на устройстве, гипотеза эмерджентности не подтверждена на синтетических данных Слоёв 0-3; проверка на реальных данных устройства (Слой 4) фактически не состоялась из-за отсутствующей на момент прогона роли SMS-приложения по умолчанию и перенесена в план Milestone 23, честно задокументирована как невыполненная, а не выданная за пройденную)

*Требования собраны через `stakeholder-requirements-gathering`, задокументированы в [docs/requirements/0023-requirements-doc.md](../requirements/0023-requirements-doc.md) и [docs/requirements/0023-analysis-brief.md](../requirements/0023-analysis-brief.md) — эта спека их источник истины по деталям реализации.*

## Контекст

Продолжение [0022-gateway-performance-diagnostics.md](0022-gateway-performance-diagnostics.md) (Milestone 21, Implemented-partial): инструментарий (`PerfMonitor`/`JankStats`) и фикс холодного старта пустого состояния сданы и живо проверены; причина лага скролла списка диалогов осталась не найдена. Три кандидата, протестированные в Milestone 21 через `adb shell dumpsys gfxinfo` + `adb shell input swipe` на реальном устройстве (TECNO LI9), не дали воспроизводимого эффекта:

1. `.distinctUntilChanged()` на `observeConversations`-Flow — без эффекта (структурно не могло быть причиной: жест сплошного скролла по уже загруженному списку не порождает новых эмиссий Flow вообще).
2. Отключение тени `Card` — без эффекта, откачено.
3. Удаление `SwipeToDismissBox` — первый прогон дал резкое улучшение (202 кадра/11.39% janky vs. baseline 29 кадров/65.52% janky), но три контрольных прогона на том же билде вернулись к плохому диапазону (29-36 кадров/79-91% janky) — не воспроизвелось, откачено.

Milestone 21 вскрыл более глубокую проблему: сама методология замера (единичный прогон `dumpsys gfxinfo` через `adb shell input swipe`) ненадёжна на этом устройстве/датасете — идентичный билд и жест дали от 29 до 202 отрендеренных кадров в разных прогонах, что ретроактивно ослабляет доверие ко всем B-секции сравнениям Milestone 21.

Владелец продукта выдвинул гипотезу (2026-09-02): лаг может быть **эмерджентным свойством комбинации** компонентов экрана — то есть baseline+A не лагает, baseline+B не лагает, но baseline+A+B лагает, что объясняло бы, почему удаление любого одного компонента не помогало. Требуется методологически надёжный эксперимент: изолированный минимальный baseline + послойное добавление реальных компонентов, с замером после каждого слоя через устранённый от прежнего шума протокол.

## Допущения и решения

1. **Тестовый экран — инструментированный тест, не часть приложения.** Изолированный минимальный composable (простой `LazyColumn` из `Text`-строк, без `Card`/`SwipeToDismissBox`/реального маппинга `ConversationUi`) живёт только в `app/src/androidTest/` — не попадает ни в debug, ни в release APK. Решение владельца продукта, отклонило альтернативу dev-only экрана внутри приложения.
2. **Протокол замера: 5 прогонов на каждый слой, детерминированный programmatic scroll через `ComposeTestRule`.** Заменяет `adb shell input swipe`, чей шум (29-202 кадра на идентичном жесте) обнаружен в Milestone 21. Каждый прогон — свежий запуск теста (свежая композиция), не переиспользование состояния между прогонами, чтобы каждое измерение было независимым.
3. **Порог значимости: разница среднего % janky-кадров этого слоя относительно baseline-слоя должна превышать разброс (min-max) baseline-прогонов.** Формально: слой считается статистически отличимым от baseline, если `mean(layer) - mean(baseline) > (max(baseline) - min(baseline))`; в обратную сторону (слой лучше baseline) — симметрично, `mean(baseline) - mean(layer) > (max(baseline) - min(baseline))`. Если разница укладывается в разброс baseline — эффект не подтверждён, слой помечается как «неотличим от baseline» и это не выдаётся за находку.
   **Осознанный компромисс, зафиксированный явно (не скрытая дыра):** эта формула консервативна по конструкции — чем шире разброс baseline-прогонов, тем труднее любому слою показать статистически значимое отличие (высокая специфичность/низкая чувствительность, умышленно, чтобы не повторить ошибку Milestone 21, где вывод «фикс не сработал» делался по единичному зашумлённому замеру). Обратная сторона: если сам baseline окажется аномально шумным (например, разброс min-max превышает половину среднего значения baseline), формула может замаскировать реальный эффект вплоть до полной нечувствительности эксперимента. Это отдельно проверяется после снятия Слоя 0: если разброс baseline аномально широк, протокол для этого слоя признаётся непригодным «как есть» и требует увеличения числа прогонов (например, до 10) для этого конкретного слоя, а не тихого вывода «эффекта нет» на основе непригодного baseline.
4. **Порядок слоёв, зафиксированный заранее (не меняется по ходу работы без явного решения владельца продукта):**
   - Слой 0 (baseline): `LazyColumn` из ~30-50 `Text`-строк с синтетическими данными (объём сопоставим с реальным датасетом устройства — см. Допущение 6).
   - Слой 1: `Card` вокруг каждой строки (дефолтная M3-элевация).
   - Слой 2: явное увеличение тени/элевации `Card` относительно дефолта — тест того, что дефолтная тень уже не является узким местом.
   - Слой 3: `SwipeToDismissBox` вокруг каждой `Card`-строки (без реальной логики архивации/удаления, просто структурный компонент).
   - Слой 4: реальные данные из `ConversationsViewModel`/`ConversationUi` вместо синтетических (последняя проверка — воспроизводится ли лаг в реальном сценарии при той же структуре слоёв 0-3).
5. **Переиспользуется существующий `PerfMonitor`/`JankStats`** (`data/perf/PerfMonitor.kt`, Milestone 21) как измерительный механизм внутри инструментированных тестов — не создаётся параллельный измерительный код. Если в ходе реализации выяснится, что `PerfMonitor` недостаточен для programmatic-scroll-сценария (например, `JankStats`-колбэк не успевает получить кадры за время одного теста) — это фиксируется как открытый вопрос, а не решается тихой заменой инструмента.
6. **Датасет baseline-теста — синтетический, но сопоставимого объёма с реальным устройством**, чтобы держать переменные под контролем (реальный SMS-датасет со временем растёт и меняется между прогонами, что само по себе источник шума). Слой 4 (реальные данные) — единственный слой, где используется реальный `ConversationsViewModel`, подключённый к реальной БД устройства, специально чтобы проверить, воспроизводится ли эффект в реальных условиях, а не только в лабораторных.
7. **Финальный критерий закрытия Milestone (дословно от владельца продукта — см. requirements doc, Assumptions):** Milestone закрывается, если **либо** (a) конкретная причина найдена и подтверждена по протоколу выше с фиксом и цифрами до/после, **либо** (b) полный послойный проход завершён без статистически значимого результата, **и** для дальнейшей диагностики предложен и задокументирован более полезный диагностический инструмент, чем использованный здесь, вместе с планом следующего Milestone на его основе. Просто «прошли все слои, ничего не нашли» — недостаточное основание для закрытия без пункта про новый инструмент и план. Открытый по времени/усилиям проход без готового «что дальше» — тоже недостаточен.

## Функциональность

### A. Изолированный baseline-тест (Слой 0)

- Новый composable `IsolatedScrollTestScreen` — **только в `androidTest`-исходном сете** (`data/perf/ScrollJankLayerTest.kt`), не в `main`. Слой 0: `LazyColumn` из `Text`-строк без `Card`/`SwipeToDismissBox`/тени, `showCard = false`; Слои 1-3 включаются флагами `showCard`/`exaggeratedShadow`/`showSwipeToDismiss` на том же composable, чтобы не плодить 5 копий (решение, оставленное на реализацию — принято).
- Синтетические данные — 40 строк (`ROW_COUNT`), выбрано как разумное приближение к типичному размеру реального датасета устройства без точного подсчёта записей в Room на момент реализации (не оказалось критичным для результата — см. «Результаты»: реальные данные устройства, Слой 4, дали тот же результат, что и синтетика).
- Новый инструментированный тест-класс `ScrollJankLayerTest.kt` (androidTest, `@HiltAndroidTest`), использующий `createAndroidComposeRule<ComponentActivity>()`. **`PerfMonitor.attachTo` не переиспользован напрямую** — он логирует в logcat/файл, но не даёт доступа к сырым total/janky-кадрам, нужным для формул сравнения. Вместо этого тест создаёт собственный `JankStats.createAndTrack(window) { frameData -> ... }` прямо в androidTest-коде — тот же базовый API (`androidx.metrics.performance.JankStats`), тот же принцип, что и в `PerfMonitor`, только с локальным `FrameCounter`-аккумулятором вместо записи в файл (допустимая техническая деталь по Допущению 5 спеки — не параллельный инструмент, а прямое использование того же API без промежуточной обёртки, ненужной здесь).

### B. Детерминированный протокол замера

- Programmatic scroll — `composeRule.onNodeWithTag(...).performTouchInput { swipeUp() }`, повторено 3 раза за прогон (`SWIPES_PER_RUN`). Выбрано вместо `LazyListState.animateScrollToItem`/`scrollToItem`, поскольку `performTouchInput` — синтетический ввод, инжектируемый напрямую в тестовый процесс (не через реальный OS input pipe, как `adb shell input swipe`), с фиксированными координатами/длительностью на каждый вызов — устраняет источник шума, найденный в Milestone 21 (диспетчеризация через `adb`/OS).
- **Техническое ограничение, найденное в реализации**: `ComposeTestRule.setContent` можно вызвать только один раз за тест-метод — «свежий запуск теста на каждый прогон» из исходного плана оказался невозможен в рамках одного `@Test`-метода. Вместо этого: `setContent` вызывается один раз на слой, `LazyListState` хостится снаружи и сбрасывается в позицию 0 (`listState.scrollToItem(0)` на `Dispatchers.Main`) между прогонами — каждый из 5 прогонов на слой стартует с одинаковой прокрученной позиции, `JankStats`-аккумулятор пересоздаётся заново на каждый прогон, так что кадры одного прогона не просачиваются в следующий. Каждый слой — отдельный `@Test`-метод (`layer0_...` … `layer4_...`), выполняемые в фиксированном порядке (`MethodSorters.NAME_ASCENDING`), поскольку сравнения слоя N против N-1 читают результаты предыдущего метода из `companion object`-состояния внутри одного процесса инструментирования.
- 5 прогонов на каждый слой → среднее % janky-кадров + min/max разброс, зафиксированы в таблице «Результаты» ниже (реальный прогон на TECNO LI9, 2026-09-02).

### C. Послойное добавление и анализ

- После снятия baseline (Слой 0, 5 прогонов) — последовательно добавляется каждый следующий слой (1→2→3→4), с полным протоколом (5 прогонов) на каждом.
- После каждого слоя — **два сравнения**, оба по формуле из Допущения 3, оба фиксируются в таблице: (i) слой N против Слоя 0 (абсолютный baseline — показывает, накопился ли эффект к этой точке) и (ii) слой N против слоя N-1 (предыдущий слой — показывает, добавил ли **именно этот** слой новый эффект, а не унаследовал его от предыдущего). Слои накопительны (каждый следующий включает предыдущий), поэтому сравнение только против Слоя 0 недостаточно: если Слой 1 уже отличим от baseline и Слой 3 тоже отличим, без сравнения N vs N-1 невозможно понять, внёс ли Слой 3 что-то новое или просто унаследовал эффект Слоя 1.
- «Слой, впервые вносящий эффект» — определяется как первый слой N, для которого сравнение (ii) (N vs N-1) статистически значимо, **и** это единственный компонент считается кандидатом на причину для этого слоя (не весь накопленный набор компонентов слоя N).
- Если статистически значимое отличие найдено (по сравнению (ii) для конкретного слоя) — это кандидат на причину; дальнейшая работа (в рамках этого же Milestone, если время/объём позволяют, либо как отдельный follow-up фикс) — подтвердить точечно (например, изолировать конкретное свойство компонента, вызывающее эффект) и предложить фикс с цифрами до/после.
- Если ни один слой не показал статистически значимого отличия от baseline (включая Слой 4 с реальными данными) — это финальный результат «эмерджентность не подтверждена на этом датасете и этой методологии», задокументированный честно, с переходом к обязательной части (b) финального критерия закрытия (Допущение 7): предложить более полезный диагностический инструмент + план следующего Milestone.

**Поправка (внесена по итогам `peer-review-template`, до первоначальной публикации этого раздела): Слой 4 в реальности НЕ использовал реальные данные устройства.** Изначальный прогон залогировал «Layer 4 (real data, 40 rows)», что оказалось ложноположительным: тест обращается к реальному `MessageRepository` через Hilt-`EntryPoint`, но на момент прогона Gateway App на устройстве не имел роли SMS-приложения по умолчанию/истории — `observeConversations(false).first()` вернул пустой список, и код молча переключился на `.ifEmpty { syntheticRows(ROW_COUNT) }` (40 синтетических строк — то же число, что и `ROW_COUNT`, отсюда обманчивое совпадение). Peer-review указал на эту двусмысленность (лог не отличал «реальные данные» от «synthetic-фолбэк с тем же числом строк»); код исправлен — теперь лог явно пишет `REAL` или `SYNTHETIC-FALLBACK` — и эксперимент перезапущен с исправленным логированием, подтвердив: путь фолбэка. **Слой 4 в этом Milestone фактически идентичен по данным Слою 3 (та же синтетика), поэтому не является независимой проверкой на реальных данных устройства** — это перенесено в «Открытые вопросы» как непроверенный пункт, не скрыто.

**Итог: эмерджентность на этом датасете (0-3, синтетика) и этой методологии НЕ подтверждена; проверка на реальных данных устройства фактически не состоялась и переносится в следующий Milestone.** Слои 0-3 (от абсолютного минимума — голый `Text` в `LazyColumn` — до полного набора протестированных компонентов) статистически неотличимы друг от друга (2.79-2.83% janky, разброс между слоями меньше разброса внутри каждого слоя). Ни `Card`, ни усиленная тень, ни `SwipeToDismissBox` не вносят измеримого джанка ни по отдельности, ни накопительно — на синтетических данных. Слой 4 не добавляет информации сверх Слоя 3 в этом прогоне (см. поправку выше).

**Более важная находка, чем сам отрицательный результат гипотезы эмерджентности**: абсолютные цифры (~2.8% janky) кардинально ниже всего диапазона, снятого в Milestone 21 через `adb shell input swipe` (55.56%-90.91% janky на тех же и похожих сценариях). Это сильно указывает, что источником наблюдаемого «лага» в Milestone 21 была по большей части **сама методология замера** (диспетчеризация синтетического касания через `adb`/ОС, а не через тестовый процесс), а не код экрана диалогов. `performTouchInput` в этом Milestone инжектирует события напрямую в тестовый процесс с фиксированными координатами/длительностью — устраняя именно тот источник шума, который Milestone 21 обнаружил, но не смог обойти. Это не строгое доказательство (эксперимент не сравнивал оба метода замера на одном и том же экране в одном прогоне — см. «Открытые вопросы»), но самая правдоподобная интерпретация данных на руках.

**Критерий закрытия (Допущение 7, вариант b) — обязательная часть, диагностический инструмент и план следующего Milestone:**

- **Более полезный диагностический инструмент**: инфраструктура этого Milestone (`ComposeTestRule` + `JankStats` + детерминированный `performTouchInput`) сама и есть искомый инструмент — качественно надёжнее единичного `adb shell input swipe` + `dumpsys gfxinfo` из Milestone 21 (детерминированный ввод, множественные прогоны, формальный порог значимости с защитой от шума). Следующий шаг — не новый инструмент с нуля, а **применение уже построенного инструмента напрямую к реальному `ConversationsScreen`** (через `MainActivity`/`hiltViewModel`, с реальной навигацией/`Scaffold`/`TopAppBar`/полем поиска — компонентами, которых не было в изолированном `IsolatedScrollTestScreen` этого Milestone) вместо изолированной копии слоёв.
- **План следующего Milestone (23)**: (1) прогнать тот же протокол (5 прогонов, `performTouchInput`, формула сравнения) напрямую на `ConversationsScreen` через `MainActivity`, **с реальной SMS-историей и реальной ролью SMS-приложения по умолчанию на устройстве, явно подтверждённой перед прогоном** (см. поправку выше — этот Milestone упустил именно это условие для Слоя 4, из-за чего проверка на реальных данных не состоялась) — если результат снова ~2-3% janky, это подтвердит гипотезу «жалоба на лаг была артефактом одного конкретного способа замера (палец/`adb`), а не кода» и закроет диагностику содержательно; если джанк всё-таки воспроизведётся на полном реальном экране (что этот Milestone не проверял — `IsolatedScrollTestScreen` не включает `TopAppBar`/поле поиска/`Scaffold`/реальный `hiltViewModel()`, а Слой 4 фактически не проверил и реальные данные), это укажет на один из этих неисследованных факторов как на новую гипотезу. (2) Параллельно — прямое сравнение `performTouchInput` vs `adb shell input swipe` **на одном и том же экране в одном и том же прогоне**, чтобы подтвердить или опровергнуть находку о методологии как источнике прежних цифр, а не оставлять её как правдоподобную, но не доказанную интерпретацию.

## Критерии приёмки

- Изолированный baseline-тест (Слой 0) существует только в `androidTest`, не влияет на debug/release APK.
- Протокол замера — 5 прогонов на слой, детерминированный programmatic scroll, среднее + min/max разброс зафиксированы для каждого слоя в таблице результатов этой спеки.
- Порог значимости применён единообразно ко всем слоям (формула из Допущения 3), не заменён волюнтаристской интерпретацией «выглядит хуже/лучше»; для каждого слоя зафиксированы оба сравнения (против Слоя 0 и против предыдущего слоя, см. раздел C) — точечная причина не приписывается слою, если эффект унаследован от более раннего слоя.
- Итог зафиксирован честно как один из двух вариантов финального критерия закрытия (Допущение 7) — не смешивается и не занижается.
- Если эмерджентность не подтверждена — предложенный «более полезный диагностический инструмент» и план следующего Milestone задокументированы конкретно (не общими словами вроде «нужно исследовать дальше»).

## Тесты

- `JankComparisonTest` (`app/src/test`, plain JUnit) — покрывает формулу из Допущения 3: `WORSE`/`BETTER`/`INDISTINGUISHABLE`, граничный случай «разница ровно равна разбросу» (не должна засчитываться как эффект), и `COMPARISON_SET_UNRELIABLE` при аномально широком baseline-разбросе, включая случай идеального нулевого baseline без деления на ноль.
- `ScrollJankLayerTest` (androidTest, `data/perf/`) — сам инструментированный эксперимент (раздел A/B/C), основной артефакт этого Milestone, не отдельная тестовая обвязка поверх готовой фичи (в отличие от предыдущих milestone'ов). 5 `@Test`-методов (`layer0_`…`layer4_`), выполняются в фиксированном порядке, каждый прогоняет 5 замеров и логирует результат + оба сравнения.
- Конкретного фикса по итогам эксперимента не найдено (эмерджентность не подтверждена, см. «Результаты») — обычные unit/instrumented тесты на фикс не применимы в этом Milestone.
- `gradle.bat :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest` и `:app:connectedDebugAndroidTest` — зелёные, включая полный регрессионный набор (не только новые тесты этого Milestone).

## Открытые вопросы / Backlog

- **Не проверено этим Milestone (главный пробел, найден peer-review)**: реальные данные устройства — Слой 4 фактически выполнился на synthetic-фолбэке (см. поправку в «Результаты»: Gateway App не имел роли SMS-приложения по умолчанию/истории на устройстве на момент прогона, `observeConversations` вернул пустой список). Полный реальный `ConversationsScreen` (через `MainActivity`, с `TopAppBar`/полем поиска/`Scaffold`/реальным `hiltViewModel()`) тоже не проверен — `IsolatedScrollTestScreen` воспроизводит только строки списка. Оба пункта переносятся в план Milestone 23 (раздел «Результаты» выше), с явным условием заранее подтверждённой роли/истории на устройстве перед прогоном.
- **Не доказано, только правдоподобно**: что именно методология `adb shell input swipe` (не код) была источником высоких цифр джанка в Milestone 21 — нужен прямой A/B-прогон `performTouchInput` vs `adb shell input swipe` на одном экране, не проведён в этом Milestone (см. план Milestone 23).
- Код теста исправлен по итогам peer-review, чтобы логировать `REAL` vs `SYNTHETIC-FALLBACK` явно (не полагаться на совпадение количества строк) — впредь эта двусмысленность не должна повториться незамеченной.
- Собственный оверхед `JankStats`/тестового `FrameCounter` не измерен отдельно — не должен влиять на относительное сравнение между слоями (все слои измеряются одним и тем же инструментом), но может слегка сдвигать абсолютные цифры janky%.

Найдено `peer-review-template` и исправлено (один реальный дефект): лог/результат Слоя 4 не различал «реальные данные устройства» от «synthetic-фолбэк с тем же числом строк» — на практике это оказалось не гипотетическим риском, а реальной ошибкой в этом самом прогоне (Layer 4 залогировал «real data, 40 rows», хотя фактически сработал фолбэк). Исправлено явным логированием `REAL`/`SYNTHETIC-FALLBACK`; эксперимент перезапущен, ошибка подтверждена и честно задокументирована в «Результаты», проверка на реальных данных перенесена в план Milestone 23 вместо того, чтобы быть молча выданной за пройденную. Остальные проверенные пункты (`compareJank`: порядок проверки `COMPARISON_SET_UNRELIABLE`, устойчивость строгих `>`-сравнений к периодическим дробям реальных данных; `FrameCounter`: пересоздаётся заново на каждый прогон, `@Synchronized` достаточен для теоретической гонки поздно пришедшего кадра — риск признан пренебрежимо малым, не блокирующим; `MethodSorters.NAME_ASCENDING` + `RunResults`-зависимость между тест-методами — осознанный компромисс для диагностического инструмента, не регрессионного теста, задокументирован в KDoc класса) — реальных дефектов не найдено.
