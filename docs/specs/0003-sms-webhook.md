# 0003 — Приём SMS (webhook)

**Статус:** Implemented

## Контекст

Milestone 3 (`docs/Roadmap.md`). Устройства и `upload_token` уже есть (`0002-devices-tokens.md`). Эта фича — приём SMS от Gateway App (`android_income_sms_gateway_webhook`, сторонний, неизменяемый) и сохранение их в `messages`. Без неё Milestone 4 (REST для просмотра) и Milestone 5 (realtime) не имеют что отдавать.

## Допущения и решения (assumptions log)

Зафиксировано в интервью с владельцем продукта перед написанием этой спеки:

1. **Транспорт `upload_token` — только query-параметр.** Проверено по факту работы Gateway App: приложение не имеет встроенного механизма авторизации, весь webhook URL, включая токен, задаётся пользователем вручную в настройках приложения-шлюза; отдельного поля/заголовка под токен нет. Значит бэкенд принимает `upload_token` **только** как query-параметр (`POST /webhook?upload_token=...`), поддержка заголовка не нужна (не будет использована и добавляет лишний код).
2. **Дедупликация — по хэшу тела запроса.** Gateway App ретраит до 10 раз без какого-либо idempotency-ключа в payload. Ключ дедупа — `SHA-256(raw body)`, привязанный к устройству (`device_id + body_hash`). Совпадение — не сохраняем новую запись, отвечаем как при успехе (идемпотентно для клиента). Осознанный компромисс: два **разных** реальных SMS с абсолютно одинаковым телом (тот же отправитель, текст, обе метки времени) от одного устройства будут считаться дублем — принято как маловероятный и не критичный edge case для MVP.
3. **`X-Signature` — опциональна per-device**, включается наличием `hmac_secret` у устройства (поле уже есть в схеме `devices` из `0002`). Если `hmac_secret` не задан (`NULL`) — подпись не проверяется, запрос принимается по одному `upload_token`. Если `hmac_secret` задан — заголовок `X-Signature` обязателен и должен быть валиден, иначе `401`.
4. **Формат ошибок** — по образцу существующих хендлеров (`internal/handlers/json.go`): `{"error": "..."}`, без кода ошибки как отдельного поля (в проекте такого поля нет нигде, вводить его отдельно для одной фичи не нужно — единообразие важнее).
5. **`sentStamp`/`receivedStamp`** приходят как Unix-эпоха в миллисекундах, **строкой или числом** — подтверждено ручным E2E-тестированием (Milestone 3, см. ниже): дефолтный шаблон Gateway App подставляет их в тело **без кавычек**, то есть в реальном трафике это JSON-числа, не строки, вопреки первоначальному предположению. Хендлер принимает оба варианта (`flexibleString` в `internal/handlers/webhook_handlers.go`, unmarshal строки или числа в `string`) и хранит как есть, `TEXT`, без парсинга/валидации формата на этом этапе (уже так в схеме `messages` из `0001_init.up.sql`) — парсинг/нормализация нужны только для сортировки в Milestone 4 и будут решаться там (сортировка по `created_at` сервера, а не по `sentStamp`, снимает эту проблему).
6. **Поля `battery`/`power`/`network`/`version`** (опциональные в Gateway App) — не сохраняются в этой версии, не входят в MVP-схему `messages`. Backlog.
7. **Rate-limiting webhook-эндпоинта** — отдельная задача Milestone 7, здесь не реализуется.

## API / интерфейс

### `POST /webhook?upload_token=<token>`

Приём одного SMS от Gateway App. Не требует `Authorization` (аутентификация — через `upload_token`).

Заголовки:
- `Content-Type: application/json; charset=utf-8`
- `X-Signature` — опционален; обязателен и проверяется, если у устройства задан `hmac_secret` (см. допущение 3). HMAC-SHA-256 от сырого тела запроса, hex-кодировка, ключ — `hmac_secret` устройства.

Тело:
```json
{
  "from": "string",
  "text": "string",
  "sentStamp": "string",
  "receivedStamp": "string",
  "sim": "string",
  "contactName": "string"
}
```
`from`, `text` обязательны и непустые. `sentStamp`, `receivedStamp`, `sim` опциональны (могут отсутствовать или быть пустыми — сохраняются как `NULL`).

`contactName` — аддитивное расширение (спека [0018-gateway-delete-contact-privacy-export.md](0018-gateway-delete-contact-privacy-export.md)), опционально, отправляется только собственным Android Gateway App и только если пользователь явно включил передачу имени контакта (по умолчанию поле отсутствует/`null`). Backend не парсит и не сохраняет это поле — незнакомое поле в JSON игнорируется существующим декодером без изменений на стороне бэкенда, обратная совместимость сохраняется.

Ответ `201 Created` (новое сообщение сохранено):
```json
{"id": 1, "created_at": "2026-08-25T12:00:00Z"}
```

Ответ `200 OK` (дубль — тело идентично уже принятому для этого устройства, см. допущение 2):
```json
{"id": 1, "created_at": "2026-08-25T12:00:00Z", "duplicate": true}
```
`id`/`created_at` — исходной (первой) сохранённой записи.

Ошибки:
- `400` — `upload_token` отсутствует в query; тело не парсится как JSON; `from` или `text` пустые/отсутствуют.
- `401` — `upload_token` неизвестен, истёк (`upload_token_expires_at` в прошлом) или отозван (перевыпущен — старое значение больше не совпадает ни с одной записью, естественное следствие `0002`); `X-Signature` отсутствует или не совпадает, когда у устройства задан `hmac_secret`.
- Прочие ошибки сервера — `500`, без тела с деталями (не палим внутреннее состояние во внешний, неаутентифицированный JWT-эндпоинт).

## Модель данных

Новая миграция `0003_message_dedup.up.sql` — добавляет к `messages` (из `0001_init.up.sql`) колонку под дедуп и составной индекс:

```sql
ALTER TABLE messages ADD COLUMN body_hash TEXT NOT NULL DEFAULT '';
CREATE UNIQUE INDEX idx_messages_device_body_hash ON messages (device_id, body_hash);
```

`body_hash` = hex(`SHA-256(raw request body)`). `DEFAULT ''` только для совместимости ALTER на непустой таблице (SQLite требует значение по умолчанию для `NOT NULL` колонки, добавляемой к существующей таблице) — на момент миграции таблица `messages` пуста (Milestone 3 ещё не реализован), реальных `''`-строк не возникнет.

Итоговые поля `messages`: `id, device_id, sender, text, sent_stamp, received_stamp, sim, body_hash, created_at`.

Down-миграция (`0003_message_dedup.down.sql`): `DROP INDEX idx_messages_device_body_hash; ALTER TABLE messages DROP COLUMN body_hash;`

## Сценарии использования

1. Gateway App получает SMS → отправляет `POST /webhook?upload_token=...` с телом → бэкенд проверяет токен (и подпись, если включена) → сохраняет → `201`.
2. Сеть обрывается после сохранения, до получения ответа Gateway App → приложение ретраит то же тело → бэкенд по `body_hash` видит дубль → `200` с `duplicate: true`, повторной записи в БД нет.
3. `upload_token` устройства перевыпущен (утечка) владельцем через `0002` → старые запросы Gateway App (ещё не обновлённого) получают `401` до тех пор, пока владелец не обновит токен в настройках приложения-шлюза (вне системы).
4. Владелец включил HMAC для устройства (задал `hmac_secret` — механизм генерации/установки `hmac_secret` вне этой спеки, уже часть модели `devices`) → запросы без `X-Signature` или с неверной подписью отклоняются `401`, даже если `upload_token` верный.

## Критерии приёмки

- Валидный `upload_token`, без `hmac_secret` у устройства, корректное тело → `201`, запись появляется в `messages` с `body_hash`.
- Тот же `upload_token` + идентичное тело повторно → `200` с `duplicate: true`, число строк в `messages` для устройства не увеличивается.
- Тело, отличающееся хотя бы одним байтом (например, другой `receivedStamp`) → новая запись, `201`.
- Неизвестный/истёкший/отозванный `upload_token` → `401`, запись не создаётся (отсутствующий в query — отдельно, `400`, см. ниже).
- `hmac_secret` у устройства задан: запрос без `X-Signature` → `401`; с неверной подписью → `401`; с верной — `201`/`200` по правилам выше.
- `hmac_secret` не задан: запрос без `X-Signature` или с любым её значением всё равно принимается (заголовок игнорируется) — проверка подписи выключена.
- Пустое/отсутствующее `upload_token` в query → `400`. Невалидный JSON тела → `400`. Пустой/отсутствующий `from` или `text` → `400`.
- `sentStamp`/`receivedStamp`/`sim` отсутствуют → сохраняются `NULL`, ответ всё равно `201`.
- Секреты (`upload_token`, `hmac_secret`) не логируются в открытом виде (наследуется из `0001-auth.md`/`0002-devices-tokens.md`).

## Тесты

- `internal/storage`: `CreateMessage` (успех, конфликт уникальности `device_id + body_hash` — возвращает существующую запись или явную ошибку конфликта, на решение слоя `services`), `GetMessageByDeviceAndBodyHash`.
- `internal/services`: `MessageService` (или расширение `DeviceService`) — приём с валидным/невалидным/истёкшим/отозванным токеном, дедуп по повторному телу, различие тел → новая запись, проверка HMAC (включена/выключена/верна/неверна), обязательность `from`/`text`.
- `internal/handlers`: HTTP end-to-end через `httptest` на `POST /webhook` — все коды из «Критериев приёмки», включая проверку заголовка `X-Signature` и корректность вычисления HMAC в самом тесте (тест сам считает ожидаемую подпись от тела и секрета).

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)
