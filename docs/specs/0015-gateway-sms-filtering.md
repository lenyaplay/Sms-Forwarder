# 0015 — Фильтрация входящих SMS (Android Gateway App)

**Статус:** Implemented

## Контекст

`SmsDeliverReceiver` (`android_gateway/`) безусловно вызывает `messageRepository.storeAndForward()` для каждого входящего SMS — нет никакой фильтрации по отправителю, SIM или содержимому. Выявлено при анализе issues референсного проекта (bogkonstantin/android_income_sms_gateway_webhook): #52 (Filter on content, not only on sender), #96 (Regex Sender Option Required), #88 (Whitelist automated sms — паттерн отправителя), #70 (возможность отключения/редактирования фильтров). Владелец продукта явно запросил реализацию фильтрации как следующий шаг после анализа этих issues.

## Допущения и решения (собраны в интервью с владельцем продукта)

1. **Две независимые системы фильтрации, применяемые последовательно**, не одна:
   - **Система 1 — приём (reception).** Решает, попадает ли входящее SMS в приложение вообще. Заблокированное на этом этапе сообщение **полностью игнорируется** — не пишется в Room, не видно нигде в UI, как будто не приходило.
   - **Система 2 — форвардинг (forwarding).** Применяется только к тому, что прошло Систему 1. Решает, уходит ли уже сохранённое сообщение на backend. Заблокированное на этом этапе сообщение **сохраняется в Room и видно в UI**, но не пересылается на backend (не создаётся `WorkManager`-задача форвардинга).
2. **Обе системы используют одну и ту же модель правил (`FilterRule`)**, различаясь только тем, к какому этапу привязан конкретный список правил (`stage: RECEPTION | FORWARDING`) — не отдельные сущности/DAO на каждую систему.
3. **У каждой системы свой независимый глобальный режим** `blacklist`/`whitelist` (не один общий переключатель на обе):
   - `BLACKLIST` — по умолчанию действие разрешено (сообщение проходит этап), правила `stage`-списка исключают конкретные случаи.
   - `WHITELIST` — по умолчанию действие запрещено, правила `stage`-списка явно разрешают конкретные случаи.
   - Дефолт при первом запуске для обеих систем — `BLACKLIST` (безопасно для существующих пользователей: апдейт не обрежет им уже работающий форвардинг молча).
4. **Правило — композитная модель, не набор отдельных сущностей на критерий**: одно правило может одновременно задавать критерий по отправителю, SIM-слоту и содержимому сообщения. Правило матчится, только если совпадают **все указанные** (непустые) критерии (логическое И). Критерий, оставленный пустым, не участвует в проверке.
5. **Матчинг паттернов** (отправитель и текст) поддерживает оба варианта на уровне правила — regex через флаг `isRegex` на каждом из полей `senderPattern`/`contentPattern`; без `isRegex` семантика различается по полю:
   - `senderPattern` — точное совпадение (номер/short-code должен совпасть целиком).
   - `contentPattern` — вхождение подстроки (текст SMS *содержит* паттерн), не точное совпадение всего сообщения. Обнаружено при живой проверке на устройстве 2026-08-29: точное совпадение для контента бесполезно на практике, т.к. ключевое слово внутри реального SMS почти никогда не равно всему телу сообщения целиком. Первоначально спека (как и допущение 5 в исходной формулировке) требовала одинаковой семантики "точное совпадение" для обоих полей — это протестировано вживую, найдено нерабочим для контента, изменение подстроки согласовано с владельцем продукта (не введено самовольно, см. правило в `CLAUDE.md` о недопустимости одностороннего изменения утверждённых требований).
6. **Критерии в правиле для v1 — все три сразу**: `senderPattern` (+`isRegex`), критерий по SIM (опционально), `contentPattern` (+`isRegex`). Ничего не отложено на будущий этап.
   - **Идентификатор SIM в правиле — `subscriptionId` (`SubscriptionManager`), не `slotIndex`.** `slotIndex` — это физический слот (0/1), он не привязан к конкретной карте: если пользователь переставит SIM в другой слот или вставит новую карту в тот же слот, `slotIndex` не меняется, хотя физическая SIM — другая, из-за чего правило "SIM2" молча начнёт применяться не к той карте, для которой было создано. ICCID (истинный серийный номер физической SIM) на практике недоступен нашему приложению: начиная с Android 10 (API 29) `SubscriptionInfo.getIccId()` без carrier-привилегий возвращает `null`/пустую строку. `subscriptionId` — компромисс: относительно стабилен (переживает reboot), но может смениться при физическом извлечении и повторной установке SIM (поведение зависит от OEM) — поэтому такая переустановка обрабатывается явно (см. ниже "Обработка недоступной SIM"), а не тихо игнорируется.
7. **Порядок применения правил внутри списка одного этапа/режима** — first-match-wins по порядку в списке (пользователь может переставлять порядок в UI кнопками «вверх»/«вниз» на строке правила, не drag-жестом — в проекте нет reorderable-библиотеки, кнопки дают ту же функциональность проще и без нового runtime-риска). Новое правило по умолчанию добавляется в конец списка своего этапа (`sortOrder` = максимум существующих + 1); при редактировании существующего правила его `sortOrder` сохраняется, не сбрасывается. Если ни одно правило не совпало — применяется дефолт режима (см. п.3).
8. **UI управления — полноценный экран** для каждой системы: список правил, добавление/редактирование/удаление, toggle `enabled` на правило, переключатель глобального режима (`BLACKLIST`/`WHITELIST`) для этой системы. Закрывает issue #70 сразу, не откладывается на будущий этап.
9. Backend, Viewer App и формат webhook (`0003-sms-webhook.md`) не меняются в этой спеке — фильтрация происходит целиком на стороне Android Gateway App, до того, как сообщение попадает в существующий пайплайн `storeAndForward`/`WebhookRequestWorker`.
10. **Обработка недоступной SIM.** Если правило ссылается на `subscriptionId`, которого нет среди текущих активных SIM (`SimOptionsProvider.getAvailableSims()`) — карту вынули, переустановили, сменился `subscriptionId` у OEM — правило **не удаляется автоматически и не игнорируется молча**. На экране правил оно помечается видимым статусом «SIM недоступна» (не может сработать), пользователь явно решает: перепривязать правило к другой активной SIM или удалить его. Матчинг такого правила при этом всегда возвращает "не совпало" (не может заблокировать/пропустить сообщение по несуществующей SIM), но остальные критерии правила (sender/content), если заданы, для матчинга по SIM-условию не проверяются в отрыве — правило в целом не матчится, пока его SIM-критерий не может быть проверен.

## Функциональность

- **Приём (Система 1)**: `SmsDeliverReceiver` перед вызовом `messageRepository.storeAndForward()` прогоняет входящее SMS (отправитель, `subscriptionId` определённой SIM, текст) через список правил `stage=RECEPTION` в текущем режиме приёма. Если результат — блокировать, `storeAndForward` не вызывается, событие никак не логируется в Room/UI.
- **Форвардинг (Система 2)**: `MessageRepository.storeAndForward()` (или вызывающий код сразу после сохранения) прогоняет то же сообщение через список правил `stage=FORWARDING` в текущем режиме форвардинга. Если результат — блокировать, сообщение вставляется в Room как обычно, но `enqueueDelivery` (постановка `WebhookRequestWorker`) не вызывается; статус доставки — новое состояние, отличное от `PENDING`/`SENT`/`FAILED` (например, `DeliveryStatus.NOT_FORWARDED`), чтобы UI мог явно показать «не форвардится по правилу фильтра», а не выглядеть как зависшая отправка.
- **Экран правил приёма** и **экран правил форвардинга** (два отдельных экрана или один с двумя вкладками) — список правил своего этапа, переключатель режима `BLACKLIST`/`WHITELIST`, добавление/редактирование правила (поля: sender pattern + regex-флаg, SIM опционально — выбор из списка текущих активных SIM по `subscriptionId`, content pattern + regex-флаг, enabled), удаление, toggle enabled без удаления, изменение порядка (для first-match-wins). Правило с `subscriptionId`, не входящим в текущий список активных SIM, отображается с пометкой «SIM недоступна».
- Некорректный regex в поле правила отклоняется на уровне UI-валидации при сохранении (правило с невалидным regex не может быть сохранено).

## Архитектура

- `data/local/db/FilterRuleEntity.kt` (новое): `@Entity(tableName = "filter_rules") data class FilterRuleEntity(id, stage: FilterStage, senderPattern: String?, senderIsRegex: Boolean, subscriptionId: Int?, contentPattern: String?, contentIsRegex: Boolean, enabled: Boolean, sortOrder: Int)`, где `FilterStage = RECEPTION | FORWARDING`. Поле называется `subscriptionId` (не `simSlot`) — хранит `SubscriptionManager`-идентификатор конкретной SIM-подписки, а не физический слот (см. допущение 6). Отдельного поля `action: ALLOW | BLOCK` в v1 нет — по решению в допущении 3 глобальный режим этапа уже определяет смысл совпадения правила (правило просто матчит, семантика allow/block берётся из режима); если при реализации найдётся веский довод ввести `action` отдельно, это фиксируется в разделе "Открытые вопросы".
- `data/local/db/GatewayDatabase.kt` — миграция `3→4`, создающая таблицу `filter_rules`.
- `data/local/GatewayConfigStore.kt` — два новых флага: `receptionFilterMode: FilterMode` (`BLACKLIST`/`WHITELIST`, default `BLACKLIST`), `forwardingFilterMode: FilterMode` (default `BLACKLIST`).
- Новый чистый (без Android/Room-зависимостей) компонент матчинга — `fun matchesRule(sender: String, subscriptionId: Int?, text: String, rule: FilterRuleEntity): Boolean` и `fun resolveFilterDecision(sender, subscriptionId, text, rules: List<FilterRuleEntity>, mode: FilterMode): Boolean` — тестируется чистыми unit-тестами без Room/Context. Правило с непустым `rule.subscriptionId`, отсутствующим среди переданного набора текущих активных `subscriptionId` (параметр функции, полученный вызывающей стороной из `SimOptionsProvider`), не матчится ни при каких условиях остальных критериев (см. допущение 10).
- `data/local/db/FilterRuleDao.kt` (новый) — CRUD + `observeRules(stage: FilterStage): Flow<List<FilterRuleEntity>>`.
- `data/repository/FilterRuleRepository.kt` (новый, либо методы в `MessageRepository`) — обёртки над DAO + чтение текущего режима из `GatewayConfigStore`; использует уже существующий `SimOptionsProvider` (из спеки 0013, SIM-выбор при отправке) для получения списка активных `subscriptionId`, определяющих статус «SIM недоступна» на экране правил.
- `sms/SmsDeliverReceiver.kt` — перед `storeAndForward` вызывает проверку по `stage=RECEPTION`.
- `data/repository/MessageRepository.kt` (`storeAndForward`) — после вставки в Room, перед `enqueueDelivery`, проверяет `stage=FORWARDING`; при блокировке пропускает `enqueueDelivery`, статус — `DeliveryStatus.NOT_FORWARDED`.
- `data/local/db/DeliveryStatus.kt` — новое значение `NOT_FORWARDED`.
- UI: `ui/filters/ReceptionFilterScreen.kt` + `ForwardingFilterScreen.kt` (или один экран с вкладками) с ViewModel по установленному в проекте MVVM/MVI-паттерну (`UiState`/`Actions`), список правил, форма добавления/редактирования, `ConfirmDialog` (переиспользуется существующий `ui/common/ConfirmDialog.kt`) перед удалением правила.
- Доступ к экранам фильтрации — из `SettingsScreen` (новый пункт навигации) или отдельный пункт в основной навигации — решить при реализации по месту, не блокирует Draft.

## Критерии приёмки

- Правило `stage=RECEPTION` с `action`-семантикой блокировки (в зависимости от режима) не даёт сообщению попасть в Room/UI вовсе.
- Правило `stage=FORWARDING`, блокирующее сообщение, оставляет его видимым в Room/UI со статусом `NOT_FORWARDED`, но не создаёт задачу форвардинга на backend.
- Обе системы имеют независимые переключатели режима `BLACKLIST`/`WHITELIST`; смена режима одной системы не влияет на другую.
- Правило матчится только при совпадении ВСЕХ непустых указанных в нём критериев (sender/SIM/content) — правило с одним указанным критерием не требует совпадения остальных (пустых) полей.
- Поддерживаются оба типа паттерна независимо для sender и content на каждом правиле: sender — точное совпадение или regex; content — вхождение подстроки или regex (см. допущение 5).
- SIM-критерий правила хранит и матчит по `subscriptionId`, не по физическому слоту — правило, созданное для конкретной SIM, не начинает молча применяться к другой карте, переставленной в тот же физический слот.
- Правило с `subscriptionId`, отсутствующим среди текущих активных SIM, не может заматчиться (эффективно не участвует в решении) и отображается на экране правил с пометкой «SIM недоступна», не удаляется автоматически.
- При отсутствии совпавших правил применяется дефолт текущего режима этапа (`BLACKLIST` → пропустить, `WHITELIST` → заблокировать).
- Порядок правил в списке влияет на результат при пересекающихся правилах (first-match-wins), порядок можно менять в UI.
- Экран правил (для каждой из систем) поддерживает добавление, редактирование, удаление (с подтверждением), toggle `enabled`, и не даёт сохранить правило с невалидным regex.
- Backend/Viewer App не затронуты — доставленные на backend сообщения продолжают приходить в прежнем формате `0003-sms-webhook.md`.

## Тесты

- Unit (чистые, без Room): `resolveFilterDecision` — совпадение по одному критерию, по нескольким критериям (AND), regex vs точное совпадение, дефолт при отсутствии совпадений в обоих режимах, first-match-wins при нескольких подходящих правилах, `enabled=false` правило игнорируется при матчинге, правило с `subscriptionId`, отсутствующим в переданном списке активных SIM, не матчится.
- Инструментированные (Room): `FilterRuleDao` — CRUD, `observeRules(stage)` фильтрует по этапу и не смешивает `RECEPTION`/`FORWARDING`.
- Инструментированные: `SmsDeliverReceiver`/`MessageRepository.storeAndForward` — сообщение, заблокированное на этапе приёма, отсутствует в Room; сообщение, заблокированное на этапе форвардинга, присутствует в Room со статусом `NOT_FORWARDED` и не создаёт задачу `WebhookRequestWorker`.
- Инструментированные (Compose): экран правил — добавление/редактирование/удаление правила, toggle enabled, переключение режима blacklist/whitelist, попытка сохранить правило с невалидным regex отклоняется, правило с недоступной SIM отображается с пометкой «SIM недоступна».
- Ручная проверка на физическом устройстве: реальное SMS от отправителя из blacklist-правила не появляется в приложении; реальное SMS, заблокированное только на этапе форвардинга, видно в треде со статусом «не форвардится», но не приходит на backend.

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Отдельное поле `action: ALLOW | BLOCK` на правиле (независимо от глобального режима этапа) — при реализации может обнаружиться веский довод ввести его вместо чистой семантики «режим определяет смысл совпадения»; если так — это расширение модели, не противоречащее уже принятым решениям, отражается в реализации и здесь же документируется постфактум.
- Индикатор «N сообщений заблокировано на этапе форвардинга» в UI (агрегированная статистика) — не запрошено явно, не в объёме v1.
