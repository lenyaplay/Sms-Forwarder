# 0037 — кнопка "назад" сначала снимает выделение сообщений

## Контекст

Milestone 30 ([Roadmap 3.md](../roadmaps/Roadmap%203.md)). Владелец продукта заметил на живом устройстве (2026-09-06): в `ThreadScreen` при активном мульти-выборе сообщений (`uiState.isSelectionMode`) нажатие системной кнопки "назад" сразу выполняет обычную навигацию (`onBack()`, выход из переписки в список бесед), вместо ожидаемого — сначала снять выделение, оставшись в переписке.

Требования собраны через `stakeholder-requirements-gathering` (2026-09-06, ответы владельца продукта).

## Текущее состояние

`ThreadScreen.kt:113-189` — мульти-select существует только в `ThreadScreen` (`ThreadUiState.isSelectionMode`/`selectedMessageIds`, снимается вызовом `viewModel::onClearSelection`, уже доступным через кнопку-крестик `SELECTION_CLOSE_BUTTON` в `TopAppBar`). В `ConversationsScreen` мульти-выбора нет вообще — там long-press на строку открывает `DropdownMenu` с действиями для одной конверсации (архив/удалить), не накопительное выделение нескольких. Системная кнопка "назад" в `ThreadScreen` сейчас никак не перехватывается — Compose Navigation обрабатывает её напрямую как обычный pop back stack, независимо от `isSelectionMode`.

## Требования (из интервью)

1. **Область действия**: только `ThreadScreen`. `ConversationsScreen` не участвует — там нет мульти-выбора, добавлять его не требуется.
2. **Поведение**: если `uiState.isSelectionMode == true`, нажатие системной кнопки "назад" вызывает `viewModel::onClearSelection` (то же действие, что и кнопка-крестик) и не выполняет навигацию. Если `isSelectionMode == false` — поведение не меняется (обычный `onBack()`).
3. **Повторное "назад"**: после снятия выделения следующее нажатие "назад" — обычная навигация (выход из `ThreadScreen`), как и сейчас при `isSelectionMode == false`.
4. **Анимация**: снятие выделения через "назад" — мгновенное, идентичное текущему поведению кнопки-крестика (никакой отдельной анимации не добавляется).

## Архитектура

- `androidx.activity.compose.BackHandler(enabled = uiState.isSelectionMode) { viewModel.onClearSelection() }` внутри `ThreadScreen` composable — стандартный Compose-механизм перехвата системного back, уже доступен в проекте (та же зависимость, что использует Navigation Compose).
- `enabled` привязан к `uiState.isSelectionMode`, так что при `false` `BackHandler` не активен и системный back проходит как обычно к `NavHost`/`onBack()` без дополнительного кода.
- `viewModel::onClearSelection` уже существует и используется кнопкой-крестиком (`ThreadScreen.kt:127`) — переиспользуется как есть, новой логики очистки выделения не требуется.

## Критерии приёмки

- В `ThreadScreen` с непустым `selectedMessageIds`: нажатие системной кнопки "назад" → `isSelectionMode` становится `false`, `TopAppBar` возвращается к обычному виду, экран остаётся `ThreadScreen` (не происходит навигация к списку бесед).
- Повторное нажатие "назад" после этого (уже вне режима выделения) → обычная навигация назад, как до этой фичи.
- В `ThreadScreen` без активного выделения (`isSelectionMode == false`) — нажатие "назад" ведёт себя как раньше (без регрессии).
- `ConversationsScreen` не затронут — поведение "назад" там не меняется.

## Тесты

- Инструментированный тест `ThreadScreenTest`: включить selection mode (long-press по бубблу или иной существующий способ входа в режим выделения), нажать системное "назад" (`Espresso.pressBack()`/аналог, уже используется в других тестах на back-навигацию проекта), убедиться — `TopAppBar` вернулась к обычному виду (`onNodeWithText(uiState.title)` или отсутствие `SELECTION_CLOSE_BUTTON`), экран не сменился.
- Тот же тест, второе нажатие "назад" — убедиться, что происходит обычная навигация (вызывается `onBack`, экран покидается — по аналогии с существующим тестом на кнопку `ArrowBack`/`onBack` в `ThreadScreenTest`, если такой уже есть).
- Регрессия: существующий тест на "назад" вне режима выделения остаётся зелёным без изменений.
- Roborazzi-снапшот `ThreadScreenSnapshotTest` не меняется (изменение — только в поведении back, не в разметке).
