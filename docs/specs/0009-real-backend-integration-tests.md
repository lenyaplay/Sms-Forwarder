# 0009 — Инструментированные тесты Android против реального бэкенда

**Статус:** Implemented

## Контекст

`docs/Roadmap.md` Milestone 8 backlog: во время ручного E2E-теста на физическом устройстве (2026-08-26, `0007-android-viewer-mvp.md`) обнаружились два реальных дефекта, не пойманных ни одним существующим автотестом — `LoginRequest` сериализовался как `username` вместо ожидаемого бэкендом `login`, и отсутствие `network_security_config` блокировало cleartext-трафик на debug-сборке. Оба всплыли только вручную, потому что все существующие Android-тесты (unit и instrumented, `0007`) подменяют `ApiService` фейком/скриптованной реализацией интерфейса — это полностью обходит реальную kotlinx.serialization и реальный OkHttp/Android network-стек.

Уже существует ad-hoc прецедент: `RealBackendLoginTest.kt` (написан в ходе того же ручного E2E) — инструментированный тест, гоняющий `LoginScreen` через реальный Retrofit/OkHttp против бэкенда, поднятого вручную (`docker compose up` + `adb reverse tcp:8080 tcp:8080`). Он не подключён ни к какому автоматическому прогону.

Эта спека формализует и расширяет этот подход на весь основной путь приложения, по явному решению пользователя (интервью перед этой спекой).

## Допущения и решения (assumptions log)

1. **Уровень тестов — инструментированные, не JVM+httptest.** Решение пользователя: JVM-тесты с фейковым Go-сервером не ловят Android-специфичные баги (`network_security_config`, реальный OkHttp/Keystore), а именно такие баги и стали поводом для этой работы. Instrumented-тесты на эмуляторе — приоритет.
2. **Бэкенд поднимается через `backend/docker-compose.yml` (Milestone 7), не через `httptest.Server`.** Ближе к реальному деплою, не требует нового механизма экспонирования Go-процесса наружу для Android-теста.
3. **Не встраивается в обычный `./gradlew test` / `connectedAndroidTest`.** Отдельный явный Gradle-флейвор/source-set `realBackendTest` (или аналогичный явный фильтр по пакету/аннотации), требующий заранее поднятого бэкенда. Обычный прогон тестов (без бэкенда под рукой) не должен падать/зависать. Раз в проекте пока нет CI для Android — эти тесты остаются explicitly-ручной командой, аналогично уже сложившейся практике ручного E2E (`0003`, `0007`).
4. **Покрытие — весь основной путь**, не только login: регистрация/привязка устройства по `download_token`, отправка сообщения через webhook (эмулирует Gateway App напрямую HTTP-запросом, как уже делает `RealBackendLoginTest.registerTestUser`), получение сообщения через `GET /devices/{id}/messages`, и realtime-доставка через `GET /events` (SSE).
5. **Изоляция данных между прогонами** — как и в `RealBackendLoginTest`, каждый тестовый прогон создаёт уникального пользователя/устройство (по timestamp/UUID в логине), не полагается на предварительно существующие данные и не требует сброса БД бэкенда между тестами.
6. **База URL — фиксированная `127.0.0.1:8080`** (как в `RealBackendLoginTest`), с той же инструкцией `adb reverse tcp:8080 tcp:8080` для физического устройства; для эмулятора `127.0.0.1` внутри эмулятора не работает без reverse/redirect — тест документирует это ограничение явно (не переизобретает настраиваемый URL, это отдельный вопрос Milestone 9).
7. **SSE проверяется тем же тестовым инструментарием**, что и REST — открытие `GET /events`, отправка сообщения через webhook в отдельном потоке/после подписки, и `waitUntil` на появление сообщения в UI/состоянии ViewModel (тот же паттерн, что `RealBackendLoginTest.waitUntil`), без искусственных `Thread.sleep`.
8. **Не входит в scope:** запуск бэкенда самим тестовым раннером (docker compose поднимается вручную оператором перед прогоном), CI-интеграция (нет CI для Android вообще), нагрузочное/многопользовательское тестирование.

## Что тестируется (сценарии)

Один инструментированный тестовый класс на сценарий, каждый — самостоятельный (создаёт своего пользователя/устройство):

1. **Login** — уже покрыто `RealBackendLoginTest` (переносится/остаётся как есть, попадает под новый Gradle-профиль).
2. **Регистрация устройства и привязка по `download_token`** — регистрирует устройство напрямую через бэкенд-API (эмулируя владельца/скрипт настройки), получает `download_token`, вводит его в `AddDeviceScreen`, проверяет появление устройства в `DeviceListScreen`.
3. **Приём сообщения через webhook и отображение в ленте** — отправляет сообщение на `/webhook` напрямую HTTP-запросом (эмулируя Gateway App, как `registerTestUser`), открывает `MessageFeedScreen` для устройства, проверяет, что сообщение показано.
4. **Realtime-доставка через SSE** — открывает `MessageFeedScreen` (SSE-соединение устанавливается), затем отправляет новое сообщение через webhook, проверяет появление в ленте без ручного обновления/повторного открытия экрана.

## Модель данных

Изменений в серверной схеме и в основном коде приложения нет — это чисто тестовая инфраструктура (новый Gradle source-set/флейвор + тестовые классы).

## Критерии приёмки

- Существует отдельный явный способ запустить эти тесты (Gradle-задача/флейвор), не пересекающийся с обычным `connectedAndroidTest`.
- Обычный `./gradlew test` и `./gradlew connectedAndroidTest` (без поднятого бэкенда) проходят без изменений в поведении — новые тесты в них не участвуют.
- Каждый из 4 сценариев выше реализован отдельным тестом, использующим реальный `ApiService` (Retrofit/OkHttp), не фейк.
- Каждый тест создаёт собственные изолированные данные (уникальный логин/устройство) и не зависит от порядка запуска или состояния БД от предыдущих прогонов.
- README/инструкция (в самом тестовом файле или `docs/DEVELOPMENT.md`) описывает точную последовательность запуска: поднять `docker compose`, `adb reverse`, команда прогона.
- Прогон всех 4 тестов вручную (с реально поднятым бэкендом) — зелёный.

## Тесты

Сама эта фича и есть тестовая инфраструктура — «тесты для тестов» не пишутся; вместо этого критерий готовности — сами 4 сценария реально проходят против реально поднятого бэкенда (см. «Критерии приёмки» выше). Ручная верификация прогона — обязательная часть приёмки этой спеки, аналогично ручной Docker-верификации в `0008`.

**Проверено вручную**: все 4 сценария (login x2, add-device, webhook→feed, SSE live-update) прогнаны по отдельности через `adb shell am instrument -e class <FQCN>` против бэкенда, поднятого `docker compose up`, с `adb reverse tcp:8080 tcp:8080` — все зелёные. Отдельно подтверждено, что обычный `connectedDebugAndroidTest` без поднятого бэкенда прогоняет только существующие 15 тестов (0 падений) и не трогает пакет `realbackend` — изоляция через `notPackage` работает.

**Известное ограничение окружения тестирования** (осознанное, аналогично `0007`/`0008`): в этой песочнице `adb reverse` периодически теряет проброс порта между независимыми `adb shell`-вызовами (подтверждено через `adb reverse --list`, пустой список при живом и доступном через `curl` на хосте бэкенде) — из-за этого прогон всех 5 тестов одним `-e package com.smsforwarder.viewer.realbackend` иногда падает с `ConnectException` на самом первом HTTP-вызове (`registerAndLogin`), хотя код и бэкенд рабочие. Не воспроизводится при запуске тестов по одному классу с непосредственно предшествующим `adb reverse`; не связано с логикой тестов или приложения — специфика проброса портов adb в этом окружении, не баг фичи.

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- CI-интеграция (поднятие бэкенда в контейнере на CI-раннере и автоматический прогон) — отдельный пункт, требует выбора/настройки CI-платформы для Android, не решено на момент этой спеки.
- Настраиваемый base URL вместо захардкоженного `127.0.0.1:8080` — пересекается с Milestone 9 (настройки сервера в приложении), не дублируется здесь.
- Аналогичное покрытие для будущих экранов (по мере появления Milestone 9) — расширяется по мере необходимости, не проектируется заранее.
