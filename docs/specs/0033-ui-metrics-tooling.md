# 0033 — Инструменты автоматического подсчёта UI-метрик

**Статус:** Implemented (Stage A, Stage B, Stage C)

## Контекст

Инициировано в рамках сессии по визуальному полишингу (2026-09-04, Milestone 26/27 в [Roadmap 2.md](../roadmaps/Roadmap%202.md)): у приложения нет ни скриншот-пайплайна, ни телеметрии, ни пользовательских исследований — доступны только code-level метрики (сборка, тесты, живой осмотр на TECNO LI9). Цель этой спеки — минимальная инфраструктура автоматического измерения UI-качества трёх основных экранов (`ConversationsScreen`, `ThreadScreen`, `SettingsScreen`), не требующая эмулятора/устройства для базового прогона.

Интервью с владельцем продукта (`stakeholder-requirements-gathering`, 2026-09-05) зафиксировано ниже в «Допущениях и решениях».

## Допущения и решения

Собраны интервью через `stakeholder-requirements-gathering` (2026-09-05):

1. **Разбиение на этапы внутри одной спеки** (не отдельные спеки на каждый блок) — по аналогии со спекой 0029, объединившей несколько пунктов одного Milestone. Причина: пункты 1-5 бэклога Milestone 27 тесно связаны (этапы B/C потребляют вывод этапа A), отдельные спеки добавили бы накладные расходы на ведение документов без выгоды.
   - **Этап A** — Roborazzi-харнесс + скрипт-аудитор контраста/touch-target. Чистый Kotlin/JVM, без внешних зависимостей.
   - **Этап B** — colorfulness + feature-congestion.
   - **Этап C** — saliency + симметрия/баланс.
2. **Технологическая граница A vs B/C**: пункты 1-2 реализуемы полностью на JVM (WCAG-контраст и touch-target grep не требуют ML/сторонних моделей). Пункты 3-5 переносятся во **внешний Python-пакет** — решение владельца продукта: если DeepGaze (saliency, п.4) в любом случае требует PyTorch-модель вне JVM, разумнее держать весь пиксельный анализ (colorfulness, feature-congestion, saliency, симметрия) в одном месте с одним набором зависимостей, а не дробить между JVM и Python по критерию "а можно ли было бы сделать на JVM". Явно принятая цена: colorfulness теряет свойство "работает без Python", но это уже не решающий фактор, раз Python всё равно обязателен для этапа C.
3. **Способ запуска Python-пакета**: отдельный шаг вне `connectedDebugAndroidTest`/CI-контура проекта — либо запускается вручную, либо из Gradle через `exec {}`-таск, который дёргает системный `python3` как внешний процесс. Требует Python-окружения на машине, где запускается анализ (не на CI по умолчанию). Явно не блокирует обычную сборку/тесты.
4. **Порог провала для WCAG-контраста/touch-target** — только информационный отчёт, **без** блокирующего fail в тестах/сборке. Причина (владелец продукта): решение о фиксе — за человеком, не за жёстким CI-гейтом на первой итерации инструмента.
5. **Обе темы (light+dark) сразу**, для всех 3 экранов, с первого прохода — не поэтапно по одной теме. Причина: проект уже поддерживает обе темы полностью, разница в трудозатратах между "одна тема" и "обе" минимальна (второй прогон снапшот-теста с другим `ColorScheme`).
6. **Baseline PNG коммитятся в git-репозиторий** — стандартный паттерн Roborazzi (record/verify режимы): без закоммиченного baseline не с чем сравнивать регрессии между запусками на разных машинах.
7. **Численные пороги приёмки для этапа C (saliency/симметрия) сознательно не фиксируются в этой спеке.** И saliency-модели (DeepGaze), и APB-симметрия валидированы на графическом дизайне/изобразительных композициях, не на чат-интерфейсах — экстраполяция, явно отмеченная в Roadmap. Владелец продукта прямо указал: нужно сначала увидеть реальные числа на реальных экранах проекта, чтобы понять, какие метрики вообще информативны для этого домена, прежде чем фиксировать порог приёмки. Критерий готовности этапа C поэтому — **наличие работающего скрипта и отчёта с числами**, не прохождение числового порога; CI для этапа C, как и для этапа A, не блокирующий.
8. **Скоуп экранов** — все три уже названных в Roadmap (`ConversationsScreen`, `ThreadScreen`, `SettingsScreen`), без сокращения. Не расширяется на другие экраны (`FilterRules`, `DeliveryScreen` и т.д.) в рамках этой спеки.

Дополнительное интервью `stakeholder-requirements-gathering` перед этапом C (2026-09-05):

9. **Критерий выбора saliency-модели**: реализуются ОБА подхода (OpenCV spectral residual и DeepGaze/PyTorch), запускаются на всех 6 PNG из этапа A, победитель выбирается **визуальной оценкой владельцем продукта** (глядя на карты внимания рядом) — не по весу зависимостей, не по скорости, не по формальной близости к published-исследованиям. Проигравший подход удаляется из кода после решения, не остаётся мёртвым/закомментированным.
10. **Симметрия/баланс — комбинированная эвристика**, не простой mirror-flip diff и не строгий published APB (готового Python-пакета для APB нет). Реализуются **оба сигнала как один модуль `symmetry.py`**, возвращающий два числа:
    - симметрия — SSIM между изображением и его зеркальным (горизонтальным) отражением;
    - баланس — взвешенный по яркости/насыщенности "визуальный момент" (центр масс визуального веса регионов относительно геометрического центра изображения).
    Явно документируется как упрощение относительно published APB (Levkowitz/Meyer-стиль), по той же философии, что и `feature_congestion.py` в этапе B — не выдаётся за точную репродукцию метрики из литературы.
11. **Формат вывода**: обе метрики этапа C добавляются как новые колонки в существующий CLI `python -m ui_metrics <path>` (не отдельный скрипт). Импорт PyTorch/DeepGaze — **ленивый** (внутри функции, не на уровне модуля), чтобы OpenCV-путь работал без PyTorch, установленного в окружении; после того как саliency-модель выбрана по п.9, ленивая обёртка сохраняется только вокруг выбранного подхода (если выбран DeepGaze) — второй, отклонённый подход удаляется вместе с кодом.
12. **Численные пороги приёмки этапа C по-прежнему не фиксируются** — подтверждено владельцем продукта, действует то же обоснование, что и в Допущении 7 (готовность = рабочий скрипт + отчёт с числами, не сравнение с порогом).

## Архитектура

### Этап A — Roborazzi-харнесс (модуль `:app`, `src/test`)

- Новая зависимость `io.github.takahirom.roborazzi` (Robolectric-based, JVM, без эмулятора) — конкретная версия фиксируется на этапе реализации (последняя стабильная на момент работы).
- Новый пакет `ui/snapshot/` (или аналогичный, по существующей структуре `ui/<feature>`) с одним `@RunWith(RobolectricTestRunner::class)` тестовым классом на экран (`ConversationsScreenSnapshotTest`, `ThreadScreenSnapshotTest`, `SettingsScreenSnapshotTest`), каждый рендерит соответствующий `*Content`-композабл (те же изолированные composable, что уже используются в существующих Compose-тестах проекта, с фейковыми данными) в обеих темах (`MaterialTheme(colorScheme = lightColorScheme/darkColorScheme)` — переиспользуется `ui/theme/Theme.kt`).
- Snapshot-файлы (`*.png`) сохраняются Roborazzi в стандартную директорию плагина внутри модуля, коммитятся в git.
- Режимы: `recordRoborazziImage`/`compareRoborazziImage` через системное свойство Gradle (`-Proborazzi.test.record=true` для записи нового baseline, обычный прогон — сравнение).

### Этап A — скрипт-аудитор контраста + touch-target

- Новый Kotlin-файл вне androidTest (например `buildSrc`/отдельный Gradle-таск или standalone `main()` в `app/src/test`, решается по факту реализации) — не тест в юнит-смысле (не должен падать сборку), а генератор отчёта.
- **Контраст**: берёт пары ролей `ColorScheme` (`primary`/`onPrimary`, `surface`/`onSurface`, `errorContainer`/`onErrorContainer` и т.д. — конкретный список пар фиксируется на этапе реализации, по факту того, какие пары реально используются в `ui/**/*.kt`), считает WCAG relative luminance/contrast ratio по формуле спецификации WCAG 2.x, печатает таблицу `пара → ratio → соответствует ли AA (4.5:1 обычный текст / 3:1 крупный текст)` для обеих тем.
- **Touch-target**: статический grep/парсинг `ui/**/*.kt` на интерактивные модификаторы (`clickable`, `combinedClickable`, `IconButton`, `Switch` и т.д.) без явного `Modifier.size`/`heightIn(min = 48.dp)` рядом — эвристика, не точный AST-анализ; ложные срабатывания возможны и допустимы (это отчёт для человека, не гейт).
- Отчёт — текстовый вывод в консоль/файл, **не** `assertTrue`/`fail` — по решению 4 выше.

### Этап B/C — Python-пакет пиксельного анализа

- Новая директория вне `android_gateway/` (например `tools/ui-metrics/` в корне репозитория) — отдельный Python-проект (`requirements.txt` или `pyproject.toml`, решается на этапе реализации), не часть Gradle-сборки.
- Вход: PNG-файлы, произведённые этапом A (Roborazzi baseline-директория).
- Модули:
  - `colorfulness.py` — метрика Hasler-Süsstrunk (арифметика по RGB-каналам пикселей).
  - `feature_congestion.py` — Rosenholtz-style feature congestion (multi-scale ориентация/цвет/яркость).
  - `saliency.py` — на время бейк-оффа содержит ОБЕ реализации (OpenCV spectral residual через `cv2.saliency` и DeepGaze через ленивый `import torch`/загрузку весов вне git); после выбора победителя (см. Допущение 9) проигравшая реализация удаляется.
  - `symmetry.py` — комбинация mirror-flip SSIM (симметрия) + взвешенный визуальный момент (баланс), см. Допущение 10; возвращает оба числа.
- Точка входа — один CLI-скрипт (`python -m ui_metrics <путь к PNG или директории>`), печатающий числа по всем метрикам (Stage B: 2, Stage C добавляет ещё до 3: saliency-скор, symmetry, balance) для каждого входного файла. Импорт `torch`/DeepGaze — ленивый (см. Допущение 11), чтобы CLI не требовал PyTorch, если выбран/остался только OpenCV-путь.
- Зависимости и веса моделей (если объёмные, например DeepGaze) — **не коммитятся в git**, документируется отдельная инструкция по получению (скачивание при первом запуске или вручную).

## Критерии приёмки

**Этап A:**
- Roborazzi-снапшоты существуют для всех 3 экранов, обеих тем — 6 PNG-файлов минимум, закоммичены в repo.
- `./gradlew :app:testDebugUnitTest` (или отдельный Gradle-таск Roborazzi) проходит в режиме сравнения на неизменном коде (снапшоты стабильны, не флейкуют между запусками на одной машине).
- Скрипт контраста печатает таблицу WCAG-ratio по обеим темам без исключений/крашей.
- Скрипт touch-target печатает список найденных интерактивных элементов с их выявленным/невыявленным явным минимальным размером.
- Ни один из двух скриптов не блокирует сборку/CI (не `fail`, не ненулевой exit code при найденных нарушениях).

**Этап B:**
- `colorfulness.py`/`feature_congestion.py` запускаются на PNG из этапа A и печатают числовой результат для каждого экрана/темы без крашей.

**Этап C:**
- `saliency.py`/`symmetry.py` запускаются на PNG из этапа A и печатают числовой результат для каждого экрана/темы без крашей.
- Численный порог приёмки **не задаётся** (см. Допущение 7) — готовность подтверждается фактом рабочего скрипта и отчёта, не сравнением с порогом.

## Тесты

- **Этап A**: сами Roborazzi-тесты (`*SnapshotTest.kt`) — это и есть тест (падают при визуальной регрессии в режиме сравнения). Отдельно — unit-тест на чистую функцию расчёта WCAG-контраста (граничные случаи: ratio ровно 4.5:1/3:1, белый на белом → 1:1, чёрный на белом → 21:1) в `src/test`.
- **Этап B/C**: unit-тест на Python-стороне (`pytest`) на то, что каждая функция метрики возвращает число в ожидаемом диапазоне для тривиальных синтетических входов (однотонное изображение → colorfulness ≈ 0; полностью случайный шум → высокий feature-congestion) — не тест "правильности" внешних моделей (DeepGaze/APB), а тест того, что обвязка (чтение PNG, вызов модели, парсинг результата) не ломается.
- `query-validation` — не применимо, миграций БД в этой фиче нет; явно зафиксировано, шаг пропущен обоснованно.

## Результаты

**Этап A — реализовано (2026-09-05):**

- Roborazzi 1.30.0 + Robolectric 4.16.1 добавлены в `android_gateway/gradle/libs.versions.toml`/`app/build.gradle.kts`. **Версии подобраны эмпирически, не по первому найденному значению**: последняя стабильная Roborazzi (1.73.0 на момент работы) оказалась скомпилирована с Kotlin-метаданными версии 2.3.0, несовместимой с Kotlin 2.0.21 проекта (`kspDebugUnitTestKotlin` падал с "Module was compiled with an incompatible version of Kotlin"). Смоук-тест (`Text("hi")` + `captureRoboImage()`) подтвердил, что 1.30.0 совместима, прежде чем писать реальные тесты — риск, заранее отмеченный в плане, подтвердился на практике.
- Обнаружено эмпирически (не в документации по умолчанию): `roborazzi { outputDir.set(...) }` применяется только при **автогенерируемом** имени файла (`captureRoboImage()` без аргумента); при явном `filePath = "..."` Roborazzi 1.30.0 игнорирует `outputDir` и пишет в корень модуля. Решение — не передавать `filePath`, полагаться на автоимя (`<пакет>.<класс>.<метод>.png`), менее читаемо, но действительно уважает `outputDir`.
- 3 snapshot-теста (`ConversationsScreenSnapshotTest`, `ThreadScreenSnapshotTest`, `SettingsScreenSnapshotTest`), обе темы каждый — 6 PNG в `android_gateway/app/src/test/snapshots/`, закоммичены. Вручную просмотрены — рендерят реальный контент экранов (аватары/группировка/OTP-подчёркивание/настройки), не пустые/не крашнутые.
- `robolectric.properties` (`sdk=34`) — заработало с первой попытки, fallback на `sdk=33` не понадобился.
- `UiMetricsReportTest` (contrast + touch-target) и `ContrastRatioTest` (unit-тест на саму формулу) — оба зелёные, отчёт печатает таблицу WCAG-контраста (все 12 строк — 6 пар ролей × 2 темы — проходят AA) и эвристический touch-target отчёт (69 находок, ожидаемо шумно — эвристика заведомо приблизительная).
- Полный `:app:testDebugUnitTest` — зелёный (перепроверено дважды: запись baseline + отдельный verify-прогон без `-Proborazzi.test.record`, оба зелёные, снапшоты стабильны). `:app:compileDebugAndroidTestKotlin` — чисто (androidTest не затронут).
- `peer-review-template`: 1 should-fix найден и исправлен — эвристика touch-target окном ±3 строки может (в редком случае) замаскировать реальный дефект у соседнего интерактивного элемента вместо лишнего шума; задокументировано комментарием в коде, логика не менялась (принятый компромисс эвристики).
- `analysis-qa-checklist`: построчная сверка критериев приёмки/тестов с реальным кодом — 1 пробел найден и закрыт: спека обещала граничный unit-тест и на 4.5:1, и на 3:1, а `ContrastRatioTest.kt` содержал только первый; добавлен `exactlyAaLargeThresholdPasses`. После фикса — все критерии Stage A подтверждены построчно (6 PNG без мусора, verify стабилен, обе темы в отчёте, touch-target печатает реальные `file:line`, `UiMetricsReportTest` не содержит ни одного `assert`/`fail`, полностью в `try/catch`).

**Этап B — реализовано (2026-09-05):**

- Новый Python-пакет `tools/ui-metrics/` (первый Python-код в продуктовой части репозитория — не считая `.claude/skills/*/scripts/`, которые не относятся к продукту). Структура: `ui_metrics/{colorfulness.py, feature_congestion.py, __main__.py}`, `tests/`, `requirements.txt` (numpy, opencv-python, pytest), `.gitignore`, `README.md`. `saliency.py`/`symmetry.py` намеренно не созданы — по решению владельца продукта, модель для saliency будет выбрана позже опытным сравнением (OpenCV spectral residual vs DeepGaze/PyTorch), создавать пустые модули под нерешённый вопрос преждевременно.
- `colorfulness.py` — точная реализация формулы Hasler-Süsstrunk, без упрощений.
- `feature_congestion.py` — **явно не точный алгоритм Rosenholtz** (тот требует multi-scale DOG-пирамиды + попиксельной локальной ковариации + расстояния Махаланобиса в совместном цвето-ориентационном пространстве — несоразмерная сложность для advisory-инструмента). Реализована задокументированная упрощённая эвристика: локальное std по L/a/b (CIE Lab) + по ориентации градиента (Sobel), на 3 масштабах box-фильтра, нормализовано и усреднено в одно число. Явно зафиксировано в docstring модуля и README — не выдаётся за настоящий Rosenholtz.
- Найден и исправлен реальный баг при первом прогоне тестов: на идеально плоском изображении `feature_congestion` возвращал 2.0 вместо ~0 — box-фильтр с крупным ядром (27px) давал float-шум ~1e-6 вместо точного нуля для двух Lab-каналов, который затем нормализовался (шум/шум=1.0) и суммировался. Исправлено повышением порога отсечения шума с `1e-9` до `1e-3` (запас на три порядка выше наблюдаемого шума, при этом ниже любого содержательного сигнала).
- `pytest tests/` — 6/6 зелёных (после фикса) — flat-image ⇒ near-zero для обеих метрик, high-variance/noise ⇒ отчётливо выше, вырожденные 1×1/4×4 изображения не крашат.
