# 0032 — Разделитель по дате в треде сообщений

**Статус:** Implemented

## Контекст

При проверке спеки 0031 (2026-09-04) владелец продукта заметил, что визуальная группировка сообщений (спека 0029, `MessageGrouping.isFirstInGroup`) в её текущем виде — только разница в вертикальном отступе (8dp vs 2dp) между сообщениями одной группы — слабо заметна. Решение (прямое указание в чате, не через `AskUserQuestion`, но столь же однозначное): **саму группировку не менять**, добавить отдельную фичу — разделитель-дата (как в Telegram/большинстве мессенджеров): если разрыв между соседними сообщениями пересекает границу календарного дня, между ними показывается по центру текст с датой (например "13 сентября").

Прочитан текущий код:
- `MessageGrouping.kt`'s `isFirstInGroup(index)` — группирует по смене отправителя/направления или разрыву ≥ 5 минут (`GROUP_GAP_MILLIS`). Остаётся без изменений.
- `ThreadScreen.kt`'s `ThreadContent` — `LazyColumn` с `itemsIndexed(uiState.messages, key = { _, message -> message.id })`, единственный тип элемента — `MessageBubble`.
- `ThreadScreen.kt`'s `messageTimeFormat = SimpleDateFormat("HH:mm", Locale.getDefault())` — существующий паттерн форматирования (единый статический форматтер, не создаётся заново на recomposition).

## Допущение, требующее подтверждения при ревью спеки

**"Разница больше дня" трактуется как пересечение границы календарного дня** (сообщения в 23:59 и 00:01 следующего дня — это уже "больше дня", хотя прошло 2 минуты), а не как буквальный интервал ≥ 24 часа между `createdAt` двух сообщений. Это стандартное поведение мессенджеров (Telegram/WhatsApp) и соответствует более раннему упоминанию "как в Telegram" в бэклоге Milestone 26. Если владелец продукта имел в виду буквально ≥24 часа — сообщить при ревью, это меняет реализацию (сравнение по `Calendar`/`LocalDate` вместо разницы `createdAt`).

## Функциональность

- Новая чистая функция `ui/thread/DateSeparator.kt` (или в `MessageGrouping.kt` рядом) — `fun List<MessageEntity>.isFirstOnNewDay(index: Int): Boolean`: `true`, если `index == 0`, либо календарная дата `this[index].createdAt` отличается от календарной даты `this[index - 1].createdAt` (сравнение через `Calendar`/дневной `LocalDate`, учитывая часовой пояс устройства — тот же подход, что и остальное форматирование дат в проекте, `Locale.getDefault()`).
- `ThreadContent`'s `LazyColumn`: перед `itemsIndexed` для сообщения, где `isFirstOnNewDay(index) == true`, рендерится дополнительный элемент — центрированный `Text` с датой (формат "13 сентября", `SimpleDateFormat("d MMMM", Locale.getDefault())`, без года — как в остальных мессенджерах для текущего года; вопрос показа года для сообщений из прошлых лет решается по факту реализации, вероятно тем же паттерном, что и WhatsApp/Telegram: год добавляется, если `createdAt` не в текущем календарном году).
- Разделитель показывается **до** первого сообщения нового дня, группировка (`isFirstInGroup`) при этом не меняется и не зависит от разделителя — если день сменился, но отправитель/направление те же и разрыв < 5 минут (пограничный случай около полуночи), сообщение всё ещё визуально в той же "группе" по отступу, но после разделителя-даты. Это осознанно — два независимых визуальных сигнала (день и группа), не связанные друг с другом.
- Реализация в `LazyColumn`: `itemsIndexed` не поддерживает вставку доп. элементов между item'ами напрямую — переход на ручной цикл (`items` с явным построением плоского списка `[MessageEntity | DateSeparator]` перед рендером, аналогично тому, как Compose-мессенджеры обычно строят такой список) или на `item {}` внутри `itemsIndexed` через дополнительную проверку и prepend условного `item` — точный механизм фиксируется в реализации (вероятно: построить `List<ThreadListItem>` = `sealed class { Message(entity); DateHeader(label) }` один раз через `remember(uiState.messages)`, затем `items(threadListItems, key = ...)`).

## Архитектура

- Новый файл (или дополнение `MessageGrouping.kt`) с `isFirstOnNewDay`, юнит-тестируемый отдельно от Compose.
- Изменения в `ThreadScreen.kt`: `ThreadContent` строит список для `LazyColumn` с учётом разделителей; новый приватный composable `DateSeparatorRow` (центрированный `Text`, `Modifier.fillMaxWidth()`, `TextAlign.Center`, отступы сверху/снизу).
- `ThreadTestTags` — новый тег для разделителя (`fun dateSeparator(index: Int)` или по дате).

## Критерии приёмки

- Между сообщениями, чьи `createdAt` попадают на разные календарные дни, показывается центрированный текст с датой.
- Между сообщениями одного календарного дня разделитель не показывается, независимо от разрыва по времени.
- Существующая группировка по отступу (спека 0029) не меняется и не ломается разделителем.
- Автотесты: unit на `isFirstOnNewDay` (смена дня/тот же день/первый элемент/полночь как граница), androidTest на видимость разделителя в `ThreadScreen` при переходе через полночь в тестовых данных.
- Полный регресс без perf-пакета зелёный.

## Тесты

- Unit (`MessageGroupingTest.kt`): `isFirstOnNewDay` — первый элемент, тот же календарный день (в т.ч. разрыв в 20 часов внутри одного дня), пересечение полуночи (23:59→00:01, разрыв 2 минуты — всё равно новый день).
- androidTest (`ThreadScreenTest.kt`): `dateSeparatorAppearsWhenMessagesCrossMidnightButNotWithinTheSameDay` — 3 тестовых сообщения (два в один день, одно на следующий), проверяет, что заголовок первого дня и заголовок второго дня оба отображаются, а всего разделителей ровно 2 (не 3 — между двумя сообщениями одного дня разделитель не появляется).
- Существующие тесты `ThreadScreenTest` (скролл к целевому сообщению, анимация до конца, long-press выделение) обновлены под новую структуру `LazyColumn` (плоский список `ThreadListItem` вместо прямого списка сообщений) — все проходят без изменения ожидаемого поведения.

## Результаты

- Компиляция (`compileDebugKotlin`/`compileDebugUnitTestKotlin`/`compileDebugAndroidTestKotlin`) — чисто.
- `:app:testDebugUnitTest` — зелёный, включая новые тесты `isFirstOnNewDay`.
- `:app:connectedDebugAndroidTest` на TECNO LI9 (устройство восстановилось после сессии, где ранее зависало с чёрным экраном, — заработало без вмешательства) — **полный регресс 161/161 зелёный**, включая изолированный прогон `ThreadScreenTest` (14/14) на этапе отладки.
- В процессе реализации найден и исправлен реальный баг (не в этой фиче, а привнесённый смежной правкой в той же сессии — см. `docs/Metrics.md`): перенос `combinedClickable` с `Column` на родительский `Row` (по просьбе пользователя — "кликать по всей полосе") слил semantics `testTag`'а бабла в родительский merged-tree узел, из-за чего `onNodeWithTag(bubble(id))` без `useUnmergedTree = true` переставал находить узел — тот же класс проблемы, что уже задокументирован в `docs/Metrics.md` (запись #1, спека 0029). Исправлено добавлением `useUnmergedTree = true` во всех местах поиска по тегу `bubble(...)`.
- Живая проверка на TECNO LI9 не завершена в рамках этой сессии — приложение на устройстве требует переназначения SMS-приложением по умолчанию/разрешения на уведомления при повторной установке, что является изменением реального системного состояния пользовательского телефона и не выполняется без отдельного явного согласия (риск: смена SMS-приложения по умолчанию на реальном устройстве пользователя). Полный regression suite на реальном устройстве считается достаточным подтверждением корректности по правилам проекта; чисто визуальная проверка разделителя остаётся открытым пунктом при следующей возможности.
