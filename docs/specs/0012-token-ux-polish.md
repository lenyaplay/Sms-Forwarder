# 0012 — UX-доработки токенов и полей ввода (Android)

**Статус:** Implemented

## Контекст

Обнаружено при ручном тестировании Milestone 10 (спека `0011`) на физическом устройстве: длинные значения токенов (`upload_token`, `download_token`), отображаемые как обычный `Text`, растягивают/переполняют экран вместо переноса на новую строку. Плюс три отдельных UX-запроса от пользователя, собранные вместе как один пакет мелких доработок: копирование токенов в буфер обмена, копирование готового webhook-URL для `upload_token` (нужно стороннему Gateway App), показ/скрытие пароля на полях ввода.

## Допущения и решения (assumptions log)

Зафиксировано через `stakeholder-requirements-gathering` (`AskUserQuestion`) перед написанием этой спеки:

1. **Тесты — на всё, что не должно меняться.** Пользователь не сузил переполнение до одного конкретного экрана явно, а сформулировал общее требование: покрыть тестами то, что должно оставаться стабильным (не растягиваться). Поэтому исправление переполнения и тесты на него применяются ко **всем** местам, где сейчас отображается токен как `Text` (не как поле ввода): `DeviceDetailScreen` (`UPLOAD_TOKEN_TEXT`, `INVITE_TOKEN_TEXT`, элементы списка `download_token`), `CreateDeviceScreen` (`UPLOAD_TOKEN_TEXT`).
2. **Способ переноса — зависит от контекста.** Пользователь явно разделил: (а) для полей ввода (`OutlinedTextField`, напр. URL/имя/токен на `ServerSetupScreen`/`CreateDeviceScreen`/`AddDeviceScreen`) — «нужно одно решение» — это уже штатное поведение `OutlinedTextField(singleLine = true)` (внутренняя горизонтальная прокрутка текста поля, сам компонент не растягивается) — изменений не требует, задокументировано как явно проверенное допущение, а не забытое; (б) для отображения токена как `Text` (не поле ввода) — перенос по словам/символам на следующую строку (`Modifier.fillMaxWidth()`, стандартный `softWrap` — по умолчанию `true` в Compose `Text`, но сейчас ширина контейнера не ограничена `fillMaxWidth()`, отсюда растягивание).
3. **Кнопка «Скопировать»** — на каждый токен, отображаемый как `Text` в местах из допущения 1 (полный список: `upload_token` на `CreateDeviceScreen`; `upload_token`, сгенерированный `download_token`-приглашение и каждый `download_token` в списке выданных — на `DeviceDetailScreen`). Использует `ClipboardManager`/`ClipEntry` (Compose `LocalClipboard`/`androidx.compose.ui.platform.ClipboardManager`), показывает подтверждение — `Snackbar` с текстом «Copied».
4. **Кнопка «Скопировать webhook URL»** — вторая, отдельная кнопка рядом с `upload_token` (не заменяет кнопку «Скопировать токен», обе присутствуют одновременно). Формат — по спеке `0003-sms-webhook.md`: `{текущий server URL}webhook?upload_token={upload_token}` (использует уже настроенный `ServerConfigStore.getUrl()`). Присутствует в двух местах: `CreateDeviceScreen` (сразу после создания устройства) и `DeviceDetailScreen` (при просмотре текущего `upload_token` и после его перевыпуска — новый URL с новым токеном).
5. **Показ/скрытие пароля («глазик»)** — на всех полях пароля в приложении: `LoginScreen` (поле пароля), `RegisterScreen` (поле пароля и поле подтверждения пароля — у каждого своя независимая кнопка-переключатель видимости, не общая на оба поля). Реализация — стандартный Compose-паттерн: `PasswordVisualTransformation()` при скрытом состоянии, `VisualTransformation.None` при показанном, `IconButton` с иконкой `Visibility`/`VisibilityOff` как `trailingIcon` поля.
6. **Это новый Milestone/новая спека**, не патч к `0011` — `0011` описывает отдельный, уже завершённый (технически) набор изменений (экран создания устройства, разрешение камеры, тёмная тема); эта спека — независимый набор UX-доработок поверх него, часть которых (кнопки на `CreateDeviceScreen`/`DeviceDetailScreen`) физически находится в тех же файлах, но логически не входит в scope `0011`.

## API / интерфейс

Изменений на бэкенде нет. Новых сетевых вызовов нет — используется уже сохранённый `ServerConfigStore.getUrl()` для построения webhook-URL на клиенте.

## Экраны и сценарии

### `CreateDeviceScreen` (изменение существующего)
- После создания устройства рядом с текстом `upload_token`: кнопка «Copy token» (копирует голый токен) и кнопка «Copy webhook URL» (копирует `{serverUrl}webhook?upload_token={token}`).
- Текст токена оборачивается в `Modifier.fillMaxWidth()` — перенос на несколько строк вместо растягивания экрана.

### `DeviceDetailScreen` (изменение существующего)
- Текущий `upload_token`: кнопка «Copy token» + кнопка «Copy webhook URL» (использует актуальное значение токена — после перевыпуска кнопки используют уже новый токен, т.к. читают его из текущего `uiState`).
- Сгенерированный `download_token`-инвайт (после «Generate invite»): кнопка «Copy token».
- Каждый элемент списка выданных `download_token`: кнопка «Copy token» рядом с кнопкой «Revoke».
- Все текстовые представления токенов — `Modifier.fillMaxWidth()` с переносом.

### `LoginScreen` / `RegisterScreen` (изменение существующего)
- Поле(-я) пароля получают `trailingIcon` — `IconButton` с переключением `PasswordVisualTransformation()` ↔ `VisualTransformation.None`, иконка меняется между `Icons.Default.Visibility`/`Icons.Default.VisibilityOff`.
- На `RegisterScreen` два независимых переключателя — для «Password» и для «Confirm password».

## Критерии приёмки

- Токен любой реалистичной длины (проверено тестом с длинной синтетической строкой), отображаемый как `Text` на `CreateDeviceScreen`/`DeviceDetailScreen`, переносится на несколько строк и не расширяет/не обрезает родительский контейнер за пределы ширины экрана.
- Нажатие «Copy token» кладёт точное значение токена в системный буфер обмена (проверяется через `ClipboardManager` в тесте) и показывает подтверждение.
- Нажатие «Copy webhook URL» на `CreateDeviceScreen` и на `DeviceDetailScreen` кладёт в буфер строку вида `{serverUrl}webhook?upload_token={upload_token}`, где `serverUrl` — реально сохранённый в `ServerConfigStore` адрес.
- На `LoginScreen` и `RegisterScreen` нажатие на иконку-глазик показывает пароль открытым текстом, повторное нажатие скрывает обратно; на `RegisterScreen` переключение видимости пароля не влияет на видимость подтверждения пароля и наоборот.

## Тесты

- **Instrumented/UI:**
  - `CreateDeviceScreenTest`/`DeviceDetailScreenTest` — новые тесты: длинный синтетический токен (например, 128 символов) не превышает ширину экрана (`assertWidthIsAtMost` на корневой контейнер экрана или сравнение ширины текстового узла с шириной окна теста); нажатие «Copy token» кладёt правильное значение в `ClipboardManager`; нажатие «Copy webhook URL» кладёт корректно собранную строку (с фиксированным `ServerConfigStore` в тесте).
  - `LoginScreenTest`/`RegisterScreenTest` — новые тесты: по умолчанию пароль скрыт (`PasswordVisualTransformation`, текст поля не читается как введённый); после клика по иконке видимость переключается (текст читается открытым); на `RegisterScreen` независимость переключателей для двух полей паролей — включение видимости одного не включает видимость другого.
- **Unit (JVM):** не требуется — вся логика этой спеки чисто UI-уровня (Compose state + ClipboardManager), без новой ViewModel-логики, кроме тривиального `mutableStateOf` для видимости пароля/показанного состояния копирования, которое покрывается инструментированными тестами по существующей конвенции проекта (см. спеку `0011` — ViewModel-тесты для простых UI-стейтов в проекте не заводятся отдельным unit-файлом).

## Открытые вопросы / Backlog (не блокируют Draft → Implemented)

- Кнопка «Copy webhook URL» не валидирует, что `ServerConfigStore` вообще содержит непустой URL (на экранах, где она показывается, это уже гарантировано — пользователь залогинен, значит URL настроен; отдельная защита не требуется).

**Проверено вручную**: на физическом устройстве — реальный `upload_token` (43 символа) на `DeviceDetailScreen` переносится на 2 строки без выталкивания кнопок за пределы экрана; кнопка «Copy webhook URL» скопировала в буфер обмена (проверено фактической вставкой в текстовое поле) точную строку `http://127.0.0.1:8080/webhook?upload_token=<токен>`, совпадающую с форматом спеки `0003-sms-webhook.md`; переключатель видимости пароля на `LoginScreen` — пароль реально стал открытым текстом при нажатии «Show», кнопка сменилась на «Hide».

Реализация — текстовые кнопки («Copy», «Show»/«Hide»), не графические иконки: `Icons.Default.ContentCopy`/`Visibility`/`VisibilityOff` отсутствуют в `material-icons-core` (только в неподключённом `material-icons-extended`) — подтверждено проверкой jar-архива зависимости. Соответствует букве спеки (везде «кнопка», не «иконка»), подтверждено `peer-review-template`.

В процессе `peer-review-template` найден и исправлен дефект теста: `longTokenDoesNotPushDoneButtonOffscreen`/`longDownloadTokenDoesNotPushRevokeButtonOffscreen` изначально использовали `assertExists()`, который прошёл бы даже при реальном переполнении (semantics-дерево Compose включает элементы за пределами экрана) — заменено на `assertIsDisplayed()`, тесты перепрогнаны, зелёные.

`./gradlew :app:connectedDebugAndroidTest` — 44 теста, 0 падений (физическое устройство). `./gradlew :app:testDebugUnitTest` — все зелёные.
